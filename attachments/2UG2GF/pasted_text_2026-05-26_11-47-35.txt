우선순위 원칙: **임팩트 ÷ 비용** + **횡단 적용 가능성** + **카테고리 이탈 방지 긴급도**
⚠️ 본 로드맵은 인터뷰 인사이트 기반 우선순위 가설

## 0. 프레이밍

### 0.1 핵심 명제

> **어드민 사용의 일상화 + 카톡 사용의 비일상화**
> 
- 이를 통해 회사 제휴팀의 시간이 **반응형 트랜잭션 처리 → 관계·전략·영업**으로 재배분됨
- 워크로드 감소가 아니라 **시간 가치의 이동**이 목표

### 0.2 채널 분리 원칙

| 구분 | 채널 | 어떤 작업 |
| --- | --- | --- |
| **일상·주기** | 어드민 | 예약 확인/확정/취소, 스케줄, 가격·메뉴, 콘텐츠, 고객 메시지, 리뷰 응대, 정산 |
| **비일상·예외** | 카톡 | 신규 상품 등록, 분쟁/이슈, 비즈니스 전략·이벤트 제안, 시스템 장애, 권한·계약 |

### 0.3 두 종류의 흡수

| 흡수 유형 | 대상 | 예시 |
| --- | --- | --- |
| **자율 처리 흡수** | 직접 처리 의향 있는 파트너 | 투어스토리 콘텐츠 편집, 모델로 사진 교체, 호수도산 인스타 연동 |
| **요청 채널 흡수** | 직접 처리는 부담스러운 파트너 | 메디큐브 — 어드민으로 요청 → 가시적 진행 상태로 카톡을 대체 |

→ 단일 정책 X. 파트너 유형별로 두 갈래를 모두 지원

### 0.4 파트너 본질·페인 매핑 (means-ends chain)

> 종합본 1.5 + 개별 정리본 "파트너가 실제로 겪는 문제" 섹션 cross-reference
> 

| 파트너 | 본질 한 문장 | 가장 강한 페인 |
| --- | --- | --- |
| 순시키 | 감당 가능한 인지 부담으로 모든 채널의 예약 직접 통제 | 가용성 통제 / 채널 통합 / 재방문 식별 |
| 메디큐브 | 양측 기대가 어긋나지 않도록 정보가 양방향 도달 | 입력 정확성 / 동행 처리 / 다이렉트 메시징 |
| 모델로 | 변화가 잦은 비즈니스가 즉시 반영 + 유연한 구조 | 상품별 스케줄 / 콘텐츠 반영 속도 / 실시간 가시성 |
| 투어스토리 | OTA 표준 수준의 자율 권한 + 다스팟·다국어 효율 | 자율 편집 / 검색 / 다국어 / 일괄 처리 |
| 아리한복 | 파워유저 운영 수준에 어드민이 도달, 일상 도구화 우선 | 예약 테이블 UI / 사진 업로드 / 메타 피드백 |
| 호수도산 | 손에서 즉시 통제 + 브랜드 자산 능동 관리 | 모바일 앱 / 다이렉트 메시징+번역 / 리뷰 동선·관리 / SNS 연동 |

**해석 가이드**: 단일 항목이 여러 파트너의 본질을 동시에 해결하면 우선순위 ↑ (예: 다이렉트 메시징 = 메디큐브·호수도산·순시키 3개 본질에 동시 기여)

### 0.5 측정 전략

**한계**: 카톡은 각 매니저 개인 카톡을 사용하므로 **직접 데이터 수집 불가**. 따라서 "어드민 사용량 증가 = 카톡 감소"라는 **간접 가정 위에서** 평가.

| 차원 | 방법 | 빈도 |
| --- | --- | --- |
| **정량 (어드민 사이드)** | `general_click_event` 활용 — 기능별 사용량, 활성 파트너 수, 자율 처리 수정 요청 건수, 메시지 발송 건수, 작업 완료율 | 상시 / 월간 리뷰 |
| **정성 (카톡 사이드)** | 카테고리 매니저별 구조화 인터뷰 — 정해진 카테고리로 카톡 요청 유형 회상·표시 | 분기 1회 |
| **이벤트 기반 (출시 임팩트)** | 신규 기능 출시 전후 30/60/90일 사용·우회 변화 | 항목별 |

## 축 1. 어드민·유저페이지 신뢰성·사용성 강화

> 이미 어드민에 존재하는 기능·페이지의 신뢰도와 사용성을 끌어올려, 일상 업무가 자연스럽게 어드민으로 옮겨가도록 함. **트랙 B(제휴팀 운영 변화)와 항상 병행**.
> 

### 1-a. 신뢰성 회복 — 버그픽스 + 알림 누락

**왜**: 신뢰 손상은 사용 회피의 가장 빠른 원인으로, 버그 한 건이 디스커버리 노력 전체를 무효화할 수 있음

**대상 항목**

- 모바일 예약 확정 화면 요일 오노출 (메디큐브 — 5/12 토 표시)
- ~~어드민 사진 수정요청 메뉴 표시 사진 ≠ 실제 관리 사진 (모델로)~~ → 개선 진행 중
- 예약 캘린더 1년치 오픈 시 기존 차단 타임 초기화 (메디큐브)
- 리뷰 작성 알림 누락 (메디큐브 인지)
- 알림 발송 신뢰성 전반 점검 + 대시보드로 가시화

### 1-b. 디스커버리 / 온보딩 강화 [트랙 B 병행 필수]

**왜**: 알림톡·리뷰 댓글+자동번역·직접 취소·상품별 스케줄 등 **이미 있는데 모르는 기능**이 모든 파트너에 다수

**제품 측 작업**

- 어드민 첫 로그인/주기적 인앱 가이드 (사용 안 한 기능 안내)
- 체크리스트 위젯: 알림톡 ON, 리뷰 댓글 활성화, 직접 취소 권한 확인 등

**제휴팀(트랙 B) 측 작업** — 병행 필수

- 카톡 요청 받았을 때 **"이건 어드민에서 직접 하실 수 있어요" 응답 템플릿** (안내 + 동선 스크린샷)
- 신규 기능 출시 시 카테고리 매니저가 담당 파트너에게 1:1 안내
- 활용도 높은 파트너(아리한복·순시키)부터 우선 적용 고려 가능

### 1-c. UIUX 폴리싱 (어드민 자체)

**왜**: 어드민을 일상 도구로 쓰는 파워유저(아리한복 등)에게서 누적된 구체적 페인. 사용량 높을수록 디테일 페인이 드러남.

**대상 항목**

- **예약 내역 테이블 리팩토링** (아리한복 제안 + 다스팟 검색 결합)
    - 컬럼 단순화: 예약 코드 / 날짜 / 시간 / 이름 / 상태
    - 상태 컬러 코딩 + 행별 컬러
    - 소팅 + 상품/이름/날짜 검색
- **예약 처리 흐름 단순화** (확정·취소·변경)
- **스팟 정보 수정 접근성** — '스팟 정보 수정 요청' 메뉴 노출·재진입성 강화
- **수정 요청 진행 가시성** — 받음 → 검토 중 → 반영 완료 단계 표시 + 알림 (투어스토리 3개월 / 모델로 1개월 대기 사례)
- 스팟 상세 편집의 사진 포맷·옵션 사진 등 디테일 (아리한복)

### 1-d. 유저페이지 개선

**왜**: 어드민만 고쳐서는 닫히지 않는 일상 페인. 입력·인지·정합성이 깨지면 다운스트림(예약 확정·연락·리뷰) 모두 깨짐.

**대상 항목**:

- **입력 단계 검증 UX** (메디큐브) — 전화/이메일 2회 입력, SNS ID 공개 여부 안내
- **여권명 기준 통일** (영문 입력 표준화) — CRM 분산 방지
- **재방문 고객 자동 표시** (순시키 — 등록번호 기반)
- **가격 인지 강화** (메디큐브 — 보증금만 노출되어 전체 가격 인지 실패)
- **상세페이지 정보 가독성**
    - ~~이벤트 토글 vs 직노출 — 파트너별 설정 가능~~ → 개선 중
    - 상단 공지/조건 시각적 강조

## 축 2. 신규 기능 추가

> 어드민에 없거나 우회 처리되고 있는 일상 작업을 어드민에서 처리하도록 신규 구축 (기능에 대한 권한 설정은 논의하며 결정)
> 

### 2-a. 신규 기능

- **2-a-1. 고객 - 파트너 다이렉트 메시징 + 자동 번역 ⭐⭐⭐**
    
    > **원천**: 메디큐브(왓츠앱 우회), 호수도산(톡방+번역), 순시키(CX팀 카톡), 모델로
    **현재 우회**: 왓츠앱, 톡방, CX팀 카톡, 이메일(느림)
    > 
    - 어드민에서 고객에게 직접 메시지 발송
    - 메시지 입력 시 **자동 번역** 옵션 (언어 자동 감지)
    - 알림톡/메일 동시 전달
- **2-a-2. 기타 신규 후보 (호흡 중장기)**
    - 동행 예약 처리 — 동행 식별 정보, 묶음 표시 (메디큐브)
    - 다국어 자율 편집 + AI 자동 번역 (투어스토리·모델로)
    - ~~비회원 리뷰 작성 허용~~(개발됨) + 리뷰 작성 동선 단순화 (호수도산·메디큐브)
    - 다스팟 운영 도구 — 일괄 처리·다건 복사 (투어스토리·호수도산)

### 2-b. 카테고리 특화 기능 (호흡 길게)

- **프레임**: 피부과 카테고리에 이미 있는 '시술 정보 관리'·'수가표 관리'와 **같은 결**의 카테고리별 1급 기능 추가. 현재 어드민의 텍스트 에디터로 관리되고 있는 정보를 카테고리별 1급 자료 구조로 끌어올림.
- **예시 후보** (세부는 별도 정리)
    - 일일투어 — itinerary(일정표) 관리, 출발·코스·옵션 구조화
    - 헤어/뷰티 — 시술 옵션·소요 시간·시술자 배정
    - 사진 스튜디오 — 패키지·옵션 조합·헤어메이크업 포함 여부
    - 한복/문화 — 대여 옵션·인원·시간대 슬롯 운영
- **시작 카테고리 결정 인풋**
    - 카테고리별 파트너 수·매출·예약 비중 (P0 데이터 작업)
    - 카테고리별 어드민 활용도

→ **호흡 길게**. 각 카테고리 매니저와 개별 정의 필요. 한 카테고리씩 진행.

## 축 3. 모바일 환경 최적화

> 일상 사용성·즉시성을 위해 모바일 경험이 카테고리 표준에 도달해야 함. **호수도산 케이스 = 모바일 부재로 다른 OTA에 예약 이탈** 실증.
> 

### 모델 (잠정 합의)

| 버전 | 스코프 |
| --- | --- |
| **v1** | 예약 관리 (확인·확정·취소) + 알림 (사용 파트너 알림톡 OFF로 전환) |
| **v2** | DM 기능 (어드민에서도 동일 사용) — 축 2-a-1과 정렬 |
- 제휴팀이 카테고리 매니저를 통해 **사용 파트너에게 직접 권유**
- 사용 결정 파트너에 한해 알림톡 OFF 전환

### 열린 결정 — 개발자 논의 필요

| 결정 항목 | 상태 |
| --- | --- |
| **PWA vs 네이티브 앱** | 잠정: PWA 충분 가설 — 추가 파악 필요 |
| v1·v2 분리 출시 vs 통합 | 미정 |

**PWA 메모**

- Android는 푸시 잘 작동
- iOS는 Safari 16.4+ + "홈 화면 추가" 필수 — install rate가 도달 병목
- 제휴팀이 직접 권유하는 모델이라 install 안내 동반 가능 → PWA에 친화적
- 단, iOS 푸시 신뢰성·백그라운드 제약은 네이티브보다 약함

→ 개발자 회의에서 iOS 비중 + install rate 가설 + 푸시 신뢰성 요구 수준으로 결정

## 트랙 B. 제휴팀 운영 변화 (축 1·2 병행)

> **별도 트랙이 아니라 축 1·2의 일부**. 각 축의 출시 체크리스트에 박혀야 굴러감.
카테고리별 매니저들이 분산 책임, 제휴팀과 소통하면서 코디네이션.
> 

### B-1. 능동적 리다이렉트 운영

- 카톡 요청 받았을 때 **"이건 어드민에서 직접 하실 수 있어요" 응답 템플릿** (안내 + 동선 스크린샷)
- 1-b 디스커버리 작업과 1:1 결합

### B-2. 신규 기능 출시 시 적극 안내(영업)

- 카테고리 매니저가 담당 파트너에게 1:1로 안내
- 활용도 높은 파트너부터 시작 — 디자인 베이스라인 검증자로 활용
    - 아리한복은 본인이 콘텐츠 생산까지 자임하는 파워유저로, UX 디테일 페인을 가장 정확히 짚어냄

### B-3. 카톡 요청 유형 분류 (정성 추적)

- 분기 1회 카테고리 매니저별 구조화 인터뷰
- 카톡 요청을 일상/예외, 작업 유형, 카테고리별로 분류·집계 → 기능 우선순위 재조정 인풋 (특히 축 2 카테고리 특화)
- ⚠️ **카톡 직접 수집 불가** 제약으로 정성·후행 지표 한계 인정

## 의사결정이 필요한 영역 (제품·운영 리더십 차원)

1. **모바일 앱 투자 규모와 모델 (PWA vs 네이티브)** — 가장 큰 단일 투자. 잘못 잡으면 다른 축을 통째로 잠식. iOS 비중·install rate·푸시 신뢰성 요구 수준 확인 후 결정.
2. **권한 등급제 운영 모델** — 기능보다 운영팀 R&R 재설계가 본질. 기존 논의 채널에서 정책 합의 선행.
3. **OTA 표준 격차 대응 속도** — 호수도산은 이미 KKday로 빠지는 중. 카테고리별 잔존율 데이터 확인 필요.
4. **제휴팀 KPI 재정의 합의** — 반응형 지표 → 관계·전략·영업 지표 전환. 운영 리더십 합의 필수.
5. **다스팟 파트너 비중** — 투어스토리 같은 다스팟 운영자 비중에 따라 2-a-3 다스팟 도구 우선순위 조정.
6. **어드민의 장기 정체성** — 단순 "운영 효율 도구"인가, "파트너 마케팅·브랜딩 인프라"(인스타·아카데미·이벤트 채널)까지 확장할 것인가. 호수도산처럼 디지털 네이티브 파트너 비중·증가 추세를 데이터로 확인 후 제품 리더십 의사결정.
7. **리뷰 시스템의 플랫폼 가치관** (2-a-3 리뷰 선행 조건) — 부정 리뷰 처리·작성자 차단 영역의 입장. KKday 모델 답습 vs 독자 균형점. 파트너 만족 ↔ 유저 신뢰의 양면.
