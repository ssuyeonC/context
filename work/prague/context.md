## Frame

- 목표: 어드민 전용 '시술 정보 관리'(K뷰티 시술) 기능을 파트너에게도 개방.
- 페이지 구조: `/beauty-treatment` (admin 앱, `BeautyTreatments.tsx`) = 2탭
  - 탭1 "시술 정보 관리"(`BeautyProcedureTable`) = 전사 공용 시술 카탈로그 CRUD (보톡스 등 정의·번역·카테고리·부가정보)
  - 탭2 "시술 연결 관리"(`BeautySpotTable`) = 스팟 단위 시술 옵션 활성화·가격·가격비공개
- 현행 권한: FE 라우트/Nav `ADMIN_AND_SUPER_ADMIN`; BE `@Roles(ADMIN, SUPER_ADMIN)` (`beauty-admin.resolver.ts`), 파트너-스팟 소유권 스코핑 없음(모든 어드민이 전부 열람).
- 파트너 모델: 같은 admin 앱 로그인, `PartnerNav.tsx`로 완전 분리된 메뉴트리. 기존 파트너 기능=대시보드/예약/정산/스팟(리뷰·수정요청·생성요청). `Reservations`·`SpotReviews`가 `isPartner` 분기로 자기 데이터만 보는 참고 패턴.
- **배경(왜 파트너에 여는가)**: 원래 크리에이트립 피부과 담당자용으로 설계된 기능(시술+하위 부가정보 생성 → 스팟에 연결). 피부과 수 증가 + 시술 정보 변동 빈도 상승으로 담당자가 전 스팟 변경을 다 챙기기 어려워짐 → 각 피부과 파트너가 자기 스팟을 직접 관리하도록 이관하려는 것.
- **데이터 구조(확인)**: `beauty_procedure`(시술, 글로벌, categoryCode) → `beauty_procedure_option`(부가정보, 글로벌, FK beautyProcedureId, default_price_krw=템플릿 기본값) → `spot_beauty_option`(스팟 연결: spotCode + beautyProcedureId + optionId + **priceKrw=스팟별 실제 가격** + isActive + displayOrder + before/after image + isPriceHidden). 즉 시술·부가정보 둘 다 공용 카탈로그, **가격은 이미 스팟별**로 분리 저장됨.
- **미해결 설계 리스크(부가정보 소유 모델)**: 부가정보가 글로벌 공용이라 파트너 자율관리 시 어색(클리닉마다 옵션 라인업 상이). 단, 어색함은 '부가정보 정의/라벨' 레이어에 국한 — 시술 글로벌 유지·가격 스팟별은 그대로 둘 수 있음. 전면 재설계 아님.

## Decisions

- **[2026-08-24] 파트너 개방 스코프 = A + 요청 흐름**
  - 파트너는 **자기 스팟의 시술 연결·가격·가격비공개만** 관리(탭2 성격). 전사 공용 시술 카탈로그(탭1)는 **어드민 전담**.
  - 카탈로그에 없는 시술 필요 시 파트너가 어드민에 **'추가 요청'** → 기존 스팟 생성요청/수정요청 승인 패턴 재사용.
  - 근거: 시술 카탈로그는 전 파트너 공용 마스터 데이터라 개별 파트너 편집 시 오염 위험(B 배제). 공백은 요청 흐름으로 해결.
- **[2026-08-24] 파트너 편집 방식 = 직접 편집(승인제 아님).** 근거: 이미 파트너가 스팟 정보 일부를 직접 변경하는 구조가 존재. 시술 옵션·가격 변경도 파트너가 즉시 반영.
- **[2026-08-24] "시술 추가 요청" = 정식 요청 엔티티/워크플로우로 구축.** 경량(메모/CS) 아님. 기존 스팟 생성/수정요청 승인 UX 참고.
  - ※ 아래 부가정보 (2) 결정으로 요청 범위 축소: 파트너가 요청하는 건 **신규 '시술'(procedure)뿐**. 부가정보는 파트너가 직접 생성하므로 요청 불필요.
- **[2026-08-24] 뷰티 스팟 대상화 = 자동 노출 우선, 단 admin-designates 폴백 허용(조건부).**
  - 1순위(자동 노출): 별도 '연결할 스팟 추가' 없이 파트너 스팟이 피부과(3068)/시력교정(3099)이면 자동으로 관리 대상. → 현 shell-row 모델 변경 필요(목록/categoryCounts/isPriceHidden이 명시적 shell row에 의존). isPriceHidden은 최초 저장 시 lazy 생성 등으로 처리.
  - 폴백(admin-designates): shell-row 구조 변경 품이 크면 **현 구조 유지** + 어드민이 파트너에게 열어줄 스팟을 명시 지정(기존 `createBeautySpot`=열림 마커 재사용) + 파트너 소유권 스코핑만 추가. 최소 변경.
  - 폴백은 단순히 저비용이 아니라 **롤아웃 통제** 이점도 있음(파일럿 클리닉부터 점진 개방). v1 전략으로 오히려 유리할 수 있음 → 구현 견적 시 확정.
- **[2026-08-24] 부가정보 소유 모델 = (2) 스팟/파트너 소유로 이전.** 시술(procedure)은 글로벌 유지, 부가정보(option)는 스팟 소유로. 파트너가 자기 스팟의 옵션 라벨을 직접 정의. 클리닉별 옵션 상이에 대응.
  - 현행 플로우(확인): 탭1에서 시술+글로벌 부가정보 정의 → 탭2 스팟상세(`BeautySpotDetailModal`)에서 글로벌 옵션들에 대해 가격/활성화/이미지만 설정(옵션 신규 생성 불가).
  - (2)의 파급:
    1. 스팟 상세 모달이 "옵션 신규 추가 + 라벨 정의 + 가격" UI로 확장(현재는 기존 옵션 가격/활성화만).
    2. 탭1 `BeautyProcedureTable`의 부가정보 관리(`ProcedureOptionModal`)는 폐지/성격 변경 → 탭1은 '시술' 글로벌 카탈로그만.
    3. 스키마: 글로벌 `beauty_procedure_option`(+trans) 폐지 또는 스팟 스코프 옵션 엔티티 신설, `spot_beauty_option.optionId` FK 대상 변경.
    4. 마이그레이션: 기존 글로벌 부가정보 + 이를 참조하는 `spot_beauty_option` 레코드 → 스팟 소유 옵션으로 복제/이전(라벨·번역 보존).

  - **[2026-08-24] 옵션 라벨 번역 정책 = 자동번역 게이트.** 파트너는 자동번역 기능(`useBeautyAutoTranslate` 등)으로 옵션 라벨 번역 → **번역이 완료된 상태여야만 해당 옵션을 공개(활성화/유저 노출) 가능.** 미번역 옵션은 노출 차단.
