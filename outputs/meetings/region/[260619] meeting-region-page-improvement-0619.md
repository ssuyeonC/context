## 0. 들어가며 — 오늘 미팅에 개발자가 들어온 이유

**PO**: 오늘은 지금까지의 페이지 개선 미팅(K-beauty, 파트너 등)과 같은 구성·포맷으로 가되, **개발자(FE 리드)를 처음부터 포함**합니다. 이유는 두 가지입니다.

첫째, 지역 페이지는 K-beauty 페이지와 달리 **이미 16개 섹션이 쌓여 있는 복잡한 페이지**예요. "무엇을 더 붙이느냐"보다 "**지금 구조가 데이터가 말하는 수요와 맞는가**"를 먼저 따져야 하는데, 그건 코드 구조를 아는 사람이 같이 봐야 정확합니다.

둘째, 오늘 나올 아이디어 중 일부(다도시 시간배분, 지역 간 이동 지도)는 **기존 데이터 모델로 되는지 안 되는지**가 실행 가능성을 가릅니다. 기획이 다 끝난 뒤 "그건 백엔드가 없어요"를 듣는 낭비를 막으려고요.

**개발자**: 좋습니다. 미리 코드베이스를 훑어왔으니, 현재 구조를 먼저 깔고 시작하면 논의가 빠를 것 같습니다.

## 1. 데이터가 말하는 '지역' 수요 (Reddit 심층 분석 요약)

**Growth Manager**: 먼저 근거 데이터를 정리합니다. r/koreatravel 10,000개 중 목적지 테마 **5,554건(55.5%)**을 따로 분석한 결과입니다.

| 발견 | 수치 | 함의 |
|------|------|------|
| 지역 글의 질문/요청형 비율 | **89.1%** (전체 평균 83.2%보다 높음) | "지역 얘기 = 곧 도와달라는 질문" |
| 지역 글 내부 동반 주제 | 볼거리 **72.5%** > 추천 53.3% > 교통 52.8% > 일정 45.6% | 지역은 주제가 아니라 **컨테이너** |
| 다(多)도시 비교 게시물 | **27.4%** (`seoul busan` 바이그램 1위, 492회) | 한국여행 = **도시 포트폴리오/시간배분 문제** |
| 당일치기/근교 | 10.9% | 서울 허브 + 경주·전주·남이섬·DMZ 스포크 |

**Growth Manager**: 핵심 한 줄은 보고서 결론 그대로입니다.

> **"'지역'은 주제가 아니라 질문의 좌표계다."** 사용자는 지역을 *선택*하기보다, 정해진/검토 중인 지역 위에 **명소·이동·일정·거점**을 *얹어 최적화*하려 한다.

**PM**: 그리고 도시별로 니즈의 결이 명확히 다릅니다. 이게 오늘 개선의 핵심 단서예요.

| 도시 | 1순위 동반주제 | 한 단어 지문 |
|------|--------------|-----------|
| **서울** | 볼거리 > 추천 > 교통 > 일정 | **'무엇을 볼까' — 큐레이션** (콘텐츠 과잉) |
| **부산** | **교통(KTX)** > 볼거리 > 일정 | **'어떻게 갈까' — 접근성** (목적지보다 도달비용 먼저) |
| **제주** | 볼거리 > 교통 > 일정 > **체험/렌터카** | **'렌터카+거점' — 차량 전제** |

**Marketer**: 보고서에 인용된 실제 제목들이 이걸 잘 보여줍니다. 제주는 *"Where to **base** in Jeju for 6 nights with a baby, travelling with car"*, 다도시는 *"How many days in **Seoul/Busan**?"* — 유저는 "어디가 좋아요?"가 아니라 **"내 N일을 어떻게 쪼개고, 거기서 뭘 보고, 어떻게 이동하나"**를 묻고 있어요.

## 2. 현재 지역 페이지 구조 — 개발자 코드 브리핑

**개발자**: 코드 기준으로 현재 `/spot/region/[id]` 페이지가 어떻게 조립되는지 설명드립니다. (`SpotRegionDetailContents.tsx` 기준)

### 2-1. 페이지 = 16개 섹션의 수직 스택 + 전면 지도

좌측(데스크톱)/하단 시트(모바일)에 **상세 콘텐츠**, 중앙/전면에 **지도(RegionMap)** 구조입니다. 콘텐츠 섹션은 렌더 순서대로:

| # | 섹션 | 데이터 축 | 비고 |
|---|------|----------|------|
| 1 | 제목·평점·Popular 플래그 | `region.translations`, `reviewSummary` | |
| 2 | 좋아요 버튼 | `regionLikeCount` | |
| 3 | 지역 설명 | `translation.description` | |
| 4 | 위치 정보 | `translation.address` + `subwayCategories`(최대 3) | **유일한 교통 정보** |
| 5 | 베스트 포토 리뷰 | 별점≥4·이미지 리뷰 | |
| 6 | 지역 리뷰 캐러셀 | `region.reviews`(20) | |
| 7 | Spot 에어리어 | `regionSpotAreas`(큐레이션 묶음) | DB상 6개뿐(실험적) |
| 8 | 블로그 | detailLocation 기반 | |
| 9 | **추천 스팟** | legalCode 기반, 내부 알고리즘 | |
| 10 | **당일치기/투어** | 카테고리 933(서울근교투어) | **regionId 4·5·15(명동·홍대·동대문)만 하드코딩** |
| 11 | **최신 스팟** | RENEWAL_DATE DESC | |

| 15 | 유저 블로그 | regionId | |
| 16 | 장소(Place/POI) | regionId | |

### 2-2. 구조적 특징 3가지 (이게 오늘의 논점)

**개발자**: 데이터 관점에서 짚을 게 세 가지입니다.

1. **모든 스팟 섹션이 `legalLocationLegalCodes`(행정구역 코드) 단일 축으로 필터링됩니다.** 즉 "이 지역 폴리곤 안에 있는 스팟"을 가져와서 **정렬 기준만 바꿔(추천/최신/인기/리뷰)** 9·11·12·14번에 반복 노출하는 구조예요. 스팟 풀은 사실상 같고 **렌즈만 다릅니다.**

2. **'테마(theme)' 축이 코드에 존재하지 않습니다.** 섹션을 가르는 축은 (a) 지리(legalCode), (b) 데이터 신선도/인기(latest/popular/recommended), (c) 콘텐츠 타입(블로그/리뷰/숙소)뿐이에요. **"볼거리 / 교통 / 투어 / 식당" 같은 유저 의도(intent) 단위 묶음이 없습니다.**

3. **지도(RegionMap)는 "지역 내부" 전용입니다.** 스팟 마커 20개 + 숙소 마커 + 지역 경계 폴리곤을 그려요. '다른 지역' 버튼이 있긴 한데 이건 **지역 전환 스위처**일 뿐, "여기서 부산까지 KTX 2시간" 같은 **지역 간 이동 정보는 전혀 없습니다.**

**PO**: 잠깐, 지금 셋 다 §1 데이터랑 정면으로 어긋나는 지점이네요. 정리하면:

| 데이터가 원하는 것 | 현재 페이지 |
|---|---|
| 볼거리·교통·투어·식당을 **의도별로** 묶어달라 | 신선도/인기 축으로만 반복 노출 (테마 없음) |
| 다도시 **시간배분**(27%) | 단일 지역 카탈로그, 배분 도구 없음 |
| 지역 간 **이동**(부산=KTX가 1순위 니즈) | 지도는 지역 내부 POI만, 이동 정보 0 |
| 도시별 **다른 지문**(서울/부산/제주) | 16섹션이 모든 지역에 동일 적용(투어만 3개 하드코딩) |

이게 오늘 미팅의 출발점입니다.

### 2-3. region 엔티티 자체의 한계 (도메인 맵 교차)

**PM**: `region-domain-map.md`에서 확인된 DB 실측도 같이 봐야 합니다. region 테이블 514개 중 **498개가 서울**이고, 발행(is_publish) 페이지는 **로케일당 ~12개뿐**입니다. 부산·제주는 각 1개. 즉 **지금 지역 페이지는 사실상 '서울 동네 카탈로그'**예요.

**개발자**: 맞습니다. 그래서 §1의 "다도시(서울+부산+제주)" 수요를 이 엔티티로 바로 풀려고 하면 **부산·제주 region 콘텐츠가 비어있다는 벽**에 부딪힙니다. 이건 기능 이전에 콘텐츠 공백 문제예요.

**Growth Manager**: 그럼 오늘 논의를 **두 레벨로 분리**해야겠네요. (A) 기존 서울 동네 페이지를 데이터에 맞게 **재구성**하는 것, (B) 다도시/지역간 이동처럼 **엔티티·모델이 더 필요한** 것. (A)는 단기, (B)는 중기로요.

**PO**: 동의합니다. 그 프레임으로 갑니다.

## 3. 개선 아이디어 — 사용자 메모 3축 기반 논의

> PO 제공 메모를 세 축으로 재구성: ① 지도(지역 간 이동), ② 지역 트리(Things to do의 category × theme), ③ (메모에서 파생) 다도시 시간배분.

### 3-1. 축 ① — 지도: "지역 내 POI"에서 "지역 간 이동"으로

**PO**: 제 메모의 첫 줄이 이거였어요 — *"지역 내 POI 위치보다, 해당 지역에서 다른 지역으로 넘어가는 것에 대한 대략적 정보."*

**Marketer**: 데이터가 정확히 이걸 가리킵니다. 부산의 1순위 동반주제가 **교통(KTX)**이고, 다도시 비교가 27%예요. 유저 머릿속 질문은 "부산 안에 뭐가 있나"보다 **"서울에서 부산 어떻게/얼마나 걸려 가나"**가 먼저입니다.

**개발자**: 구현 관점에서 단계를 나눠보면:

| 단계 | 내용 | 데이터 필요 | 공수 감 |
|------|------|-----------|--------|
| **Lite** | 지역 페이지 상단/지도에 "여기서 주요 도시까지" 이동 요약 카드 (서울↔부산 KTX 약 2:40, 서울↔제주 항공 약 1:10 등) **정적 데이터** | 도시쌍 이동시간 테이블(수기/상수) | **소** (FE 위주, 1~2일) |
| **Map** | 지도 줌아웃 시 지역 간 연결선/소요시간 오버레이 | 좌표는 있음, 경로/소요시간 소스 필요 | 중 |
| **Dynamic** | 출발지 기반 실시간 경로(대중교통 API) | 외부 API 연동 | 대 |

**개발자**: 솔직히 **Lite부터 가는 걸 강력 추천**합니다. 도시쌍 이동시간은 거의 안 바뀌는 정적 정보라 상수 테이블로 시작해도 유저 가치의 80%를 줍니다. RegionMap에 손대는 Map 단계는 지금 지도 컴포넌트가 "지역 내부" 가정으로 짜여 있어서 줌/마커 로직을 꽤 건드려야 해요.

**Growth Manager**: 동의합니다. Lite는 "이동 정보 수요가 실제로 클릭되는가"를 **싸게 검증**하는 용도로도 좋아요. 클릭률 보고 Map 단계 투자 여부 결정.

**PO**: 축 ①은 **'지역 간 이동 요약 카드(Lite)'를 1순위 후보**로 둡니다.

### 3-2. 축 ② — 지역 트리: Things to do에 'theme' 축 도입

**PO**: 제 메모의 트리 구조였어요. 서울 > 강남/경복궁/명동 각각에 "Things to do(category: Activities… / **theme: ?**)", 그리고 교통·투어·식당. 부산·제주도 동일 패턴. 제가 **theme에 물음표**를 단 건, 이 theme 축을 뭘로 채울지가 안 풀려서예요.

**개발자**: 코드로 답을 드리면 — **지금 theme 축은 존재하지 않습니다.** 스팟은 category(Activities/Dining 등)와 지리(legalCode)로만 묶여요. 그래서 메모의 "category: Activities"는 지금도 되지만, "theme: ?"는 **신규 분류 축을 만들어야** 합니다.

**PM**: 그럼 질문을 뒤집죠. **theme을 뭘로 정의해야 §1 데이터를 충족하나?** 데이터에서 지역 글의 동반 주제 순위가 답을 줍니다 — 볼거리 / 추천(worth it) / 교통 / 일정 / 식당 / 체험 / 숙소. 이게 **유저 의도 단위**예요. 즉 theme ≈ **"이 지역에서 유저가 하려는 일(intent)"**.

**Marketer**: 한 발 더. 보고서에 **"명동·홍대·북촌·인사동은 제목엔 거의 안 나오고 본문에만 자주 등장"**한다는 발견이 있어요(북촌 173건 중 제목 6건). 이건 이런 동네가 **'주제'가 아니라 '서울 일정 안에 끼우는 구성요소(후보 리스트)'**로 소비된다는 뜻이에요. → 동네 페이지의 theme은 **"이 동네는 [한복체험/야경/쇼핑/카페] 하러 가는 곳"** 같은 **목적 태그**가 되어야 끼워넣기 좋습니다.

**PO**: 정리하면 theme 축의 후보 정의는 두 결입니다.

| theme 정의안 | 예 | 데이터 근거 | 개발 난이도 |
|---|---|---|---|
| **A. 의도(intent)별 묶음** | 볼거리 / 먹거리 / 교통 / 투어 / 쇼핑 / 체험 | 동반주제 순위 | 중 (category→intent 매핑 필요) |
| **B. 목적 태그(vibe)** | 야경·한복·카페투어·K-pop성지·로컬맛집 | 본문 빈출 지명의 소비 맥락 | 중~대 (태깅 체계 신설) |

**개발자**: 난이도 현실 체크. **A안은 기존 category를 intent 버킷으로 재그룹핑**하는 거라 비교적 가볍습니다 — 새 DB 축 없이 FE에서 category→섹션 매핑 테이블로도 1차 구현 가능해요. **B안(vibe 태그)은 스팟/지역에 새 태그 데이터를 붙여야** 해서 어드민·백엔드·콘텐츠 작업이 따라옵니다.

**Growth Manager**: 그럼 **A를 먼저, B를 나중에**가 자연스럽네요. A안으로 16개 신선도-축 섹션을 **"볼거리 / 먹거리 / 투어·체험 / 교통·이동 / 숙소" 의도 탭**으로 재편하면, 같은 데이터를 **유저 머릿속 구조에 맞게 재배열**하는 거라 콘텐츠 추가 없이도 체감이 큽니다.

**PM**: 중요한 건 이게 §2-2에서 본 **"같은 스팟 풀을 신선도 렌즈로 4번 반복"** 문제를 직접 해소한다는 거예요. 추천/최신/인기를 **의도 탭 안의 정렬 옵션**으로 흡수하면 섹션 중복도 줄고요.

**PO**: 축 ②는 **'Things to do의 intent 탭 재편(A안)'을 핵심 후보**로 두고, vibe 태그(B안)는 콘텐츠 로드맵과 묶어 중기 검토.

### 3-3. 축 ③ — 다도시 시간배분 (데이터 1순위 니즈)

**Growth Manager**: 메모엔 명시 안 됐지만 §1에서 **니즈 1순위가 "도시 간 시간 배분 가이드"**(다도시 27.4%)였어요. 이건 지역 *상세* 페이지가 아니라 그 **상위(지역 인덱스/허브)**에 들어갈 기능일 수 있습니다.

**PM**: 맞아요. "서울 4 / 부산 2 / 제주 2가 맞나"는 단일 지역 페이지에서 못 풀어요. **여행일정 검증 파일럿**(retention-d1, 3/16)이 이미 이 수요의 일부를 사람이 받고 있죠. 거기랑 연결하면:

```
[지역 페이지] 부산 보다가 "서울이랑 며칠씩 나눌지 모르겠다"
  → "다도시 일정, 전문가가 봐드려요" (검증 파일럿 진입점)
  → 또는 경량 "추천 배분" 프리셋: 7일=서울4/부산2/제주? 식 템플릿
```

**개발자**: 경량 프리셋(정적 추천 배분 템플릿)은 데이터 의존도가 낮아 붙이기 쉽습니다. 동적 최적화(실제 스팟·이동 계산)는 플래너 도메인과 얽혀서 별 트랙이에요.

**PO**: 축 ③은 **독립 기능이라기보다 '지역 페이지 ↔ 일정 검증 파일럿 연결 고리'**로 봅니다. 오늘 범위에선 *진입점 제안*까지만, 실제 배분 도구는 플래너 트랙과 합쳐 별도 논의.

### 3-4. 도시별 차별화 — '동일 16섹션'을 깨야 한다

**Marketer**: §1의 도시 지문이 다르다는 게 가장 강한 무기인데, 현재 페이지는 명동이든 부산이든 **똑같은 16섹션**이에요. 투어만 3개 지역 하드코딩됐고요.

**PM**: 그래서 **지역 타입별 '섹션 우선순위 프로파일'**을 제안합니다. 같은 섹션 풀에서 **순서·강조만 도시 지문에 맞게** 바꾸는 거예요. 신규 개발 최소, 효과는 큼.

| 지역 타입 | 최상단 강조 | 근거 |
|---|---|---|
| **서울 동네**(명동·홍대 등) | 볼거리 큐레이션 + 동선 + 근교 당일치기 | 서울=큐레이션 지문, 끼워넣기 소비 |
| **부산** | **이동(서울↔부산 KTX) 카드** + 볼거리 | 부산=접근성 1순위 |
| **제주** | **렌터카·거점 숙소** + 체험 | 제주=차량 전제 |

**개발자**: 이건 §3-1(이동 카드)·§3-2(intent 탭)이 만들어지면 **그 위에 "지역 타입별 노출 프로파일"을 얹는** 형태라 궁합이 좋습니다. 다만 지역 타입을 뭐로 판정하느냐(city_slug? 신규 region_type 컬럼?)는 정해야 해요. 일단 city_slug로 분기하면 코드만으로 시작 가능합니다.

**PO**: 좋습니다. 도시별 차별화는 **별도 기능이 아니라 축 ①②의 '배치 규칙'**으로 흡수합니다.

## 4. 우선순위 종합 (개발자 공수 감 포함)

**PO**: 오늘 나온 후보를 ICE 감각으로 정리합니다. (Impact=데이터 부합도, Confidence=근거 명확성, Effort=개발자 추정)

| 후보 | Impact | Conf. | Effort | 분류 | 판단 |
|------|:---:|:---:|:---:|------|------|
| **A. intent 탭 재편** (볼거리/먹거리/투어/교통/숙소) | 高 | 高 | 中 | 단기(A) | **1순위 후보** |
| **B. 지역 간 이동 요약 카드 (Lite)** | 高 | 高 | 小 | 단기(A) | **1순위 후보** (가장 싼 검증) |
| **C. 도시 타입별 섹션 프로파일** | 中 | 中 | 小 | 단기(A) | A·B 위에 얹는 2순위 |
| **D. vibe(목적) 태그 체계** | 高 | 中 | 大 | 중기(B) | 콘텐츠 로드맵과 묶기 |
| **E. 다도시 배분 ↔ 검증 파일럿 연결** | 高 | 中 | 中 | 중기(B) | 플래너 트랙과 합치기 |
| **F. 부산·제주 region 콘텐츠 확충** | 高 | 高 | 大(콘텐츠) | 중기(B) | 선행 의존성(콘텐츠팀) |

**Growth Manager**: 챌린지 하나. **B(이동 카드)와 A(intent 탭) 중 뭐 먼저냐.** 저는 **B 먼저**를 주장합니다. Effort가 작고, "지역 간 이동 수요가 실재하는가"라는 §1의 핵심 가설(부산=교통 1순위)을 **가장 빨리·싸게 검증**하니까요. 클릭 데이터가 나오면 A·C 투자 방향이 선명해집니다.

**PM**: 동의하지만 A는 "페이지 정보구조 자체"를 바꾸는 거라 리드타임이 길어요. **B를 먼저 띄워 검증하면서 A 설계를 병행**하는 게 맞습니다.

**개발자**: 리소스 관점도 같습니다. B는 FE만으로 1~2일, A는 섹션 컴포넌트 재배치 + intent 매핑이라 설계 포함 1~2주예요. B를 스파이크로 먼저 내보내고 A를 정식 트랙으로.

**PO**: 확정. **B(이동 카드) 선행 스파이크 → A(intent 탭) 정식 트랙 병행**, C는 A에 흡수, D·E·F는 중기.

## 5. 합의

### 합의 1: 문제 정의
> 지역 페이지의 핵심 문제는 "섹션이 부족"한 게 아니라, **데이터가 말하는 유저 의도(볼거리·교통·투어 / 다도시 / 지역간 이동)와 페이지의 분류 축(신선도·인기)이 어긋나 있다**는 것. 같은 스팟 풀을 신선도 렌즈로 반복 노출하는 구조를 **유저 의도(intent) 축으로 재편**하는 게 1차 방향.

### 합의 2: 단기/중기 분리
> - **단기(A, 기존 서울 동네 페이지 재구성)**: 이동 카드(B) + intent 탭(A) + 도시 타입 프로파일(C).
> - **중기(B, 모델·콘텐츠 필요)**: vibe 태그(D), 다도시 배분×검증 파일럿(E), 부산·제주 콘텐츠 확충(F).

### 합의 3: 실행 순서
> **이동 요약 카드(Lite)를 선행 스파이크로 먼저 출시**(가장 싼 가설 검증) → 그 클릭 데이터를 보며 **intent 탭 재편**을 정식 트랙으로 병행. 도시별 차별화는 두 작업의 '배치 규칙'으로 흡수.

### 합의 4: theme 축의 정의 방향
> 신규 'theme'은 **유저 의도(intent) 버킷(볼거리/먹거리/투어·체험/교통·이동/숙소)**으로 1차 정의. 기존 category를 intent로 재그룹핑하는 A안으로 시작하고, 무드/목적 태그(vibe, B안)는 콘텐츠 로드맵과 묶어 중기.

### 합의 5: 데이터 의존성 인지
> 다도시·지역간이동 수요를 '제대로' 풀려면 **부산·제주 region 콘텐츠 공백(514개 중 498개 서울)**이 선행 병목임을 인지. 단기 트랙은 이 병목을 우회하는 범위(서울 동네 재구성 + 정적 이동 정보)에서만 진행.

## 추가 논의 (2026-06-19) — 지역 페이지 퍼포먼스 데이터 충격

### 배경

> 미팅 직후 PO가 지역 페이지의 실제 퍼포먼스 데이터를 공유. 이 숫자가 앞선 논의의 **전제(투자 가치)** 자체를 흔들어, 추가 논의를 진행한다.

| 지표 | 지역 페이지(`/spot/region/`) | 스팟 리스트 페이지 | 비율 |
|------|:---:|:---:|:---:|
| 활성 사용자 | — | — | **약 3.8%** (리스트 대비) |
| 평균 참여시간 | **11초** | 49초 | **약 22%** |
| 페이지 내 → 스팟 이동률 | **~5%** | — | "나쁘지 않음" |

**PO**: 솔직하게 깔고 가야 합니다. **활성 사용자가 리스트 페이지의 3.8%, 참여시간은 22%(11초)**예요. 11초면 사실상 **랜딩하자마자 이탈**입니다. 그런데 들어온 사람의 스팟 이동률은 5%로 나쁘지 않고요. 이 세 숫자를 어떻게 읽느냐가 오늘 추가 논의의 전부입니다.

### 1. 세 숫자의 재해석 — 무엇이 깨졌나

**Growth Manager**: 숫자를 분해하면 **서로 다른 세 개의 고장**입니다. 섞으면 안 됩니다.

| 숫자 | 진단 | 깨진 단계 |
|------|------|----------|
| 트래픽 3.8% | **아무도 안 온다** | 유입(Acquisition) |
| 참여 11초 | **온 사람도 즉시 떠난다** | 활성화(Activation) |
| 스팟 이동 5% | **남은 소수는 전환된다** | 전환(Conversion) — 유일하게 멀쩡 |

**Growth Manager**: 즉 페이지의 **콘텐츠 가치가 0인 게 아닙니다.** 끝까지 본 5%는 스팟으로 넘어가요. 문제는 **(a) 그 페이지까지 오는 사람이 거의 없고, (b) 온 사람의 대부분이 11초 안에 "내 질문에 대한 답이 없네" 하고 튕긴다**는 두 가지예요.

**개발자**: (b)는 우리가 §2-2에서 코드로 본 그대로입니다. 유저가 부산을 누르고 들어오면 **"추천 스팟 / 최신 스팟 / 인기 스팟"** — 같은 스팟 풀을 정렬만 바꿔 16번 보여줍니다. "서울에서 부산 어떻게 가나(부산 1순위 니즈)"에 대한 답이 **첫 화면에 없어요.** 11초 이탈은 데이터가 아니라 **구조의 결과**입니다.

### 2. 가장 강력한 프레이밍 — 55% vs 3.8%

**Marketer**: 저는 이 두 숫자를 나란히 놓는 게 오늘 미팅 전체의 핵심이라고 봅니다.

> **외부 여행 담론의 55.5%가 '지역'인데, 우리 지역 페이지는 전체 트래픽의 3.8%만 받는다.**

수요가 없는 게 아니에요. **수요는 거대한데(55%) 우리 페이지가 그걸 못 받고 있는(3.8%) 것.** 이 격차 자체가 진단이자 기회 크기예요. "활성 사용자가 적으니 버리자"가 아니라 "**왜 가장 큰 수요 주제가 가장 안 쓰이는 페이지가 됐나**"를 물어야 합니다.

### 3. 근본 질문 (Growth 챌린지) — 이 페이지를 고치는 게 맞나

**Growth Manager**: 그래도 냉정한 챌린지를 하나 해야 합니다. **3.8% 베이스에서는 페이지를 아무리 잘 고쳐도 절대 임팩트의 천장이 낮습니다.** 참여시간을 11초→30초로 3배 올려도, 모수가 작으면 전사 지표엔 안 잡혀요. "고칠 가치가 있나"를 진지하게 따져야 합니다.

**PO**: 정당한 지적입니다. 그래서 **"페이지를 고친다"와 "트래픽을 페이지로 보낸다"를 분리**해야 해요. 활성화(11초)만 고치면 — 좋아진 페이지를 여전히 아무도 안 봅니다. 유입(3.8%)만 늘리면 — 11초 이탈 페이지에 사람을 더 부어 이탈만 늘려요. **둘은 반드시 같이 가야** 의미가 있습니다.

**PM**: 그리고 유입이 왜 적은지를 코드로 확인했는데, 원인이 명확합니다.

### 4. 유입(Acquisition) 진단 — 지역 페이지는 '내비게이션'이 아니다

**개발자**: 지역 페이지로 보내는 링크를 전부 훑었습니다. 진입 경로가 이렇습니다:

| 진입 경로 | 성격 |
|---|---|
| 지도 마커(RegionMap '다른 지역' 버튼 / SpotListMap·SpotMainMap 지역 플래그) | **부수적** — 지도를 만져야만 보임 |
| 검색 자동완성 / 검색결과 지역 섹션 | 검색어를 쳐야 노출 |
| tips/region-guide, 지하철 가이드, place 상세 | 깊은 하위 페이지 |
| recommend-seoul-region 퀴즈 결과 | 퀴즈를 끝까지 해야 도달 |
| 브레드크럼/구조화 데이터 | SEO용(유저 클릭 경로 아님) |

**개발자**: 핵심은 — **메인 내비게이션이나 스팟 리스트 상단에 "지역으로 둘러보기" 같은 1차 진입점이 없습니다.** 지역 페이지는 **지도를 만지다 우연히, 또는 검색하다 걸려서** 가는 곳이에요. 3.8%는 당연한 결과입니다.

**Growth Manager**: 그럼 유입 레버는 분명하네요. **이미 트래픽이 있는 곳(스팟 리스트 49초, 스팟 홈)에서 지역 페이지로 가는 1차 동선을 만드는 것.** 다만 이건 "11초 페이지로 사람 보내기"라 **활성화 개선이 선행/병행돼야** 한다는 PO 말이 맞습니다.

### 5. 전략적 분기 — 별도 페이지 vs 리스트 페이지로 흡수

**PM**: 여기서 더 근본적인 선택지를 테이블에 올려야 합니다. **지역 '의도'를 꼭 별도 페이지로 풀어야 하나?**

- 유저는 이미 **스팟 리스트 페이지(49초, 높은 참여)**에 있습니다.
- 우리가 만들려는 intent 탭(볼거리/먹거리/투어/교통)·이동 카드는 **리스트 페이지 안에서도 성립**합니다.
- 11초짜리 별도 페이지로 유저를 빼내는 대신, **리스트 페이지에 지역 의도 레이어를 주입**하면 — 이미 머무는 곳에서 가치를 주는 거예요.

| 안 | 내용 | 장점 | 단점 |
|---|---|---|---|
| **안 1: 지역 페이지 개선** | `/spot/region/` 자체를 intent·이동 중심으로 재편 | SEO 자산·지역 단위 URL 유지 | 11초·3.8% 베이스, 유입까지 따로 풀어야 |
| **안 2: 리스트 페이지 흡수** | 지역 의도 기능을 스팟 리스트에 주입 | 49초 트래픽 위에 바로 얹음 | 지역 단위 SEO·전용 콘텐츠 약화 |
| **안 3: 병행** | 리스트에 '지역 의도' 진입 위젯 → 개선된 지역 페이지로 | 유입+활성화 동시 공략 | 범위 큼, 단계 필요 |

**Marketer**: SEO 관점에서 지역 페이지를 완전히 버리는 안 2는 위험합니다. `region-domain-map`에서 봤듯 region은 **잠재 SEO 자산**(다국어 514개)이에요. 외부(구글·Reddit) 유입의 랜딩으로서 지역 페이지는 가치가 있습니다 — 다만 **지금은 그 랜딩이 11초 이탈**이라는 거죠.

**PO**: 그래서 **안 3(병행)**이 답이라고 봅니다. 정리하면:
- **활성화**: 개선된 지역 페이지(intent 탭 + 이동 카드)로 11초 이탈을 잡는다 → 이게 앞선 미팅의 합의 그대로.
- **유입**: 스팟 리스트(49초)에 "지역으로 둘러보기" 1차 진입 위젯을 만들어 지역 페이지로 동선을 연결한다 → **신규**.
- **검증 순서**: 활성화 개선을 먼저 띄워 11초가 의미있게 오르는지 본 **뒤에** 유입 동선을 연다. 안 그러면 깨진 페이지에 트래픽만 붓는다.

### 6. 기존 합의에 미치는 영향

**Growth Manager**: 새 데이터가 앞선 합의를 뒤집진 않습니다. 오히려 **합의 1(분류 축이 어긋남)을 11초 이탈이 정량 증명**해요. intent 재편의 정당성이 더 세졌습니다. 다만 다음을 보완해야 합니다.

1. **합의 2/3에 '유입 트랙' 추가.** 기존엔 단기(A)=서울 동네 재구성만 있었는데, **유입(리스트→지역 동선)을 별도 트랙으로** 명시. 활성화 개선 검증 후 개방.
2. **성공 지표 재정의.** 기존엔 "이동 카드 클릭률" 중심이었는데, **참여시간 11초 → 목표치, 페이지 이탈률**을 1차 성공 지표로 승격. 스팟 이동률 5%는 baseline으로 고정해 "개선이 전환을 해치지 않는지" 가드레일로 사용.
3. **임팩트 천장 인지(Growth 챌린지 수용).** 3.8% 베이스에서 활성화만으론 전사 임팩트가 작음을 인정하고, **유입 트랙이 붙어야 비로소 의미있는 규모**가 됨을 합의 5에 추가.

**PM**: 한 가지 더. 11초 이탈을 잡는 가장 빠른 지렛대는 **"첫 화면(above the fold)에 유저 의도 답을 놓는 것"**입니다. 지금은 첫 화면이 제목·평점·설명·주소예요. 여기에 **intent 탭(또는 이동 카드)을 첫 화면으로 끌어올리는 것**만으로도 11초가 움직일 수 있습니다. 이건 §3-1·§3-2의 부분집합이라 추가 공수도 작습니다.

### 7. 수정/추가되는 결론

**합의 6 (신규): 문제는 '활성화'와 '유입'의 동시 고장이다**
> 지역 페이지는 (a) 트래픽 3.8%(유입), (b) 참여 11초(활성화) 두 가지가 동시에 깨져 있고, (c) 스팟 이동 5%(전환)는 멀쩡하다. 외부 담론의 55%가 지역인데 페이지는 3.8%만 받는 격차가 기회 크기. **활성화(intent·이동 재편으로 11초 이탈 차단)를 먼저 검증한 뒤, 유입(리스트 49초 트래픽에서 지역으로 동선 연결)을 연다.** 깨진 페이지에 트래픽을 먼저 붓지 않는다.

**합의 7 (신규): 별도 페이지 vs 리스트 흡수 → 병행(안 3)**
> 지역 페이지는 SEO 랜딩 자산으로 유지·개선하되(활성화), 유입은 스팟 리스트에 '지역 의도' 진입 위젯을 심어 연결한다. 지역 단위 SEO를 버리지 않으면서 49초 트래픽을 활용한다.

**합의 3 수정: 첫 화면 우선 배치**
> intent 탭·이동 카드를 단순 추가가 아니라 **above-the-fold로 끌어올려** 11초 이탈을 직접 공략한다.

## 추가 논의 #2 (2026-06-19) — 개선 최종 형태: 3단 페이지 위계 검토

### 배경

> PO가 구상한 **개선 최종 형태**를 공유. 앞선 논의(intent 탭·이동 카드·유입/활성화)를 하나의 **3단 페이지 위계(IA)**로 종합한 구조다. 개발자·PM·Growth가 현재 엔티티/라우팅에 매핑하며 실현 가능성과 선행조건을 검증한다.

### 0. 제시된 타겟 구조

```
① 지역 메인          /region
   - 한국 내 '도시' 노출 (서울·부산·제주·경주 등 큰 범위)
   - 도시 ↔ 도시 이동수단 및 소요시간

② 도시 상세          /region/{city}        e.g. /region/seoul
   - 구역(area) 단위 필터 → 클릭 시 해당 구역에 연결된 스팟만 큐레이션 노출
     ('구역' = 광화문·홍대처럼 행정구역은 아니나 여행객이 인지하는 지역의 집합)
   - Reddit 데이터 기반 상품 큐레이션 (썸네일 n개 + '더보기' → ③)
   - 해당 도시 → 타 지역 이동수단·소요시간

③ 도시·테마 상세     /region/{city}/{category}   e.g. /region/seoul/tickets
   - 구역 단위 필터 (②와 동일)
```

### 1. 현재 구조 대비 — 무엇이 근본적으로 뒤집히나

**개발자**: 먼저 가장 큰 변화를 짚습니다. **위계의 주어가 바뀝니다.**

| 항목 | 현재(`/spot/region/`) | 제안(`/region/`) |
|------|---|---|
| 1급 엔티티 | **동네**(명동=regionId `4`, 홍대=`5`) | **도시**(`/region/seoul`) |
| 도시의 지위 | region의 속성(`citySlug`) | URL 1급 경로 |
| 동네/구역의 지위 | 독립 페이지(numeric id) | **도시 페이지 안의 필터로 강등** |
| URL | `/spot/region/4` (숫자 id) | `/region/seoul/tickets` (slug) |
| 테마(category) 축 | **없음** | **URL 1급(/{category})으로 승격** |
| 도시 인덱스 | **없음**(퀴즈만 존재) | `/region` 신설 |

**개발자**: 코드로 확인한 호재 하나 — region 엔티티에 **`slug`·`citySlug`가 이미 있고** `regionsForRegionPage` 쿼리가 이미 전체 지역을 slug와 함께 내려줍니다. 그래서 **slug 기반 라우팅(`/region/seoul`)은 새 데이터 없이 가능**합니다. 문제는 라우팅이 아니라 **그 페이지에 채울 엔티티가 정합한가**예요.

### 2. 엔티티 매핑 — 각 요소가 어디에 붙나 (domain-map 교차)

**PM**: 제안의 각 요소를 `region-domain-map.md`의 4개 층위에 매핑했습니다.

| 제안 요소 | 매핑되는 기존 엔티티 | 현재 상태 | 갭 |
|---|---|---|---|
| ① 도시 리스트 | `category`(type=CITY) 169개 | 존재하나 잡값 섞임(평양·타이페이) | 노출용 도시 화이트리스트 필요 |
| ① 도시간 이동 | **없음** | 미존재 | 도시쌍 이동 데이터(정적 테이블) 신설 |
| ② `/region/{city}` | `region.citySlug` | 서울만 충실(498개), 부산·제주 각 1개 | **부산·제주·경주 도시 콘텐츠 공백** |
| ② '구역' 필터 | `category`(type=DETAIL_LOCATION) 158개 + `region_has_detail_location` | 데이터 존재하나 부채 큼 | **66% parent 고아 + 관광지/행정구 혼재** |
| ② Reddit 기반 큐레이션 | `region_spot_area`(큐레이션 묶음) | DB상 6개뿐(실험적) | 큐레이션 로직·콘텐츠 대폭 신설 |
| ③ `/{category}` 테마 | `category`(상품 카테고리, 예 tickets/tours) | 상품엔 category 있음, **지역×테마 결합 페이지는 없음** | 지역×테마 교차 엔티티/쿼리 |

**PM**: 즉 **라우팅·껍데기는 기존 자산으로 되지만, 내용물 3개(도시 콘텐츠 / 구역 정합성 / 지역×테마 큐레이션)가 전부 선행 정리·신설 대상**입니다.

### 3. 핵심 쟁점

#### 쟁점 A — '구역' 필터의 데이터 부채 (가장 큰 선행조건)

**개발자**: 유저가 정의한 구역("광화문·홍대처럼 행정구역 아닌 여행객 인지 지역")은 정확히 **DETAIL_LOCATION 카테고리**입니다. 그런데 domain-map §6·§7에서 본 그대로 이게 가장 약한 고리예요:

- **158개 중 105개(66%)가 parent(도시) 없는 고아** → 어느 도시 필터에도 안 붙음.
- **관광지명(명동·홍대)과 행정구(강남구·종로구)가 한 바구니에 혼재** → 유저가 원하는 "여행객 인지 구역"만 깔끔히 못 거름.
- **이름 중복**(서면×3, 성수동×2).

**개발자**: 그래서 "구역 필터"는 **DETAIL_LOCATION의 parent 보정 + 관광지/행정구 분리 + 중복 제거가 선행**돼야 작동합니다. 이건 domain-map §7-5의 운영 개선(어드민에 상위도시 선택 추가 → 고아 양산 차단 → 105개 일괄 보정)과 **같은 작업**이에요. 기획 트랙이 아니라 **데이터 정합성 트랙**이 먼저 움직여야 합니다.

**PO**: 중요한 발견입니다. 구역 필터는 멋진데, **그 밑단 데이터가 안 정리되면 빈 필터·엉뚱한 필터가 나옵니다.** 쟁점 A를 **최우선 선행 과제**로 못 박습니다.

#### 쟁점 B — 도시 페이지의 데이터 소스 (부산·제주·경주 공백)

**PM**: ②`/region/seoul`은 region(서울 498개)으로 채워지지만, **`/region/busan`·`/region/jeju`·`/region/gyeongju`는 채울 region 콘텐츠가 거의 없습니다**(부산·제주 각 1개, 경주는 신규 작업 흔적만 — outputs/region-gyeongju).

**Growth Manager**: 그런데 §1 Reddit 데이터의 다도시 수요(27%)·도시 지문(부산=교통, 제주=렌터카)은 **바로 이 부산·제주를 가리킵니다.** 가장 수요 있는 도시 페이지가 콘텐츠가 비어있는 모순.

**개발자**: 선택지는 둘입니다.
- **B-1**: 도시 페이지를 region(콘텐츠) 기반으로 → 부산·제주 region 콘텐츠를 콘텐츠팀이 채워야(대). 
- **B-2**: 도시 페이지를 **category(CITY)+스팟 집계** 기반으로 → 콘텐츠 작성 없이 스팟·이동·테마만으로 페이지 성립(소~중). 단 "도시 소개 글" 같은 에디토리얼은 약해짐.

**PO**: **B-2로 시작**합시다. 부산·제주 페이지를 "스팟 큐레이션 + 이동 + 테마"로 먼저 세우면 콘텐츠 공백을 우회해 다도시 수요를 즉시 받습니다. 에디토리얼(region 콘텐츠)은 서울처럼 나중에 덧붙이고.

#### 쟁점 C — 테마(/{category}) 정의

**PM**: ③`/region/seoul/tickets`의 'tickets'는 앞 미팅 §3-2의 **intent/theme 축이 독립 URL로 승격**된 형태입니다. 단 'tickets'는 의도(볼거리)보다 **상품 카테고리**에 가까워요. 그래서 테마 축을 둘로 합쳐야 합니다.

| 테마 후보 | 예 | 출처 |
|---|---|---|
| 상품 카테고리형 | tickets / tours / activities / food | 기존 category |
| 의도형(Reddit) | 볼거리·교통·체험·쇼핑 | §3-2 intent 버킷 |

**개발자**: URL slug는 안정적인 **상품 카테고리 기반**(tickets/tours…)으로 가는 게 SEO·구현상 깔끔합니다. 의도형은 그 안의 큐레이션 정렬/묶음으로 흡수. 즉 **URL=카테고리, 큐레이션 로직=Reddit 의도**.

#### 쟁점 D — 기존 498개 동네 URL의 운명 (SEO)

**Marketer**: 현재 `/spot/region/4`(명동) 같은 동네 페이지가 498개 있고 일부는 검색 유입 자산입니다. 도시 1급으로 가면 이 URL들이 **`/region/seoul?area=명동`(필터 상태)으로 흡수**되는데, **301 리다이렉트 + canonical 전략**이 없으면 기존 SEO가 증발합니다.

**개발자**: 맞습니다. 동네 → 도시+필터 매핑 테이블 만들고 301 처리해야 해요. slug가 이미 있어서 매핑 자체는 가능합니다. **이건 IA 전환의 필수 동반 작업**으로 묶습니다.

#### 쟁점 E — Reddit 기반 큐레이션의 정체

**Growth Manager**: "Reddit 데이터 기반 상품 큐레이션"을 구체화해야 합니다. 두 해석:
- **E-1(콘텐츠)**: §1 도시 지문대로 큐레이션을 **사람이 편성**(서울=볼거리 우선, 부산=교통 우선, 제주=렌터카·체험 우선). region_spot_area(현 6개) 확장.
- **E-2(자동)**: Reddit 빈출 지명·테마를 신호로 스팟 랭킹 가중.

**PO**: 파일럿은 **E-1(수동 편성)**로 시작. §1이 이미 도시별 우선순위를 줬으니, 그걸 큐레이션 묶음으로 사람이 만들면 됩니다. 자동화(E-2)는 효과 확인 후.

### 4. 성능 데이터와의 정합성 — 이 구조가 3.8%/11초를 푸는가

**Growth Manager**: 핵심 점검. 이 3단 구조가 추가논의 #1의 두 고장을 푸느냐.

| 고장 | 3단 구조의 해법 | 평가 |
|---|---|---|
| 유입 3.8% | `/region` 메인 인덱스 신설 → 메인 내비/리스트에서 1차 진입점 | ✅ 유입 동선의 그릇이 생김 |
| 활성화 11초 | 도시 페이지 첫 화면 = 도시 지문 큐레이션 + 이동 정보(유저 질문에 즉답) | ✅ 이탈 직격 (단, 첫 화면 배치 전제) |
| 전환 5% | 구역 필터·테마 더보기로 스팟 진입 동선 다양화 | ↑ 잠재 상승 |

**Growth Manager**: 구조적으로는 **두 고장을 다 겨냥**합니다. 다만 천장은 여전히 유입에 달렸어요 — `/region` 그릇을 만들어도 **메인 내비/리스트에서 거기로 보내는 1차 링크**가 없으면 3.8%는 안 움직입니다. 추가논의 #1의 '리스트→지역 진입 위젯'이 이 구조에선 **`/region` 메인으로 보내는 동선**으로 구체화됩니다.

### 5. 단계적 실행 (한 번에 다 못 만든다)

**개발자**: 3단 + 데이터 정합성 + SEO를 한 번에 치면 분기 단위 프로젝트입니다. 의존성 순으로 쪼갭니다.

| Phase | 범위 | 선행 의존성 | 비고 |
|---|---|---|---|
| **P0 (선행)** | DETAIL_LOCATION 정합성 정리(parent 보정·관광지/행정구 분리·중복) + 어드민 상위도시 입력 | — | 쟁점 A. 기획 아닌 데이터 트랙 |
| **P1** | `/region` 메인(도시 리스트 + 도시간 이동 정적 테이블) | 도시 화이트리스트 | 유입 그릇 + 다도시 이동(B 카드 승격) |
| **P2** | `/region/{city}` 도시 상세 — **서울 먼저**(구역 필터 + Reddit 수동 큐레이션 + 타지역 이동) | P0(구역), P1 | 활성화 직격 |
| **P2.5** | 부산·제주 도시 상세 (category 기반 B-2) | P2 패턴 | 다도시 수요 직접 흡수 |
| **P3** | `/region/{city}/{category}` 테마 상세 + 498 동네 URL 301 | P2, 쟁점 C·D | SEO 전환 동반 |
| 유입 | 리스트/메인 → `/region` 1차 진입 위젯 | P1 출시 후 | P2 활성화 검증 후 개방 |

**PM**: P2(서울 도시 상세)가 **이 구조의 가치를 처음 증명하는 지점**입니다. 여기서 11초가 의미있게 오르면 P2.5·P3 투자가 정당화됩니다.

### 6. 합의 업데이트

**합의 8 (신규): 개선 최종 형태 = 3단 위계 채택, 단 단계적**
> `/region`(도시+이동) → `/region/{city}`(구역 필터 + Reddit 큐레이션 + 이동) → `/region/{city}/{category}`(테마)의 3단 IA를 타겟으로 채택. 라우팅·slug는 기존 자산(region.slug/citySlug)으로 가능하나, **내용물 3종(도시 콘텐츠·구역 정합성·지역×테마 큐레이션)은 선행 정리·신설 대상**.

**합의 9 (신규): 데이터 정합성(DETAIL_LOCATION)이 P0 선행**
> '구역 필터'의 전제인 DETAIL_LOCATION의 parent 고아(66%)·관광지/행정구 혼재·중복을 먼저 정리한다(domain-map §7-5와 동일 작업). 이게 안 되면 빈/엉뚱한 필터가 난다.

**합의 10 (신규): 도시 페이지는 category(CITY) 기반(B-2)으로 시작**
> 부산·제주·경주 region 콘텐츠 공백을 우회하기 위해, 도시 상세를 "스팟 큐레이션+이동+테마"(category 기반)로 먼저 세운다. 에디토리얼(region 콘텐츠)은 서울처럼 후행 보강.

**합의 11 (신규): 테마 URL=상품 카테고리, 큐레이션 로직=Reddit 의도**
> `/{category}` slug는 안정적인 상품 카테고리(tickets/tours…) 기반, 그 안의 묶음·정렬은 §1 도시 지문(Reddit 의도)으로 편성(수동 시작).

**합의 7 갱신**: 추가논의 #1의 "리스트→지역 진입 위젯"은 이 구조에서 **`/region` 메인으로 보내는 1차 동선**으로 구체화. P1 출시 + P2 활성화 검증 후 개방.
