## ① 정수연 → 트래볼루션 (1차 문의: 토큰 재발급 · Rate Limit · 부분취소)

안녕하세요, 처음 인사드립니다.
크리에이트립 PM 정수연입니다.

Bank of Trip 파트너 API 연동을 진행하기 위해 개발환경(dev.bankoftrip.com)에서 검토 중입니다. 이 과정 중에 확인이 필요한 점이 있어 연락드립니다.

**1. 개발환경 API 토큰 재발급 요청**
현재 개발환경 어카운트(partner@creatrip.com)로 발급받은 액세스 토큰이 API 호출 시 INVALID_TOKEN으로 반려되어 정상 호출이 되지 않습니다.
(문서상 Authorization: Bearer {token} 포맷은 확인했으며 그대로 적용했습니다.)
요청: 개발환경 API 토큰 재발급 부탁드립니다.
재발급 후 유효 기간·갱신 방식(만료 시 재발급 절차)도 함께 안내해주시면 감사하겠습니다.

**2. Rate Limit 정책 확인**
응답 헤더에 x-ratelimit-limit: 600 / x-ratelimit-remaining 값이 포함되어 있는 것을 확인했습니다. 호출량·재시도 설계를 위해 아래를 확인 부탁드립니다.
- x-ratelimit-reset 헤더도 함께 제공되나요? (제공된다면 창(window) 단위는 저희가 실측으로 확인하겠습니다.)
- 저희 실측상 상한 600은 분(per-minute) 단위로 추정되는데, 맞는지 확인 부탁드립니다.
- 초과 시 동작: 한도 초과 시 429를 반환하나요? 반환 시 Retry-After 등 재시도 대기 정보가 함께 오나요?
- 운영·개발 환경의 한도가 동일한지도 알려주시면 감사하겠습니다.

**3. 부분취소 / 부분환불 처리 방안**
크리에이트립은 운영상 주문의 일부만 취소·환불해야 하는 케이스가 발생합니다. (예: 다인 예약 중 일부 인원만 취소)
다만 파트너 API의 주문 취소(DELETE /orders/{orderNumber})는 주문 전체 단위 취소만 지원하고, unit, 수량 지정 파라미터가 없어 파트너 측에서 부분취소를 실행할 방법이 없는 것으로 확인됩니다. 이에 아래를 확인 부탁드립니다.

- 크리에이트립이 부분취소를 요청하면 트래볼루션 측에서 처리해주실 수 있을까요?
- 처리 가능하다면 요청 채널(콘솔 / 메일 / 별도 API)과 처리 리드타임은 어떻게 되나요?
- 처리 결과가 저희에게 PARTIAL_CANCELED 웹훅으로 통지되나요?
- 향후 파트너발 부분취소를 API로 지원하실 계획이 있으신가요? (unit·수량 지정 취소)
- 1과 2 모두 불가하다면, 전체취소 후 잔여 인원 재주문 외에 권장하시는 운영 방법이 있을까요?
  이 경우 재주문 시점의 재고·가격·좌석(스케줄) 보장 이슈가 우려됩니다.

번거로우시겠지만 위 3가지 항목에 대해 확인 부탁드립니다. 회신 주시면 연동 설계에 반영하여 진행하겠습니다.

**1. API 인증 방식 및 키 재발급**

API 인증 방식
당사 API 문서 기준으로 API 호출 시에는 별도의 Bearer 접두어 없이 인증 키를 전달해 주시면 됩니다.

다만, 당사에서 웹훅을 발송할 때는 인증 정보에 접두어를 포함하고 있어 이로 인해 혼선이 발생한 것으로 보입니다. 해당 부분은 내부 검토를 거쳐 향후 양쪽 인증 방식이 호환될 수 있도록 개선 가능한지 확인하겠습니다. 이용에 혼선을 드린 점 양해 부탁드립니다.

인증 키 재발급
인증 키는 아래와 같이 재발급해 드렸습니다.

`a26f3097-daae-4667-a968-c3a38cefdb5b`

해당 키에는 별도의 유효기간이 없습니다. 추후 재발급이 필요한 경우 언제든지 요청해 주시면 됩니다.

**2. API 호출 한도 및 제한 초과 시 동작**

호출 한도 및 적용 단위
현재 설정된 호출 한도는 분당 최대 600회입니다.
- 최대 호출 수: 600회
- 적용 단위: 1분
- 기준: 600 requests / 1 minute

다만, 해당 수치는 고정적으로 보장되는 정책은 아니며 서버 운영 상황에 따라 조정될 수 있는 점 참고 부탁드립니다.

Rate Limit 응답 헤더
정상적으로 호출 한도 내에서 요청이 처리되는 경우 아래 헤더가 제공됩니다.
- X-RateLimit-Limit
- X-RateLimit-Remaining

호출 한도를 초과할 경우에는 별도의 LIMIT 관련 헤더없이 HTTP 429 Too Many Requests 응답이 다음과 같은 Body와 함께 응답되게 됩니다.

```json
{
    "code": "INTERNAL_ERROR",
    "message": "Too Many Attempts."
}
```

환경별 호출 한도
현재 운영 환경과 개발 환경 모두 분당 600회로 동일하게 설정되어 있습니다.
다만, 해당 한도 역시 서버 상황 및 운영 정책에 따라 변경될 수 있습니다.

**3. 주문 취소 API 및 부분취소 처리**

취소 API 사용 범위
당사의 주문 취소 API는 주문 전체를 취소하는 경우에만 호출해 주시는 것이 맞습니다.
수량 일부 또는 주문 일부만을 취소하는 별도의 부분취소 API는 현재 지원하고 있지 않으며, 별도의 개발 계획도 없는 상태입니다.
따라서 부분취소가 필요한 경우에는 기본적으로 현재 운영 중인 방식과 동일하게 양사의 오퍼레이션 팀 간 커뮤니케이션을 통해 요청 사항을 확인하고 처리하게 됩니다.

부분취소 상태로 처리되는 경우
취소 API는 전체 취소 요청에 한하여 제공되지만, 최종 주문 상태는 아래와 같은 경우 전체취소가 아닌 부분취소(PC, PARTIAL_CANCELED) 상태로 처리될 수 있습니다.
- 당사의 취소 및 환불 규정에 따라 일부 금액만 환불되는 경우
- 양사의 오퍼레이션 팀 간 협의를 통해 부분취소 처리가 결정된 경우

수량 취소 등 API에서 지원하지 않는 요청의 처리 절차
수량 일부 취소와 같이 API에서 지원하지 않는 요청은 기존 운영 절차에 따라 처리됩니다. 부분취소가 필요한 경우 귀사의 오퍼레이션 팀에서 당사 오퍼레이션 팀으로 요청해 주시면, 주문 상태와 가격 및 재고 상황 등을 확인한 후 아래 기준으로 안내 및 처리하고 있습니다.

- 가격 또는 재고 등에 문제가 없는 경우
  기존 주문을 전체 취소한 후 재주문하는 방식으로 안내드립니다.
- 가격 또는 재고 변동 등으로 재주문이 어려운 경우
  취소 후 재주문 방식은 안내드리지 않습니다. 고객과 협의한 뒤, 당일 최종 사용이 완료된 이후 주문을 부분취소 상태로 변경하여 처리해 드립니다.

부분취소에 대한 구체적인 처리 방법과 시점은 주문별 상황에 따라 달라질 수 있으므로, 관련 요청은 기존과 동일하게 양사의 오퍼레이션 팀 간 커뮤니케이션을 통해 협의해 주시기 바랍니다.

추가 문의사항 있으시면 언제든 편하게 연락주십시오.

## ⑤ 정수연 → 트래볼루션 (3차 문의: 바우처 사용완료 상태 통지)

안녕하세요,
크리에이트립 정수연입니다.
Bank of Trip 파트너의 상품의 운영 프로세스를 함께 검토하며 바우처 사용완료 상태 관련해서 질문이 있어 문의드립니다.

고객이 발급된 바우처를 현장에서 사용하면, 트래볼루션 운영 콘솔에서 해당 주문이 '사용완료'로 표시되는 것을 확인했습니다.
저희 내부적으로 사용완료 상태는 정산 처리에 필요한 값이라, 이를 자동으로 수신·반영할 수 있는지 확인이 필요합니다.

다만 현재 API 문서(v1.1.4)의 웹훅 eventType에는 CANCELED / PARTIAL_CANCELED / BOOKING_ACCEPTED / BOOKING_REJECTED 4종만 안내되어 있어, 사용완료 관련 통지가 어떤 방식으로 이루어지는지 확인하고자 합니다.

- 바우처 사용완료 시점에 등록된 웹훅 URL로 이벤트가 발송되나요? 발송된다면 정확한 eventType 값과 발송 시점을 알려주시면 감사하겠습니다.
- 웹훅으로 발송되지 않는다면, GET /orders/{orderNumber} 주문 조회 응답에서 사용완료 여부를 확인할 수 있는지(어떤 status 값으로 반영되는지) 함께 안내해주시면 감사하겠습니다.

운영 콘솔상으로는 사용완료가 확인되나, 등록된 웹훅 URL 또는 주문 조회 API로 해당 상태를 자동으로 받아올 수 있는지가 저희 정산·연동 설계의 기준이 되어 확인을 요청드립니다.

## ⑥ 트래볼루션 → 정수연 (3차 회신: REDEEMED / RESTORED 웹훅 · status AP) — 이미지 첨부

안녕하세요. 트래볼루션 전원식입니다.

웹훅은 사용 처리 시 REDEEMED 상태로 발송되며, 이후 사용 복구가 이루어질 경우 RESTORED 상태로 발송됩니다.

또한 웹훅뿐만 아니라 주문 조회 API를 통해서도 현재 주문 상태를 확인하실 수 있습니다. 주문 상태값(status)이 AP인 경우 사용 처리된 주문을 의미하오니, 연동 시 참고 부탁드립니다.

### 첨부 이미지 (Bank of Trip API 문서 v1.1.4 캡처)

**첨부 1 — `attachments/8whslt/1787033747154.png` (Connecting a Webhook > REDEEMED)**
- 주문이 사용 처리되면 웹훅이 발송된다는 설명과 `REDEEMED` 이벤트 페이로드 예시:
  ```json
  {
      "eventType": "REDEEMED",
      "createdAt": "2024-08-02 11:07:50",
      "data": {
          "orderNumber": "TV2475657141",
          "referenceNumber": "x8BFOXvu2UHJZaaI",
          "dateAt": "2024-08-02 11:07:48"
      }
  }
  ```
- 필드 설명: `eventType`(웹훅 이벤트 타입), `createdAt`(생성 시각, `yyyy-MM-dd'T'HH:mm:ss` ISO8601), `data`(주문 정보 객체), `orderNumber`(`TV`로 시작), `referenceNumber`(채널 주문번호), `dateAt`(주문 사용 일시).
- 우측 Event Type 목록: **REDEEMED**, RESTORED, CANCELED, PARTIAL_CANCELED, BOOKING_ACCEPTED, BOOKING_REJECTED.

**첨부 2 — `attachments/dlBPKy/1787033858088.png` (Order > Search order > status enum)**
- `GET /api/partner/v1.1/orders/{orderNumber}` 주문 조회 응답의 `status` enum 정의(강조 부분):
  - **AV: Available**
  - **AP: Approved(Used)** ← 사용 처리된 주문
  - CR: Cancel Request
  - CL: Canceled
  - PC: Partial Canceled
  - EP: Expired
- 샘플 응답에 `"status": "AP"`, `"type": "BK"`, `bookingStatus`, `bookingAt`, `validFrom`/`expiredAt`, `unitAmounts` 등 포함.

## 이 스레드에서 확정된 사항 (요약)
1. **인증**: API 호출 = 접두어 없이 키만 / 웹훅 수신 = `Bearer` 접두어 포함. dev 인증키 재발급 `a26f3097-daae-4667-a968-c3a38cefdb5b`, 유효기간 없음.
2. **Rate Limit**: 분당 600회(dev·prod 동일, 변동 가능). 초과 시 헤더 없이 HTTP 429 + `{"code":"INTERNAL_ERROR","message":"Too Many Attempts."}`.
3. **부분취소**: 파트너발 API 미지원·개발계획 없음 → 양사 오퍼팀 커뮤니케이션. 결과는 PC/PARTIAL_CANCELED 상태로 반영.
4. **웹훅 등록**: `dev@bankoftrip.com` 메일 요청, 영업일 1일 내, dev·prod 각각 별도 등록.
5. **웹훅 검증**: 별도 서명(HMAC) 없음, nonce 중복 여부만 확인. Authorization은 우리가 사전 제공한 Bearer 토큰을 그대로 실어 보냄.
6. **prod 전환**: dev 테스트 완료 후 prod 인증키 요청. prod 상품은 dev와 유사하나 동일 보장 아님. 매핑 상품은 `www.bankoftrip.com/ko/products/b2b`, 미매핑 목록은 `op@bankoftrip.com` 요청.
7. **사용완료 통지**: 웹훅 `REDEEMED`(사용) / `RESTORED`(사용 복구), 주문 조회 `status=AP`(Approved/Used)로 확인.
