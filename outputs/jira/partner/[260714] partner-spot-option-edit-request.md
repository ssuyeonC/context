# 세부 기획안 요구사항 문서

## 배경

### 문제 정의

파트너 어드민의 스팟 수정 요청 중 **'옵션 정보 수정'(상품/옵션)** 기능이 실무적으로 사용 불가능한 상태다.

- 파트너가 입력하면 안 되는 값(**수수료·정산가**)이 파트너 화면에서 입력 가능하게 열려 있어, 잘못된 값이 들어가거나 검수 단계에서 반려된다. (그 외 실무 사용 불가 사유 추가 정리 — TBD)
- 그 결과 대부분의 옵션 정보 변경은 파트너가 관리자에게 **카카오톡으로 직접 요청**해 처리되고 있으며, 어드민 내 옵션 수정 요청 기능은 사실상 쓰이지 못한다.
- 데이터로도 확인된다. 옵션(상품/옵션) 수정 요청은 61건(전체 파트너 수정 요청의 0.5%)에 그치고, 그마저 승인 8건(13%)·반려 32건(52%)·대기 21건(34%)으로 승인율이 매우 낮다. 낮은 사용량은 수요가 없어서가 아니라, 기능이 못 쓸 상태라 요청이 카카오톡으로 우회된 결과다.

### 가설적 임팩트

- 옵션 정보 수정 기능을 정상화하면 현재 카카오톡으로 유입되는 옵션 수정 요청이 어드민 안으로 회수되어, 관리자-파트너 간 개별 소통 부하가 줄어든다.
- 파트너가 상품/옵션 정보를 스스로 정확하게 요청·반영할 수 있게 되어 반려·재요청이 감소한다.
- (정량 임팩트: **카카오톡으로 접수되던 옵션 수정 요청 건수 감소율**이 핵심 지표. 현재 카카오톡 유입량 베이스라인 파악 필요 — TBD)

## 구현

### 유저 플로우

파트너가 상품/옵션 정보를 수정하는 경우 아래 흐름을 따른다.

1. 파트너가 **'수정하기'** 버튼을 클릭해 편집 모드로 진입한다.
2. 파트너가 기존 상품/옵션 정보를 수정하거나, **'+ 상품 추가' / '+ 옵션 추가'** 로 새 상품/옵션을 추가한다.
3. 파트너가 입력·변경한 내용에 대해 번역을 진행한다. (신규 추가는 항상 번역, 기존 수정은 명칭이 바뀐 경우에만 번역)
4. 파트너가 **'수정완료'** 버튼을 클릭한다. (버튼 하단에 안내 문구 **"수정하신 정보는 관리자의 승인을 거쳐 최종 반영됩니다."** 노출)
5. 관리자가 관리자 어드민에서 요청을 검토하며, 이때 **정산가를 입력/수정**한다.
6. 관리자가 최종 **승인 혹은 반려**한다.

**추가와 수정의 분기**

- **상품/옵션 추가 시**: 파트너는 상품(옵션)명 · 판매가 · 정가를 입력하고 **번역하기**로 자동번역을 실행한다. 명칭·판매가·정가·번역 완료가 모두 필수이며, 미완료 시 검증 문구 **"모든 값을 입력하고 번역하기를 완료해주세요."** 를 노출한다. → 관리자가 검수 시 **정산가를 입력**하고 승인한다.
- **상품/옵션 수정 시**: 파트너는 상품(옵션)명 · 판매가 · 정가를 수정하고, **명칭이 바뀐 경우에만** 번역하기를 실행한다. → 관리자가 검수 시 **정산가를 수정**하고 승인한다.

### 프론트엔드 요구사항

- 옵션 정보 수정 영역은 **상품(부모) → 옵션(자식)** 계층으로 노출한다. 옵션은 상품 하위에 들여쓰기로 표시하며 **'옵션'** 라벨을 붙인다.
- 각 상품/옵션 항목은 **판매가(KRW)** · **정가(KRW)** · **정산가(KRW)** 를 노출한다.
- **파트너는 수수료와 정산가를 입력·편집할 수 없다.** 파트너 화면에서 수수료는 편집 대상으로 노출하지 않으며, 정산가는 조회 전용으로만 노출한다. 정산가 옆에는 안내 문구 **"'정산가'는 변경이 요청되면 관리자가 검토 후 입력합니다."** 를 함께 표시한다.
- 파트너는 상품에 **'+ 옵션 추가'**, 목록 하단에 **'+ 상품 추가'** 로 항목을 추가한다.
- 상품/옵션 명칭 옆에 **'번역하기'** 를 두고, 번역이 끝나면 **'번역 완료 ✓'** 로 상태를 표시한다.
- 수정 요청되어 승인 대기 중인 기존 항목은 **"⏳ 승인 대기 · 수정 요청됨"** 배지와 함께 비활성(디밍)으로 표시한다.
- 신규 추가되어 생성 대기 중인 항목은 **"⏳ 생성 대기 · 수정 요청됨"** 배지로 표시하며, 정산가 칸은 **"관리자 입력 대기 중입니다"** 로 노출한다.

**수정 요청 내역 확인**

- 편집 영역 우상단에 **'수정 요청 내역 확인'** 진입점을 둔다. 클릭 시 해당 스팟의 변경 요청 내역을 모달로 노출한다. (모달 제목: **"{스팟명} 변경 요청 내역"**)
- 내역은 표로 노출하며 컬럼은 **요청 ID · 수정 요청일 · 승인일 · 변경 내용 · 승인 여부**로 구성한다.
- 승인 여부는 상태 배지로 구분한다: **승인 · 대기 · 반려**.
- **반려** 건에는 **'반려 사유'** 를 확인할 수 있는 진입점을 함께 노출한다.
- 변경 요청 내역은 옵션 정보뿐 아니라 기본 정보·예약 기본 정보 등 다른 수정 요청 유형도 함께 노출한다. (노출 대상 유형 범위 확정 — TBD)

### 백엔드 요구사항

- 상품/옵션의 명칭·판매가·정가 변경 요청과 관리자 정산가 입력값을 저장·조회한다. **수수료·정산가는 파트너 입력 경로로 저장하지 않는다.**
- '수정 요청 내역 확인' 모달을 위해 스팟별 변경 요청 이력(요청 ID·요청일·승인일·변경 내용·승인 상태·반려 사유)을 조회한다. (기존 변경 요청 데이터 재사용 여부·필요 필드 확인 — TBD)

### 관리자 어드민 요구사항 (기능 확장 필요)

파트너가 제출한 상품/옵션 변경 요청을 관리자가 검수·처리할 수 있도록 관리자 어드민 기능 확장이 필요하다.

- **상품/옵션 추가 요청 검수**: 관리자는 검수 화면에서 해당 상품/옵션의 **정산가를 입력**한다. 이때 파트너가 입력한 명칭·판매가·정가도 관리자가 수정할 수 있어야 한다. 정산가 입력·검토 후 **승인**하면 최종 반영된다.
- **상품/옵션 수정 요청 검수**: 관리자는 검수 화면에서 해당 상품/옵션의 **정산가를 수정**한다. 마찬가지로 파트너가 입력한 값도 관리자가 수정할 수 있어야 한다. 검토 후 **승인**하면 최종 반영된다.
- 관리자는 검수 결과로 **승인 또는 반려**를 처리하며, 반려 시 파트너의 '수정 요청 내역 확인' 모달에서 볼 수 있도록 **반려 사유**를 함께 남긴다.
- (정산가 저장 데이터 모델·검수 대상 목록 조회 등 세부 확장 범위 — TBD)
