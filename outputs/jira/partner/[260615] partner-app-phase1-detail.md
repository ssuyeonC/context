# Phase 1 상세 요구사항

> 프레임워크 선정(Capacitor vs RN vs Native) 판단을 위한 자료이자, 개발 착수 전 스코프·디테일 확정용 문서.
> 양식 문서가 아닌 Phase 1 스코프 + 동작 디테일 정리. 본문의 **굵은 문구**는 사용자에게 노출되는 카피 초안이며, `{확정 필요}`는 개발 착수 전 정해야 할 열린 질문.

## 목표

- Phase 1의 본질: 현재 카카오 **알림톡(공식 채널)을 모바일 앱 푸시로 전환**한다.
- 스코프: 예약 관리 + 푸시 알림. (Phase 2 DM은 별도)
- 안정성 요건: 파트너 매장 운영에 직접 영향을 주므로, 출시 전 충분한 테스트와 기능 오류 최소화가 전제다.
- 성공 기준: ① 앱 전환 파트너가 알림톡 없이도 예약을 제때 처리한다(처리 지연이 알림톡 대비 늘지 않는다), ② 예약 처리 동선이 "알림 확인 → 앱 내 처리" 한 흐름으로 이어진다.

## 프론트엔드 요구사항 (앱)

### F1. 로그인 화면

- 파트너는 **어드민과 동일한 아이디·비밀번호**로 로그인한다. 어드민에 로그인할 수 있는 계정이면 별도 가입 절차 없이 그대로 진입한다.
- 파트너 등급 `TRAVEL_PARTNER` / `TRAVEL_PARTNER_SUPERIOR`은 동일한 화면·기능을 본다. 등급에 따른 분기는 없다.
- 최초 1회 로그인 후에는 재로그인이 필요 없다. 앱을 껐다 켜도 자동으로 로그인 상태를 유지한다.
- 발급받은 토큰은 OS 보안 저장소(iOS Keychain / Android Keystore)에 보관한다.
- 토큰이 만료·무효화된 상태로 진입하면 안내 **"다시 로그인해 주세요."**를 보이고 로그인 화면으로 보낸다.
- 로그인 실패 시 안내 **"아이디 또는 비밀번호를 확인해 주세요."**를 노출한다.
- 공유 단말(매장 공용 기기) 시나리오는 Phase 1 비범위로 둔다.
- `{확정 필요}` 수동 로그아웃 진입점을 둘지 — 공유 단말은 비범위지만, 계정 교체·기기 분실 대비로 필요한지 검토.

### F2. 예약 리스트 화면 — 파트너 어드민 웹 모바일 버전 재사용

- 본 화면은 신규로 만들지 않는다. **파트너 어드민 웹의 예약내역(리스트) 화면을 모바일 환경에 맞춘 버전을 그대로 사용**한다. 표시 컬럼·정렬·상태 구분·검색/필터·다중 스팟 통합 노출 등은 어드민 예약내역 화면의 사양을 따른다.
  - 따라서 "예약 항목에 무엇을 보일지, 어떻게 정렬·구분할지, 빈 상태·오류는 어떻게 다룰지"는 본 문서에서 별도 정의하지 않고 파트너 어드민 예약내역 리스트 기획을 단일 소스로 삼는다. (의존·연계 참고)
- 앱이 추가로 책임지는 부분은 **모바일 셸 동작**이다.
  - 앱 진입 시점에 최신 리스트를 1회 동기화한다.
  - **푸시 수신이 리스트 갱신의 주 트리거**다. 포그라운드에서 푸시를 받으면 **시스템 배너 노출과 리스트 자동 갱신을 모두** 수행한다.
  - 당겨서 새로고침(pull-to-refresh) 등 모바일에 맞는 갱신 수단을 제공한다.
- `{확정 필요}` 어드민 예약내역 화면을 모바일 폭에서 그대로 쓸 때의 반응형 완성도 — 추가 모바일 대응이 필요한 구간(컬럼 접힘, 가로 스크롤, 필터 UI 등)을 어디까지 보강할지.

### F3. 예약 상세 + 처리 액션 — 파트너 어드민 웹 모바일 버전 재사용

- 본 화면도 신규로 만들지 않는다. **파트너 어드민 웹의 예약 상세 화면(처리 액션 포함)을 모바일 버전으로 그대로 사용**한다. 상세에 표시되는 예약 정보, **[승인] / [변경 요청] / [취소 처리]** 액션, 변경 요청 공용 폼, 처리 결과 피드백은 어드민 예약 상세의 사양을 따른다.
  - 액션 노출/활성 조건(상태별), 변경 요청 폼의 입력 항목, 처리 성공·실패 피드백은 어드민 예약 상세 기획을 단일 소스로 삼는다.
- 앱이 추가로 책임지는 부분은 **진입 경로와 모바일 피드백 톤**이다.
  - 푸시 탭·인박스·리스트에서 이 상세 화면으로 진입한다(딥링크는 F4).
  - 처리 완료 피드백은 모바일에 맞는 인앱 토스트로 노출한다. (예: **"예약을 승인했어요." / "변경 요청을 보냈어요." / "취소 요청을 처리했어요."** — 최종 문구는 어드민 피드백과 톤 정렬)
- 모든 처리는 운영팀 어드민 알림에 정상 도달해야 한다(처리 로직·도달은 B2).

### F4. 푸시 수신·표시·딥링크

- 푸시를 탭하면 **해당 예약 상세로 바로 이동**한다.
- 앱 상태별 동작을 다음과 같이 보장한다.
  - **포그라운드**: 시스템 배너 노출 + 리스트 자동 갱신 (F2와 동일).
  - **백그라운드**: OS 알림으로 표시되고, 탭하면 예약 상세로 진입한다.
  - **종료(콜드 스타트)**: 앱을 실행하고, 인증이 유효하면 곧바로 의도한 예약 상세로 진입한다.
- **콜드 스타트 + 토큰 만료** 케이스: 로그인 화면 → 로그인 성공 후 **원래 의도된 예약 상세로 자동 복귀**한다(intent preservation).
- `{확정 필요}` 다건 푸시 묶음 표시(그룹핑)와 앱 아이콘 미읽음 뱃지 카운트 적용 여부.

### F5. OS 푸시 권한 거절 배너

- 앱 진입 시 OS 푸시 권한이 꺼져 있으면 인앱 상단에 안내 배너를 노출한다 — **"푸시가 꺼져 있어요. 알림을 받으시려면 설정에서 켜주세요."**
- 배너의 CTA **[설정 열기]**는 OS 설정 화면으로 딥링크한다.
- 권한을 허용하면 배너는 사라진다.
- 파트너는 배너를 닫을 수 있다. 단, **닫음은 현재 노출 세션 동안만 유효**하며, 푸시가 여전히 꺼져 있으면 다음 두 시점에 배너를 다시 노출한다.
  - 앱을 백그라운드로 보냈다가 다시 포그라운드로 가져올 때
  - 앱을 종료했다가 다시 켤 때(콜드 스타트)
- 즉 앱은 (백그라운드→포그라운드 전환, 콜드 스타트) 진입 시마다 OS 푸시 권한을 다시 확인하고, 꺼져 있으면 직전에 닫았더라도 배너를 재노출한다. 권한이 켜져 있으면 노출하지 않는다.
- `{확정 필요}` 최초 권한 요청 시점 — 로그인 직후 즉시 요청할지, 첫 예약 수신 등 맥락이 생긴 뒤 요청할지.

### F6. 알림 인박스 화면

- 파트너는 받은 푸시 이력을 앱 내 알림 인박스에서 다시 확인한다.
- 인박스는 보관된 이력을 시간순으로 노출한다.
- 각 항목은 **이벤트 타입 · 스팟명 · 예약자명 · 발생 시각 · 읽음/안읽음**을 보이고, 읽음/안읽음은 배경색으로 구분한다.
- 항목을 클릭하면 **읽음 상태로 전이**하고 해당 예약 상세로 이동한다.
- 단건 삭제가 가능하다.
- 인박스 진입점(예: 상단 벨 아이콘)에 미읽음 개수를 표시한다.
- 받은 알림이 없을 때 안내 **"받은 알림이 없어요."**를 노출한다.
- 어드민 알림에서 쓰는 처리 필요/처리됨/자동확정 같은 상태 라벨은 본 인박스에 적용하지 않는다(단순화).
- `{확정 필요}` 연결된 예약이 삭제·만료되어 상세로 이동할 수 없는 항목의 처리 방식.
- `{확정 필요}` 전체 읽음 처리(모두 읽음) 액션 제공 여부.

### F7. 강제 업데이트 화면

- 앱 진입 시 최소 지원 버전을 확인하고(아래 B5), 미달이면 전체 차단 화면을 노출한다.
- 차단 화면은 안내 **"앱을 업데이트해 주세요."**와 **[스토어로 이동]** CTA를 보인다.
- `{확정 필요}` 권장 업데이트(소프트, 건너뛰기 가능)와 강제 업데이트(하드, 차단)를 구분할지 — 화면 단에서 둘 다 표현 가능한 구조로 둘지.

### F8. 알림톡 관련 (앱 측)

- 앱은 알림톡 관련 UI/조작을 일절 노출하지 않는다. (앱과 알림톡은 별개 채널 — 운영·발송 측면은 B6 참고)

## 백엔드 요구사항

### B1. 파트너 인증

- 어드민과 동일한 계정 체계로 인증한다. 어드민 로그인 가능한 모든 파트너 계정이 그대로 사용 가능하다.
- 재로그인이 필요 없도록 장기 토큰을 발급한다.
- 관리자 측에서 권한 회수 등으로 **토큰을 강제 무효화**할 수 있어야 한다. 무효화된 토큰의 요청은 거부한다(앱은 이를 받아 로그인 화면으로 전환 — F1).

### B2. 예약 조회·처리 — 어드민 예약내역 오퍼레이션 재사용

- F2/F3가 파트너 어드민 예약내역 화면을 재사용하므로, **백엔드도 어드민 예약내역이 이미 사용하는 조회·처리 오퍼레이션을 그대로 사용**한다. 리스트/상세 표시·처리를 위한 신규 API 신설은 기본적으로 불필요하다.
  - 예약 조회: 어드민 예약내역 화면이 쓰는 조회를 그대로 사용한다. **파트너의 보유 스팟 전체 통합 조회는 어드민이 이미 처리**하므로 앱용 별도 집계 API를 새로 만들지 않는다.
  - 예약 처리: 어드민의 예약 처리(승인 / 변경 요청 / 취소 처리) 뮤테이션을 그대로 사용한다.
- **모든 처리 액션은 운영팀 어드민 알림 시스템에 정상 도달해야 한다**(예약 변경 요청, 예약 거절/취소 요청 등). — 별도 진행 중인 어드민 알림 기획에 의존.
- 앱 전용으로 추가될 수 있는 백엔드 작업은 인증(B1)·푸시(B3)·인박스(B4)·버전게이트(B5) 쪽이며, 예약 리스트/상세 자체는 어드민과 같은 데이터 경로를 탄다.
- `{확정 필요}` 동시 처리 충돌(TOCTOU) — 같은 예약을 웹 어드민에서 이미 처리한 뒤 앱에서 다시 처리하려는 경우, 최신 상태를 반환해 중복 처리를 막는 가드. (어드민 처리 경로를 공유하므로 어드민 측 가드와 동일하게 동작)

### B3. 푸시 발송

- **발송하는 푸시메시지의 종류·본문·정책은 파트너 어드민 알림 시스템 태스크(COM-2504)를 단일 소스로 삼는다.** (https://creatrip.atlassian.net/browse/COM-2504, 세부내용 변경 가능) 백엔드는 해당 태스크에서 정의된 이벤트 시점에 맞춰 파트너에게 푸시를 발송한다.
  - 참고(현재 기준, COM-2504에 따라 변경 가능): 예약 접수 / 예약 변경 요청 / 예약 취소 요청 / 예약 변경 처리 완료 / 예약 취소 요청 처리 완료.
- 푸시 본문에 **스팟명, 예약자명, 예약 일시** 등 식별 정보를 포함한다. (다중 스팟 파트너가 어느 매장 건인지 본문만으로 식별 가능해야 함)
- 탭 시 예약 상세로 이동할 수 있도록 **딥링크 페이로드**를 포함한다.
- `{확정 필요}` **발송 인프라 선택.** 현재 사내 푸시는 OneSignal을 쓰지 않는다(OneSignal은 메일에만 관여). 푸시는 **AWS와 Firebase**를 사용 중이므로, 본 앱 푸시를 어느 인프라로 발송할지는 별도 검토가 필요하다.
- 발송→전달→탭 단계를 관측(로깅)할 수 있게 한다. 푸시 신뢰성은 알림톡 대체의 핵심 품질 지표다.
- 이벤트 타입별 수신 ON/OFF 같은 인앱 푸시 수신 설정은 Phase 1 범위에서 제외한다(비범위 참고). 정의된 이벤트는 모두 발송한다.

### B4. 알림 인박스 저장

- 발송한 푸시 이력을 **30일 보관**하고 조회·삭제할 수 있게 한다. 30일이 지난 항목은 자동 삭제한다.
- 항목별로 이벤트 타입·스팟명·예약자명·발생 시각·읽음 상태를 관리한다.
- 항목의 읽음 상태 전이와 단건 삭제를 지원한다.
- 인박스에 쌓이는 알림의 종류·정책은 푸시 발송과 동일하게 COM-2504를 따른다.
- 인박스 항목은 **연결된 예약의 생애주기와 독립적으로 보관**한다. 예약이 삭제·만료되어도 인박스 이력은 그대로 남으며, 백엔드는 저장된 항목을 그대로 반환한다. 이 경우 상세로 이동할 수 없으므로 앱은 **"예약을 찾을 수 없습니다."**를 노출한다(F6).

### B5. 버전 게이트

- 앱 진입 시 호출하는 **최소 지원 버전 확인 엔드포인트**를 제공한다.
- v1 출시 시점에 인프라만 박아두고, 실제 강제 발동 정책(어느 버전부터 차단할지)은 운영 중에 정의한다.

### B6. 알림톡 연계 (운영 영역)

- 알림톡 수신 설정은 관리자 운영 영역이다. 어드민에 기존 토글 기능이 있으므로 그대로 활용한다(신규 개발 최소).
- 전환 운영 흐름:
  1. 관리자가 파트너에게 앱 사용을 권유한다.
  2-1. 파트너가 앱을 사용함 → 관리자가 어드민에서 해당 파트너의 알림톡 설정을 제거한다.
  2-2. 파트너가 미사용 → 알림톡 설정을 유지한다.
- 전환은 파트너별로 수동·점진적으로 진행한다. 전환이 끝나기 전까지 한 파트너가 앱 푸시와 알림톡을 **동시에 받을 수 있으며**, 이는 누락을 막기 위한 의도된 과도기 상태다.
