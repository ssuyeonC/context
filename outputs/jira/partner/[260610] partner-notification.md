# 세부 기획안: 파트너 대상 어드민 알림 기능

## 배경

### 문제 정의

현재 파트너가 받는 알림은 카카오 알림톡(예약 접수·확정)뿐이며, 파트너 어드민 내부에는 파트너가 자신과 관련된 사건을 능동적으로 인지할 수 있는 알림 채널이 없음.

그 결과 파트너는 어드민에 접속해도 다음을 직접 메뉴를 돌며 확인하거나, 알림톡·카톡에 의존해야 함.

- 새 예약이 접수되었는지
- 유저가 예약 변경 또는 취소를 요청했는지
- 자신이 보낸 스팟 수정 요청이 어드민에서 승인 또는 반려되었는지
- 자신의 스팟에 새 리뷰가 작성되었는지

> 참고) 추후 진행될 파트너 예약 관리 모바일 앱은 푸시·알림 인박스를 "어드민 알림과 동일한 스펙"으로 설계할 예정.

### 가설적 임팩트

- 파트너가 어드민 한 곳에서 일상 사건을 통합 인지 → 알림톡·카톡 의존 빈도 감소, 어드민 일상화(파트너 어드민 개선 로드맵의 핵심 명제)에 직접 기여
- 새 예약·변경/취소 요청을 즉시 인지 → 파트너의 예약 처리 리드타임 단축
- 리뷰 작성 즉시 인지 → 리뷰 응대 속도 향상(파트너 리뷰 답글 권한 개방과 시너지)
- 채널 비종속 알림 모델 확보 → 추후 모바일 앱 푸시·인박스의 선행 공통 기반

## 구현

### 유저 플로우

**알림 발생 (이벤트 → 파트너)**

이벤트가 발생하면 시스템은 대상 스팟을 관리하는 파트너에게 어드민 인앱 알림을 1건 생성한다. 알림은 파트너가 취해야 할 후속 동작의 성격에 따라 세 등급으로 분류한다.

- **A. 액션 필수** — 파트너의 처리(승인/거절 등)가 있어야 예약 흐름이 진행되는 알림.
- **B. 인지 + 후속 동선** — 처리는 필수가 아니나, 자연스러운 후속 액션(선택적 CTA)이 따라붙는 알림.
- **C. 순수 인지** — 이미 완료된 사건의 통지로, 파트너는 인지만 하면 되는 알림.

| # | 이벤트 | 트리거 주체 | 등급 | 파트너 후속 액션 | 도착 화면 |
|---|--------|:--------:|:--:|----------------|----------|
| 1 | 유저 예약 접수 — **수동 승인 상품** | 유저 | A | 예약 승인 / 예약 변경 요청 / 예약 거절 요청 | 예약 상세 |
| 2 | 유저의 예약 변경 요청 | 유저 | A | 변경 승인 / 거절 / 무시 | 예약 상세 |
| 3 | 유저가 파트너의 변경 제안을 **거절('원하는 날 없음')** | 유저 | A | 예약 승인 / 예약 변경 요청 / 예약 거절 요청 | 예약 상세 |
| 4 | 유저의 리뷰 작성 | 유저 | B | 리뷰 답글 작성(선택) | 리뷰 상세 |
| 5 | 유저 예약 접수 — **자동 확정 상품** | 유저 | C | — | 예약 상세 |
| 6 | 유저가 파트너의 변경 제안을 **승낙** | 유저 | C | — | 예약 상세 |
| 7 | 유저의 예약 취소 완료 | 유저 | C | — | 예약 상세 |
| 8 | 유저의 예약 변경 요청에 대한 관리자 처리 완료 | 관리자 | C | — | 예약 상세 |
| 9 | 파트너의 예약 거절 요청에 대한 관리자 처리 완료 | 관리자 | C | — | 예약 상세 |
| 10 | 파트너의 스팟 수정 요청에 대한 관리자의 처리 완료 | 관리자 | C | — | 수정 요청 상세 |

**분류 해설 — 비대칭/분기 포인트**

- **예약 접수는 상품 설정에 따라 분기(#1·#5).** 수동 승인 상품이면 파트너 액션이 필요하고(A), 자동 확정 상품이면 이미 확정되어 인지만 하면 된다(C).
- **'예약 승인'과 '예약 거절'은 비대칭.** 승인은 즉시 확정되지만, 거절은 '거절 요청' → 운영팀 승인 → 완료의 흐름을 거친다. 그래서 파트너가 '거절 요청'을 누르면 후속으로 #9(거절 요청 처리 완료, C)가 따라온다.
- **유저의 변경 제안 응답은 두 갈래.** 승낙하면 즉시 반영되어 인지만 하면 되고, '원하는 날이 없음'으로 거절하면 파트너가 다시 처리해야 한다.
- **유저의 예약 취소는 즉시 상태가 바뀜.** 요청-승인 단계가 없으므로 '취소 완료' 통지로 인지만 하면 된다.
- 다중 스팟을 보유한 파트너(투어스토리 등)는 보유한 모든 스팟의 이벤트를 통합 수신하며, 알림 본문에 **스팟명**을 포함해 어느 스팟의 사건인지 식별할 수 있다.

**알림 수신 (파트너)**

1. 파트너는 파트너 어드민 상단 알림 영역에서 미확인 알림 개수를 배지로 확인한다.
2. 파트너는 알림 패널을 열어 시간순으로 정렬된 알림 리스트를 본다.
3. 파트너가 알림 항목을 클릭하면 다음 두 가지가 동시에 일어난다.
   - 해당 알림이 '읽음' 상태로 바뀐다. (배경색 변화로 구분)
   - 알림이 가리키는 상세 화면이 열린다. (예약 관련 → 예약 상세, 수정 요청 결과 → 스팟 수정 요청 상세, 리뷰 → 스팟 리뷰 상세)
4. 파트너는 알림을 단건으로 삭제할 수 있다.

**조치 필요 구분 (A등급)**

- 알림 패널에 **전체 / 조치 필요** 필터(또는 탭)를 제공한다.
- '조치 필요'는 A등급(액션 필수) 알림 중 **연결된 예약·요청이 아직 처리되지 않은 것**만 모아 보여준다.
- 파트너가 해당 액션을 완료하면(예: 예약 승인/거절 요청 발송, 변경 요청 승인/거절/무시) 그 알림은 '조치 필요'에서 자동으로 빠진다. (전체 목록에는 읽음 기록으로 남는다)
- '조치 필요' 건수는 미읽음 배지와 별개로 "처리할 항목 수"로 강조 노출할 수 있다.
- 이 구분은 알림에 처리 상태 필드를 저장해서가 아니라, A등급 알림이 가리키는 예약·요청의 **현재 상태에서 파생**한다(백엔드 §4 참조). 따라서 운영팀 알림식 처리 상태 라이프사이클 라벨(처리 필요 → 처리됨)을 알림 자체에 도입하는 것은 아니다.

**알림톡과의 관계 — 상호 독립 채널**

- 어드민 알림과 알림톡은 내용상 동일한 사건을 다루지만 **상호 독립적인 기능**이다. 동일 이벤트가 발생하면 두 채널이 각각 발송되며, 한쪽이 다른 쪽의 발송을 대체하거나 차단하지 않는다.
  - 예: 유저의 예약 발생 → 알림톡 발송 **그리고** 어드민 알림 발송 (○) / 알림톡 발송 ↔ 어드민 알림 발송이 서로 연동·배타되는 구조 (×)
- 채널별 수신 제어는 별개로 관리된다. 파트너의 알림톡 수신 여부는 **관리자 어드민의 기존 기능**으로 제어한다. 향후 앱을 사용하는 파트너는 관리자 어드민에서 알림톡 수신을 끄는 방식으로 채널을 정리한다.

### 프론트엔드 요구사항

**파트너 어드민 - 알림 영역 (신규)**

- 파트너 어드민 헤더(또는 우측 영역)에 알림 아이콘과 미읽음 배지를 노출한다.
  - 미읽음 알림이 1건 이상이면 미읽음 수를 숫자 배지로 노출한다.
  - 미읽음 알림이 없으면 배지를 노출하지 않는다.
- 알림 패널(드롭다운 또는 모달)을 제공한다.
  - 알림은 발생 일시 기준 최신순으로 정렬한다.
  - **전체 / 조치 필요** 필터(또는 탭)를 제공한다. '조치 필요'는 처리되지 않은 A등급 알림만 노출한다.
  - 알림 항목별 표시 정보
    - 이벤트 타입 라벨
    - 대상 스팟명 (다중 스팟 파트너 식별용)
    - 사건 식별 정보 (예약자명, 리뷰 일부 등 이벤트 성격에 맞는 식별값)
    - 발생 일시
    - 읽음/미읽음 (배경색으로만 구분, 별도 텍스트 라벨 없음)
  - 알림 항목 자체가 클릭 영역이며, 별도 '확인하기' 버튼은 두지 않는다.
  - 알림 단건 삭제 아이콘을 제공한다. 본문 클릭 동작과 분리하여, 삭제 아이콘 클릭이 상세 이동으로 이어지지 않도록 한다.
  - '전체 읽음 처리'를 제공한다.
  - 알림 패널을 열 때마다 최신 알림 리스트를 다시 조회한다.
- 알림 항목에는 운영팀 어드민 알림식 처리 상태 텍스트 라벨(처리 필요 / 처리됨 / 자동확정)을 두지 않는다. 처리 상태는 항목 단위 라벨이 아니라 '조치 필요' 필터로 표현한다(읽음/미읽음 + 조치 필요 필터, 모바일 앱 인박스와 동일한 단순화 방침).

**조치 필요 카운트**

- 미읽음 배지와 별개로, 처리되지 않은 A등급 알림 수(=조치 필요 건수)를 강조 노출할 수 있다. (배치·표현은 디자인 단계에서 확정)

**미읽음 배지 갱신 방식**

- 웹 v1은 실시간 푸시(SSE/WebSocket)를 도입하지 않는다. 따라서 미읽음 배지(및 조치 필요 카운트)는 다음 두 방식의 조합으로 갱신한다.
  - **클라이언트 이벤트 시 재조회** — 파트너 어드민 페이지 진입, 탭 포커스 복귀, 알림 패널 오픈 시 다시 조회한다.
  - **주기적 폴링** — 위 이벤트와 별개로 일정 주기(기본 60초)로 재조회하여, 파트너가 화면을 만지지 않는 동안 발생한 사건도 곧 배지에 반영되도록 한다. (폴링 주기는 운영 후 조정 가능)
- 파트너 본인 동작으로 수치가 바뀌는 경우(알림 읽음 처리, 상세에서 처리 완료 등)는 클라이언트가 즉시 반영한다. 위 재조회·폴링은 외부(유저·관리자)에서 발생한 인바운드 사건을 반영하기 위한 것이다.
- 사건 발생 즉시 수준의 실시간 알림은 모바일 앱 푸시가 담당하며(본 범위 외), 동일 알림 기록을 구독해 재사용한다.

**이벤트 타입별 노출 카피 (파트너에게 보이는 문구) — 초안**

- 신규 예약 접수: **"새 예약이 접수되었어요"**
- 유저 예약 변경 요청: **"예약 변경 요청이 도착했어요"**
- 유저가 변경 제안 거절: **"고객이 제안하신 변경일을 받지 않았어요"**
- 유저가 변경 제안 승낙: **"고객이 변경일을 수락했어요"**
- 유저 예약 취소: **"예약이 취소되었어요"**
- 신규 리뷰 작성: **"새 리뷰가 작성되었어요"**
- 예약 변경 요청 처리 완료(관리자): **"예약 변경 요청이 처리되었어요"**
- 예약 거절 요청 처리 완료(관리자): **"예약 거절 요청이 처리되었어요"**
- 스팟 수정 요청 승인: **"보내신 스팟 수정 요청이 승인되었어요"**
- 스팟 수정 요청 반려: **"보내신 스팟 수정 요청이 반려되었어요"**

> 위 카피는 초안이며, 디자인·카피 단계에서 확정한다.

**액션 필수(A) 알림의 처리 동선**

- 액션 필수 알림(접수·변경 요청·변경 제안 거절)은 알림에서 상세로 진입한 뒤 **그 화면에서 바로 처리**를 할 수 있어야 한다. 알림톡의 처리 동선과 결과가 일관되도록 한다.
- 유저 예약 변경 요청(#2)의 처리 액션은 **승인 / 거절 / 무시** 3가지이며, 예약 상세의 요청 처리·진행 배너 정의(`requirements_partner-reservation-list-detail-improvements.md`의 요청 처리·진행 배너)를 그대로 따른다.

**알림 클릭 시 이동 경로**

- 예약 관련 알림: 해당 예약 상세로 이동한다.
- 수정 요청 처리 결과 알림: 해당 스팟 수정 요청 상세로 이동한다.
- 리뷰 작성 알림: 해당 스팟 리뷰 상세로 이동한다.

### 백엔드 요구사항

**1. 알림 데이터 모델 — 채널 비종속·다수신자 수용**

- 기존 운영팀 어드민 알림 테이블의 수신자 모델을 **운영팀과 파트너 모두 수용**할 수 있도록 확장한다(수신자 유형 + 수신자 식별자).
- 알림 기록은 이벤트 종류, 대상 스팟, 식별 정보, 읽음 여부, 생성 일시를 저장하며, **노출 채널과 분리**한다(향후 앱 푸시 채널이 동일 기록을 구독).
- 파트너 알림의 수신자는 스팟 소유 파트너 단일이다(아래 §2). 운영팀 알림과 파트너 알림이 동일 인프라를 공유하므로, 수신자 모델은 운영팀·파트너 두 유형을 구분해 수용한다.
- 파트너 알림은 **처리 상태 필드 없이 읽음/미읽음만 관리**한다. '조치 필요' 여부는 알림에 저장하지 않고, A등급 알림이 가리키는 연결 엔티티(예약·요청)의 현재 상태에서 파생한다(§4).

**2. 수신자 결정**

- 파트너와 스팟의 관계는 **파트너 : 스팟 = 1 : N**이다. 한 파트너가 여러 스팟을 보유할 수 있으나(예: '투어스토리'는 연결된 스팟이 매우 많다), **하나의 스팟은 하나의 파트너에만 귀속된다**(스팟의 소유자가 단일 값으로 관리됨). 대부분의 파트너는 1개 스팟만 보유한다.
- 따라서 이벤트 대상 스팟의 **소유 파트너**가 수신자로 단일하게 결정된다.
- 다수의 스팟을 보유한 파트너(투어스토리 등)는 보유한 모든 스팟의 이벤트를 수신한다. 알림량이 많을 수 있으므로 본문의 **스팟명** 식별이 특히 중요하며, 스팟 단위 필터·그룹화는 차기 과제로 둔다.

**3. 알림 발송 트리거**

상세 분류는 유저 플로우의 '알림 유형 매트릭스(#1~#10)'를 따른다. 발송 트리거는 다음과 같다.

| 이벤트(매트릭스 #) | 발송 시점 | 수신자 |
|--------|----------|--------|
| 유저 신규 예약 생성 (#1·#5) | 예약 생성 성공 시. 상품의 확정 방식(수동 승인/자동 확정)에 따라 등급 분기 | 대상 스팟 파트너 |
| 유저 예약 변경 요청 (#2) | 변경 요청 생성 시 | 대상 스팟 파트너 |
| 유저가 파트너 변경 제안 거절 (#3) | 유저가 '원하는 날 없음'으로 응답 시 | 대상 스팟 파트너 |
| 유저 리뷰 작성 (#4) | 리뷰 생성 성공 시 | 대상 스팟 파트너 |
| 유저가 파트너 변경 제안 승낙 (#6) | 유저가 변경일 수락 시 | 대상 스팟 파트너 |
| 유저 예약 취소 (#7) | 예약 취소 상태 전이 성공 시(즉시 취소) | 대상 스팟 파트너 |
| 관리자의 유저 발 예약 변경 요청 처리 완료 (#8) | 관리자 처리 완료 시 | 대상 스팟 파트너 |
| 관리자의 파트너 발 예약 거절 요청 처리 완료 (#9) | 관리자 처리(승인/반려) 완료 시 | 요청을 보낸 파트너 |
| 관리자의 스팟 수정 요청 처리 완료 (#10) | 수정 요청 상태 전이(승인/반려) 시 | 요청을 보낸 파트너 |

**4. 조회**

- 본인 수신 알림 리스트 조회 (최신순, 페이지네이션)
- 미읽음 알림 수 조회 (배지용) — 클라이언트 이벤트 재조회 및 주기적 폴링(기본 60초)에서 반복 호출되므로, 가볍게 응답할 수 있어야 한다(미읽음 수만 반환).
- **조치 필요 조회·카운트** — A등급 알림 중 연결된 예약·요청이 아직 미처리 상태인 것만 필터링/집계한다.
  - 처리 여부는 알림에 저장된 값이 아니라, 연결 엔티티의 현재 상태(예: 예약이 아직 승인 대기인지, 변경 요청 케이스가 아직 종료되지 않았는지)로 판정한다.
  - A등급은 전체 알림 중 소수이므로, 조치 필요 판정을 위한 연결 엔티티 조회 비용은 감당 가능한 수준이다.

**5. 변경**

- 알림 읽음 처리 (단건 / 전체)
- 알림 단건 삭제

**6. 보존 정책**

- 알림 생성 후 30일 경과 시 자동 삭제한다(운영팀 어드민 알림의 기존 보존 배치 재사용).

**7. 향후 채널 확장 지점 (참고 — 본 범위 외)**

- 모바일 앱 개발 시, 동일 알림 기록을 푸시 발송 어댑터가 구독해 FCM/APNS로 전달하고 앱 인박스에 노출한다.
- 이벤트 타입별 파트너 수신 ON/OFF 설정은 모바일 앱 v1의 푸시 설정과 정렬되는 지점이나, 웹 인앱 알림 v1에서는 다루지 않는다(기본 전체 수신).

## 비범위 (Out of Scope)

- 모바일 앱 푸시·알림 인박스 (모바일 앱 v1 스코프)
- 알림톡 채널의 발송 내용·설정 변경
- 이벤트 타입별 파트너 수신 설정 토글 (차기 검토)
- 파트너 ↔ 운영팀/고객 간 양방향 메시지(다이렉트 메시징 기획과 별개)
- 파트너 대상 알림의 슬랙 발송 — 슬랙 알림은 운영팀 전용으로 유지한다(파트너 대상은 발송하지 않음).

## 확정 사항 (검토 완료)

- **수신자 모델**: 파트너 : 스팟 = **1 : N** (한 파트너가 다수 스팟 보유 가능, 1스팟은 단일 파트너 귀속 — 스팟 소유자가 단일 값으로 관리됨을 스키마로 확인). 수신자 = 이벤트 대상 스팟의 소유 파트너 단일. 다스팟 파트너는 보유 전 스팟의 이벤트를 수신(§백엔드 1·2 반영).
- **알림톡과의 관계**: 어드민 알림과 알림톡은 상호 독립 기능. 동일 이벤트에 각 채널이 독립 발송되며 연동·배타하지 않는다. 채널별 수신 제어는 별개(알림톡 수신은 관리자 어드민의 기존 기능으로 관리)(§유저 플로우 반영).
- **조치 필요 구분**: A등급(액션 필수) 알림을 '조치 필요'로 묶어 별도 필터·카운트로 제공. 처리 완료 여부는 알림에 저장하지 않고 연결 엔티티 상태에서 파생하여, 처리되면 자동으로 조치 필요에서 빠진다(§유저 플로우·프론트·백엔드 4 반영).
- **슬랙 발송**: 파트너 대상 알림에는 불필요(비범위 반영).
