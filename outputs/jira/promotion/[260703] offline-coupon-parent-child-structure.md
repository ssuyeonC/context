# 세부 기획안 요구사항 문서

## 배경

### 문제 정의

오프라인 쿠폰은 동일한 공급처로부터 공급받는 혜택이더라도, 혜택 내용이나 쿠폰 적용을 위한 바코드가 달라지면 구조적으로 매번 새로운 쿠폰 객체를 만들어야 한다.

- 예: 롯데백화점이 제공하는 쿠폰이라도, 4월 1일부터 혜택과 바코드가 바뀌면 운영자는 새로운 오프라인 쿠폰을 별도로 생성해야 한다.
- 이때 변경 전에 만들어둔 쿠폰은 만료 처리되며, **해당 쿠폰을 이미 다운로드해둔 유저의 쿠폰도 함께 만료 처리된다.**

그 결과 유저는 같은 제휴처에 유효한 후속 혜택이 존재함에도 만료된 쿠폰을 다시 발견해 재다운로드해야 하고, 운영자는 혜택이 갱신될 때마다 쿠폰 전체를 새로 구성해야 하는 비효율과 유저 이탈·혼선을 감수하게 된다.

현재 오프라인 쿠폰 하나가 갖는 정보는 다음과 같다: 활성화 여부, 쿠폰 이름, 담당자, 할인 혜택, 스팟 연결, 거래처 연결, 등록일자, 사용 주기, 유효기간, 저장 수, 비고, 쿠폰 이미지.

이 중 혜택 갱신 시점마다 실제로 바뀌는 값(할인 혜택, 유효기간, 비고, 쿠폰 이미지)과, 제휴처 단위로 유지되는 값(그 외)이 하나의 객체에 묶여 있어, 값 일부만 바뀌어도 쿠폰 전체를 재생성해야 하는 구조가 문제의 원인이다.

### 가설적 임팩트

- **관리자의 쿠폰 관리 리소스 효율화**: 혜택·기간·바코드가 갱신될 때 쿠폰 전체를 새로 만들지 않고, 부모 쿠폰에 자식(기간별 혜택)만 추가하면 되도록 하여 운영 공수를 절감한다.
- 유저의 재다운로드 마찰과 만료 혼선을 줄여, 이미 다운로드한 쿠폰이 후속 혜택으로 자연스럽게 이어지도록 한다.

## 구현

### 유저 플로우

- 유저는 오프라인 쿠폰(부모)을 다운로드하며, 저장은 부모 단위로 이루어진다.
- 유저는 다운로드한 쿠폰에서 **현재 시점에 유효한 자식**의 정보(할인 혜택, 유효기간, 비고, 쿠폰 이미지)를 본다.
  - 자식이 여러 개인 경우, 유효기간 시작일 순서대로 현재 시점에 해당하는 자식 1개만 노출한다.
- 시간이 흘러 기간이 넘어가면, 유저는 별도 조작 없이 동일한 부모 쿠폰에서 다음 자식의 정보를 보게 된다.
  - 예: 오프라인 쿠폰 A에 자식a(유효기간 1/1–3/31), 자식b(유효기간 4/1–6/30)가 있을 때, 3/30에 A를 다운로드한 유저는 3/31까지는 자식a의 정보를 보고 있다가 4/1로 넘어가면 동일한 A의 자식b 정보를 보게 된다.
- 현재 시점에 유효한 자식이 하나도 없는 경우(모든 자식이 만료된 경우), 해당 쿠폰은 마이페이지 쿠폰함의 **만료됨** 섹션으로 이동한다. (현재 만료 쿠폰 처리 방식과 동일)

### 프론트엔드 요구사항

**어드민 — 오프라인 쿠폰 등록/수정 화면**

- 오프라인 쿠폰 등록/수정 화면을 부모-자식 구조로 개편한다.
- 부모 영역에서 관리하는 값: 활성화 여부, 쿠폰 이름, 담당자, 스팟 연결, 거래처 연결, 등록일자, 사용 주기, 저장 수.
- 자식 영역에서 관리하는 값: 할인 혜택, 유효기간, 비고, 쿠폰 이미지.
  - 운영자는 하나의 부모 쿠폰 아래에 자식을 여러 개 추가·수정·삭제할 수 있다.
- 자식의 유효기간 입력을 기존 단일 날짜 값에서 **시작일–종료일 범위** 입력으로 변경한다.
- 하나의 부모 쿠폰 안에서 자식들의 유효기간이 서로 겹치지 않도록 어드민에서 유효성 검증을 한다.
  - 운영자가 저장하려는 자식의 유효기간이 같은 부모의 다른 자식과 하루라도 겹치면 저장을 막고, **"유효기간이 다른 쿠폰과 겹칩니다. 겹치지 않는 기간으로 설정해 주세요."** 안내를 노출한다.
  - 겹침 여부는 시작일–종료일이 하루라도 교차하는 경우를 포함하며, 경계일이 맞닿는 경우(예: 자식a가 3/31 종료, 자식b가 3/31 시작)도 겹침으로 본다. 따라서 다음 자식의 시작일은 이전 자식의 종료일보다 최소 하루 이후여야 한다.
  - 자식 간 사이에 공백 기간(어느 자식에도 속하지 않는 날짜)이 생기는 것은 허용한다. 해당 기간에는 유효한 자식이 없으므로 쿠폰이 일시적으로 만료 상태로 노출된다.

**유저 — 쿠폰 노출**

- 다운로드·저장 수는 부모 단위로 집계·표시한다.
- 쿠폰 카드/상세에 노출되는 할인 혜택·유효기간·비고·쿠폰 이미지는 현재 시점에 유효한 자식 값에서 가져온다.
- 유효한 자식이 없어 만료된 쿠폰은 기존과 동일하게 **만료됨** 섹션에서 노출한다.

### 백엔드 요구사항

- 오프라인 쿠폰 데이터 모델을 부모-자식 구조로 분리한다.
  - 부모: 활성화 여부, 쿠폰 이름, 담당자, 스팟 연결, 거래처 연결, 등록일자, 사용 주기, 저장 수.
  - 자식: 할인 혜택, 유효기간(시작일 `start_date` – 종료일 `end_date`), 비고, 쿠폰 이미지.
- 유효기간을 기존 단일 날짜에서 시작일–종료일 범위로 변경한다.
  - 시작일·종료일은 모두 **포함** 기준이다. 종료일이 3/31이면 3/31 하루 전체가 유효하고, 4/1부터 만료로 전환된다.
- 현재 시점에 노출할 자식을 선택하는 로직을 추가한다.
  - 유효기간 시작일 오름차순으로, 현재 시점(오늘)이 시작일–종료일 범위에 포함되는 자식 1개를 선택한다.
  - 조건에 해당하는 자식이 없으면 해당 부모 쿠폰은 만료 상태로 취급한다.
- 자식 유효기간 겹침 방지 검증을 서버에서도 수행한다.
  - 자식 생성·수정 시 같은 부모의 다른 자식과 유효기간이 겹치면 저장을 거부한다. (어드민 UI 검증과 동일 규칙을 서버에서도 보장하여 우회·동시 저장을 방지)
  - 이 규칙에 따라 현재 시점에 유효한 자식은 항상 최대 1개가 되도록 보장한다.
- 유저 조회 API는 부모 정보와 함께 현재 시점 유효 자식의 정보(할인 혜택·유효기간·비고·쿠폰 이미지)를 반환한다.
- 저장(다운로드)·저장 수 집계는 부모 단위로 처리한다. 자식이 바뀌어도 유저의 다운로드 상태는 유지된다.
- 기존 데이터 마이그레이션
  - 기존 오프라인 쿠폰을 부모로 승격한다.
  - 각 기존 쿠폰의 정보를 바탕으로 자식 1개를 생성한다. 이때 기존 **등록일자**를 자식의 `start_date`로, 기존 **유효기간**을 자식의 `end_date`로 구성한다.
  - 기존 쿠폰의 할인 혜택·비고·쿠폰 이미지도 해당 자식으로 이관한다.
  - 기존 쿠폰을 이미 다운로드한 유저의 저장 상태는 부모 기준으로 유지되어, 마이그레이션 이후에도 만료되지 않는다.
