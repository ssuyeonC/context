# 세부 기획안 요구사항 문서 — 트래볼루션(Bank of Trip) API 연동 · 작업 티켓 분해

> 상세 API 규격·실측값은 마스터 스펙 문서 참고: `outputs/jira/reservation/[260723] travolution-api-integration.md`
> 본 문서는 개발 착수를 위한 **작업 단위(에픽 + 하위 티켓) 분해**이며, 각 티켓의 스코프·완료조건·선행의존을 정의

## 배경

### 문제 정의
- 트래볼루션(공급사, API 브랜드 **Bank of Trip**)이 B2B로 공급하는 티켓·예약 상품의 주문을 현재 **어드민에서 수동으로 확정·부킹** 처리 중
- 수동 처리로 크리에이트립 주문 생성 → 공급사 반영까지 **6시간~+1일 이상** 지연(공급사 실측), 즉시발권 상품도 실시간 바우처 불가, 예약 상품은 재고·마감 수동 관리로 오퍼레이션 부담
- 공급사가 API(v1.1.4) 연동을 제안·제공 → 주문 전달·확정·상태동기화 자동화로 리드타임 단축 및 공수 절감 (연동 진행 확정)

### 가설적 임팩트
- **운영 효율**: 수동 부킹 작업(연 약 300건 규모) 제거 → 운영 인력 시간 절감
- **전환율**: 즉시발권(TK) 상품 실시간 바우처 발급 → 구매 전환 개선
- **에러 감소**: 수동 입력 과정의 주문 누락·지연 등 휴먼 에러 제거
- **확장성**: 공급사 신규 어트랙션·체험 상품 지속 확대에도 추가 운영 부담 없이 대응

## 구현

### 유저 플로우

**작업 순서(롤아웃)**: Phase 1(공통 기반 + 즉시발권 TK) 우선 오픈 → Phase 2(예약 BK) 확장. 과도기엔 자동·수동 주문 공존, 미매핑 상품은 기존 수동 유지

**① 티켓(TK · 즉시발권) 구매 흐름**
- 유저가 TK 상품 구매·결제 완료
- 결제 완료 시 백엔드가 공급사 주문 생성 자동 호출 → **즉시 확정, 실시간 바우처 발급·전달**
- 유저 취소 요청 시 공급사 주문 취소 자동 연동

**② 예약(BK) 구매 흐름**
- 유저가 예약 상품 조회 시 **예약 가능 날짜·시간(재고)** 노출
- 유저가 날짜·시간 선택 + **필수 추가정보 입력**(항목별 선택형/입력형) 후 결제
- 결제 완료 시 공급사 예약 주문 생성 → **승인 대기(PD)** 상태
- 공급사 승인/거절 결과를 웹훅으로 수신 → 승인 시 **확정 안내**, 거절 시 환불·CS 연계

**③ 상태 변경 수신(공통)**
- 사용 완료·복구, 전체/부분 취소를 웹훅으로 수신 → 크리에이트립 주문 상태 자동 반영

### 프론트엔드 요구사항

**[T6] (FE·Phase1) 티켓(TK) 실시간 바우처 노출**
- TK 상품 주문 완료 후, 발급된 바우처를 유저에게 **실시간 노출**
- 바우처 형식 분기 노출: 코드형(QR·바코드·핀번호) / 파일·링크형 / 코드 없는 수동처리(ONVL — 안내 문구로 대체)
- 완료 조건: 즉시발권 상품 결제 완료 시 바우처가 화면·발송 채널에 즉시 표시
- 선행: T3

**[T9] (FE·Phase2) 예약(BK) 날짜·추가정보 입력 UI + 상태 안내**
- 예약 상품 상세·구매 화면에 **날짜·시간 선택 UI** 추가 — 가용 슬롯·재고를 스케줄 조회 결과로 구성, **재고 소진 슬롯은 마감 처리**
- **필수 추가정보 입력 폼** — 항목별 응답 유형에 따라 렌더링 분기
  - 선택형(SEL): 공급사가 내려주는 선택지 목록에서 고르는 셀렉트박스
  - 입력형(IPU): 자유 입력창
  - 항목 성격 분기: 주문당 1회 공통 입력(BAC) / 여행자별 반복 입력(TRV)
- 예약 상태를 유저에게 명확히 안내: **승인 대기 → 확정**, 거절 시 안내
- 확정 리드타임 안내: 즉시확정 아닌 상품은 **"확정까지 최대 24시간 소요"** 등 표시
- 완료 조건: 예약 상품을 날짜·추가정보 입력까지 정상 주문 가능, 승인/거절 상태가 화면에 반영
- 선행: T7, T8

### 백엔드 요구사항

#### Phase 1 — 공통 기반 + 티켓(TK) 즉시발권

**[T1] API 클라이언트·인증·조회 연동**
- 공급사 API 클라이언트 모듈 구현(기존 외부 연동 패턴 준용)
- **인증**: `Authorization` 헤더에 인증 키 전달, **`Bearer` 접두어 없이 키 값만**(공급사 확정). 웹훅 수신 시엔 접두어 포함되므로 방향별 처리 구분
- **환경 분리(필수)**: baseURL(개발 `dev.bankoftrip.com` / 운영 `www.bankoftrip.com`), 인증 키, 웹훅 URL을 **환경설정으로 관리**(하드코딩 금지) → dev↔prod 전환이 설정 변경만으로 가능
- 조회 연동: 상품·옵션·가격/단위 조회
- **Rate limit 대응**: 분당 600회 한도, 초과 시 `HTTP 429`(`{"code":"INTERNAL_ERROR"}`) → **백오프·재시도** 처리
- 완료 조건: dev 환경에서 상품·옵션·가격 조회 정상 응답, 429 대비 재시도 동작 확인

**[T2] 상품 매핑 테이블 설계·구축**
- 공급사 **3단 UID(product / option / unit)** ↔ 크리에이트립 상품·옵션·요금 단위를 잇는 매핑 테이블 설계·구축
- 상품 유형(TK/BK)은 상품 조회 응답 `type`으로 확인 → 매핑엔 UID 대응만 보관(주문 생성 경로 저장 불필요, 생성은 단일 엔드포인트)
- 상품 추가·변경에 대비해 **데이터로 관리**(하드코딩 금지), 확장 용이하게
- ⚠️ **운영 매핑은 prod 상품 UID 기준으로 구축·검증** — dev 매핑(현재 18종)은 구조 파악용이며 운영과 상품 구성이 다를 수 있음
- 완료 조건: 크리에이트립 주문 → 공급사 3단 UID로 정확히 변환, 매핑 추가가 데이터 작업만으로 가능
- 선행: T1

> **[T2 설계 노트] 매핑 대응 구조 — 크리에이트립 데이터 모델 실측 (2026-08-13)**
>
> **주의**: 크리에이트립엔 spotItem과 별개인 "option" 엔티티가 없다 — **SpotItem = 테이블 `spot_options`** (엔티티명만 SpotItem, FK `option_code`). SpotItem은 자기참조 부모-자식(`p_code`)으로 중첩. 예약이 실제 잡는 최소 단위 = `ReservedItem.option_code`(=리프 SpotItem), 여기에 `price`/`settlement_price`가 붙는다.
>
> **3단 UID 대응**:
> | 트래볼루션 | 크리에이트립 |
> |---|---|
> | product (상품) | **Spot** |
> | option (옵션 그룹) | **SpotItem 부모**(`p_code` 상위 노드) |
> | unit (요금·좌석 단위, B2B/B2C 가격) | **SpotItem 리프**(`price` 있는 예약 단위) |
>
> → 트래볼루션 option·unit은 **둘 다 SpotItem(`spot_options`)** 에 떨어진다(별도 option 엔티티 없음). 크리에이트립 스팟마다 중첩 깊이가 달라(평면 1단 vs 옵션→단위 2단), option+unit이 리프 하나로 합쳐질 수도·부모+자식 2단으로 갈릴 수도 있음.
> - **매핑 1:1 키 = 트래볼루션 unit UID ↔ 크리에이트립 리프 SpotItem**(가격·예약이 붙는 단위). product·option은 그룹핑 맥락.
> - **선례**: 기프티콘 연동 `spot_item_gifcon_mapping` 도 **권종 단위 SpotItem마다 공급사 코드 1:1** 매핑(face_value도 SpotItem에 부착) → 트래볼루션도 동일 패턴.
>
> **운영 흐름 (확정 모델)**: 트래볼루션이 상품+UID 코드 전달 → 운영이 relay·등록 → 시스템 API 자동 예약. **product UID 하나만 알면 option·unit은 API로 목록 자동 조회**(`GET options`/`GET units`) 가능 → 운영은 "이 스팟 = 트래볼루션 product 몇 번"만, 시스템이 하위 목록 끌어와 매칭. **등록 방식 확정: 운영이 개발자에게 상품 등록 요청 → 개발이 DB 등록**(어드민 셀프입력 UI 미구축). 신규 상품 추가 빈도가 높지 않아 개발 데이터옵스로 충분.

**[T3] 주문 생성 (TK) + 바우처 발급**
- TK 상품: 가격/단위 확인 후 주문 생성 호출 → **즉시 확정**, 응답의 바우처 정보로 발급 트리거
- 주문 생성 시 크리에이트립 주문번호를 참조번호(referenceNumber, 최대 64자)로 전달 → 웹훅·조회 매칭 키
- 바우처 구조 분기 처리: 코드형(주문당 1코드 / unit당 1코드) / 파일·예약번호형 / **코드·파일 없는 수동처리(ONVL)** — ONVL 상품(예: 난타)은 자동발권 예외로 별도 처리
- 바우처 발송 정책: **크리에이트립 자체 발송(`voucherSendType=0`) 확정** — 로고·브랜딩 요구 때문에 공급사 직발송 불가(직발송은 Bank of Trip 브랜딩). 아래 설계 노트 참고.
- 완료 조건: dev에서 TK 주문 생성 시 바우처가 즉시 응답에 포함되어 발급까지 연결
- 선행: T1, T2

> **[T3 설계 노트] 바우처 자동 발송 — 현행 실측 기반 (2026-08-13 조사)**
>
> **현행 상태 (BigQuery·PDF 실측)**: 트래볼루션(파트너 code 69)은 바우처 템플릿 253개, 발급 바우처 IMAGE 8,664 + TEXT 7. **거의 전부 `is_custom_generated`/`is_pre_purchased`/`is_external_generated` 플래그 0 + `docs_gen_template_slug` 없음** = 자동 생성 로직이 안 붙은 **수동 사전재고 IMAGE(PDF)** 모델. 발급 시 `voucher.service.ts:copyVoucherImageToReservationDirectory`로 재고 PDF를 예약 폴더(`reservations/{id}/voucher/*.pdf`)에 복사.
> **현행 바우처 실물**: **크리에이트립 로고(초록 워드마크) 박힌 PDF** + "QR Ticket / Confirm Number" 섹션에 QR + PASS Number. **QR 디코딩 결과 = 트래볼루션 주문번호 `TV...`(순수 텍스트) = API `orderNumber`** (예: `TV2668626101`). `voucherCode`가 아님. 하단 푸터는 공급사 CS(`cs@bankoftrip.com`)·`© TRAVOLUTION` 혼합. → **로고 요구는 이미 충족**돼 있으나 **PDF를 사람이 수동 생성·업로드**하는 구조.
>
> **자동화 설계**: 지금 사람이 콘솔에서 받아 손으로 넣던 TV번호를 **API `orderNumber`(주문 생성 응답)로 자동 주입** → 기존 크리에이트립 브랜딩 PDF 템플릿(로고·QR 로직 이미 존재) 자동 렌더 → `issueExternalVoucher`(IMAGE) 발급 → 예약 페이지 노출 + 확정 메일. **템플릿 신규 디자인 불필요, 재사용.**
> - **유일한 신규 빌드**: "API 데이터 → 브랜딩 PDF 자동 생성" 스텝 배선. 현재 이 PDF는 자동 파이프라인 밖(수동/외부 생성, docs-gen slug 없음)이라, docs-gen 템플릿 slug 신설 또는 barcode-voucher 로고오버레이(`reservation_barcode_voucher_issuance.logo_image_path`) 방식 중 택1로 자동화.
> - **유형별 범위**: TK = 주문 응답 즉시 완전 자동 / BK(현행 라이브 상품 전부) = 승인 웹훅(`BOOKING_ACCEPTED`→AC) 수신 후 자동 생성·발급.
> - **ONVL(코드·파일 없는 수동) 상품 = 현행 라이브 0건 (2026-08-13 전수 스캔 확인)**: 파트너 69 바우처 발급 실적이 있는 스팟(템플릿) **165개 전부 TV번호 QR 보유**(=API `orderNumber`). 난타(117)는 dev 테스트 상품일 뿐 라이브 아님. → 자동 QR 불가 예외는 **현재 없음**. 향후 ONVL형 상품이 신규로 붙을 때만 수동 예외 처리 검토(지금 결정 불필요).
> - **발송 채널**: 예약 페이지 노출 + 확정 메일 홀드-후-발송(`shouldHoldReservationMailUntilVoucherIssued`). **전용 바우처 카톡·SMS 채널 없음**(AREX 이벤트만 예외) — 별도 푸시 원하면 채널 신규 구축 필요.
>
> **공급사 확인 불필요 (닫힘)**: 로고·자체발송(`voucherSendType=0`)·QR값 전부 우리 쪽. QR 리딤값은 자체 디코딩으로 `orderNumber` 확정, 현행 운영에서 이미 스캔·검증됨. **잔여**: 신규 TK/QR 상품 리딤값(`orderNumber` vs `voucherCode`)은 상품 추가 시 API 응답 디코딩으로 건별 확인(공급사 문의 아님).

**[T4] 웹훅 수신 엔드포인트 + 멱등 처리**
- 공급사 → 크리에이트립 상태변경 통지를 수신하는 **HTTPS·JSON 엔드포인트** 구현, URL을 공급사에 등록·승인
- 수신 이벤트: 사용 완료(REDEEMED)·복구(RESTORED)·전체취소(CANCELED)·부분취소(PARTIAL_CANCELED) (예약 승인/거절은 T8)
- **보안**: `x-nonce`(일회성 난수) 기반 **중복 수신 방지(멱등)**, Authorization 토큰(옵션) 검증
- **최소 페이로드 대응**: 웹훅엔 상세가 없으므로 수신 즉시 **주문 재조회로 상세 상태 대사** 후 반영
- **재시도 보정**: 공급사는 웹훅 자동 재전송을 하지 않음(문서 확정) → 누락 대비 **주문 조회 폴링·대사** 설계
- 웹훅 수신 로깅(기존 웹훅 로깅 패턴 활용)
