# 세부 기획안 요구사항 문서 — 트래볼루션(Bank of Trip) API 연동 · 작업 티켓 분해

> 상세 API 규격·실측값은 마스터 스펙 문서 참고: `outputs/jira/reservation/[260723] travolution-api-integration.md`
> 본 문서는 개발 착수를 위한 **작업 단위(에픽 + 하위 티켓) 분해**이며, 각 티켓의 스코프·완료조건·선행의존을 정의

## 배경

### 문제 정의
- 트래볼루션(공급사, API 브랜드 **Bank of Trip**)이 B2B로 공급하는 티켓·예약 상품의 주문을 현재 **어드민에서 수동으로 확정·부킹** 처리 중
- 수동 처리로 크리에이트립 주문 생성 → 공급사 반영까지 **6시간~+1일 이상** 지연(공급사 실측), 즉시발권 상품도 실시간 바우처 불가, 예약 상품은 재고·마감 수동 관리로 오퍼레이션 부담
- 공급사가 API(v1.1.4) 연동을 제안·제공 → 주문 전달·확정·상태동기화 자동화로 리드타임 단축 및 공수 절감 (연동 진행 확정)

### 가설적 임팩트
- **운영 효율**: 수동 부킹 작업(연 약 300건 규모) 제거 → 운영 인력 시간 절감
- **전환율**: 즉시발권(TK) 상품 실시간 바우처 발급 → 구매 전환 개선
- **에러 감소**: 수동 입력 과정의 주문 누락·지연 등 휴먼 에러 제거
- **확장성**: 공급사 신규 어트랙션·체험 상품 지속 확대에도 추가 운영 부담 없이 대응

## 구현

### 유저 플로우

**작업 순서(롤아웃)**: Phase 1(공통 기반 + 즉시발권 TK) 우선 오픈 → Phase 2(예약 BK) 확장. 과도기엔 자동·수동 주문 공존, 미매핑 상품은 기존 수동 유지

**① 티켓(TK · 즉시발권) 구매 흐름**
- 유저가 TK 상품 구매·결제 완료
- 결제 완료 시 백엔드가 공급사 주문 생성 자동 호출 → **즉시 확정, 실시간 바우처 발급·전달**
- 유저 취소 요청 시 공급사 주문 취소 자동 연동

**② 예약(BK) 구매 흐름**
- 유저가 예약 상품 조회 시 **예약 가능 날짜·시간(재고)** 노출
- 유저가 날짜·시간 선택 + **필수 추가정보 입력**(항목별 선택형/입력형) 후 결제
- 결제 완료 시 공급사 예약 주문 생성 → **승인 대기(PD)** 상태
- 공급사 승인/거절 결과를 웹훅으로 수신 → 승인 시 **확정 안내**, 거절 시 환불·CS 연계

**③ 상태 변경 수신(공통)**
- 사용 완료·복구, 전체/부분 취소를 웹훅으로 수신 → 크리에이트립 주문 상태 자동 반영

### 프론트엔드 요구사항

**[T6] (FE·Phase1) 티켓(TK) 실시간 바우처 노출**
- TK 상품 주문 완료 후, 발급된 바우처를 유저에게 **실시간 노출**
- 바우처 형식 분기 노출: 코드형(QR·바코드·핀번호) / 파일·링크형 / 코드 없는 수동처리(ONVL — 안내 문구로 대체)
- 완료 조건: 즉시발권 상품 결제 완료 시 바우처가 화면·발송 채널에 즉시 표시
- 선행: T3

**[T9] (FE·Phase2) 예약(BK) 날짜·추가정보 입력 UI + 상태 안내**
- 예약 상품 상세·구매 화면에 **날짜·시간 선택 UI** 추가 — 가용 슬롯·재고를 스케줄 조회 결과로 구성, **재고 소진 슬롯은 마감 처리**
- **필수 추가정보 입력 폼** — 항목별 응답 유형에 따라 렌더링 분기
  - 선택형(SEL): 공급사가 내려주는 선택지 목록에서 고르는 셀렉트박스
  - 입력형(IPU): 자유 입력창
  - 항목 성격 분기: 주문당 1회 공통 입력(BAC) / 여행자별 반복 입력(TRV)
- 예약 상태를 유저에게 명확히 안내: **승인 대기 → 확정**, 거절 시 안내
- 확정 리드타임 안내: 즉시확정 아닌 상품은 **"확정까지 최대 24시간 소요"** 등 표시
- 완료 조건: 예약 상품을 날짜·추가정보 입력까지 정상 주문 가능, 승인/거절 상태가 화면에 반영
- 선행: T7, T8

### 백엔드 요구사항

#### Phase 1 — 공통 기반 + 티켓(TK) 즉시발권

**[T1] API 클라이언트·인증·조회 연동**
- 공급사 API 클라이언트 모듈 구현(기존 외부 연동 패턴 준용)
- **인증**: `Authorization` 헤더에 인증 키 전달, **`Bearer` 접두어 없이 키 값만**(공급사 확정). 웹훅 수신 시엔 접두어 포함되므로 방향별 처리 구분
- **환경 분리(필수)**: baseURL(개발 `dev.bankoftrip.com` / 운영 `www.bankoftrip.com`), 인증 키, 웹훅 URL을 **환경설정으로 관리**(하드코딩 금지) → dev↔prod 전환이 설정 변경만으로 가능
- 조회 연동: 상품·옵션·가격/단위 조회
- **Rate limit 대응**: 분당 600회 한도, 초과 시 `HTTP 429`(`{"code":"INTERNAL_ERROR"}`) → **백오프·재시도** 처리
- 완료 조건: dev 환경에서 상품·옵션·가격 조회 정상 응답, 429 대비 재시도 동작 확인

**[T2] 상품 매핑 테이블 설계·구축**
- 공급사 **3단 UID(product / option / unit)** ↔ 크리에이트립 상품·옵션·요금 단위를 잇는 매핑 테이블 설계·구축
- 상품 유형(TK/BK)은 상품 조회 응답 `type`으로 확인 → 매핑엔 UID 대응만 보관(주문 생성 경로 저장 불필요, 생성은 단일 엔드포인트)
- 상품 추가·변경에 대비해 **데이터로 관리**(하드코딩 금지), 확장 용이하게
- ⚠️ **운영 매핑은 prod 상품 UID 기준으로 구축·검증** — dev 매핑(현재 18종)은 구조 파악용이며 운영과 상품 구성이 다를 수 있음
- 완료 조건: 크리에이트립 주문 → 공급사 3단 UID로 정확히 변환, 매핑 추가가 데이터 작업만으로 가능
- 선행: T1

**[T3] 주문 생성 (TK) + 바우처 발급**
- TK 상품: 가격/단위 확인 후 주문 생성 호출 → **즉시 확정**, 응답의 바우처 정보로 발급 트리거
- 주문 생성 시 크리에이트립 주문번호를 참조번호(referenceNumber, 최대 64자)로 전달 → 웹훅·조회 매칭 키
- 바우처 구조 분기 처리: 코드형(주문당 1코드 / unit당 1코드) / 파일·예약번호형 / **코드·파일 없는 수동처리(ONVL)** — ONVL 상품(예: 난타)은 자동발권 예외로 별도 처리
- 바우처 발송 정책 반영: 공급사 직발송 vs 크리에이트립 자체 발송(발송 파라미터 지정) — {정책 결정 TBD, 아래 미결 참고}
- 완료 조건: dev에서 TK 주문 생성 시 바우처가 즉시 응답에 포함되어 발급까지 연결
- 선행: T1, T2

**[T4] 웹훅 수신 엔드포인트 + 멱등 처리**
- 공급사 → 크리에이트립 상태변경 통지를 수신하는 **HTTPS·JSON 엔드포인트** 구현, URL을 공급사에 등록·승인
- 수신 이벤트: 사용 완료(REDEEMED)·복구(RESTORED)·전체취소(CANCELED)·부분취소(PARTIAL_CANCELED) (예약 승인/거절은 T8)
- **보안**: `x-nonce`(일회성 난수) 기반 **중복 수신 방지(멱등)**, Authorization 토큰(옵션) 검증
- **최소 페이로드 대응**: 웹훅엔 상세가 없으므로 수신 즉시 **주문 재조회로 상세 상태 대사** 후 반영
- **재시도 보정**: 공급사는 웹훅 자동 재전송을 하지 않음(문서 확정) → 누락 대비 **주문 조회 폴링·대사** 설계
- 웹훅 수신 로깅(기존 웹훅 로깅 패턴 활용)
- 완료 조건: dev에서 웹훅 수신 시 중복 이벤트가 1회만 처리, 재조회 대사로 주문 상태 정확히 반영 (로컬 테스트는 ngrok 등 활용)
- 선행: T1

**[T5] 주문 취소 연동 + 취소 불가 처리**
- 크리에이트립발 취소 시 공급사 주문 취소 호출(**주문 전체 단위만** — 부분취소 API 미지원, 공급사 확정)
- 취소 불가 조건 에러 처리: 주문없음/만료/사용됨/이미취소됨/취소불가/코레일패스오류 → 각 케이스별 유저·어드민 처리 흐름 정의
- **부분환불(부분취소)**: API 미지원 → **양사 오퍼레이션팀 커뮤니케이션으로 처리**(가격·재고 문제없으면 전체취소 후 재주문 / 재주문 어려우면 당일 사용완료 후 부분취소 상태 변경). 어드민 수동 플로우로 설계, `PARTIAL_CANCELED` 웹훅으로 결과 수신
- 완료 조건: dev에서 전체취소 정상 연동, 취소 불가 케이스가 에러 기준으로 분기 처리
- 선행: T3

**[T6] (FE) — 프론트엔드 요구사항 참고**

#### Phase 2 — 예약(BK) 확장

**[T7] BK 스케줄·재고·추가정보 조회 연동**
- **스케줄·재고 조회**: 옵션별 예약 가능 날짜·시간·실시간 재고 조회(날짜 필터 지원), 스케줄 없음 응답(404) 처리
- **필수 추가정보 조회**: 옵션의 추가정보 항목 목록 조회 → 항목별 유형(BAC/TRV)·응답유형(SEL/IPU)·선택지 파악
- 완료 조건: BK 상품의 가용 슬롯·재고와 추가정보 항목을 조회해 프론트에 전달 가능
- 선행: T1, T2

**[T8] 주문 생성 (BK) + 예약 승인/거절 웹훅 상태 반영**
- BK 상품: 스케줄·추가정보 확인 후 주문 생성(예약일시·추가정보 포함) → **생성 직후 승인 대기(PD)** 로 보류
- 재고 부족·마감 에러 처리(재고부족/스케줄재고부족/스케줄마감) → 유저·어드민 흐름 정의
- 예약 승인(BOOKING_ACCEPTED → 확정 AC) / 거절(BOOKING_REJECTED → RJ, 환불·CS 연계) 웹훅 수신·상태 반영
- 기존 **수동 부킹 상태 모델과 정합**(자동·수동 주문 공존 과도기 고려)
- 완료 조건: dev에서 BK 주문이 PD로 생성되고 승인/거절 웹훅에 따라 상태가 AC/RJ로 전환
- 선행: T4, T7

**[T9] (FE) — 프론트엔드 요구사항 참고**

#### 공통

**[T10] 폴백(수동 처리) 경로 + 에러 모니터링**
- 연동 실패(호출 오류·타임아웃·거절) 시 **폴백(수동 처리) 경로 유지** — 자동 전환 상품도 예외 건은 어드민 확인·개입 가능
- 자동 연동 주문과 기존 수동 주문의 **상태 모델 통합** 방식 반영
- 에러 리포팅·알림(기존 Sentry·Slack 패턴 활용): 주문 생성 실패 시 운영팀 알림
- 완료 조건: 연동 실패 케이스가 어드민에 노출되고 수동 처리로 폴백
