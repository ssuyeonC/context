# 세부 기획안 요구사항 문서

## 배경

### 문제 정의

- 사용자가 예약일 변경을 요청한 뒤, 파트너·관리자의 응답을 기다리는 **진행 중** 상태에서 요청을 스스로 되돌릴 **철회 수단이 부재**
- 잘못 보냈거나 마음이 바뀐 요청도 상대의 승낙·거절을 기다리거나 CX 문의로만 취소 가능 → 불필요한 응답 대기·오처리 유발
- 기존 철회 기능은 **관리자·파트너가 본인이 보낸 요청**을 되돌리는 범위로만 구축(참조: `[260803] date-change-request-modification-history.md`) — **사용자 발(發) 요청은 철회 대상에서 제외**되어 사용자 셀프 철회 경로가 비어 있음
- 마이페이지 예약 카드에는 예약 변경 요청 진입점이 노출되지 않아, 사용자가 변경을 원할 때 접근 경로가 불명확 — 변경 요청·철회 모두 발견성 낮음

### 가설적 임팩트

- 사용자가 진행 중 변경 요청을 즉시 셀프 철회 가능 → 불필요한 응답 대기·CX 취소 문의 감소 기대
- 마이페이지 예약 카드에 변경 요청·철회 진입점을 상시 노출 → 예약 변경 기능 발견성 제고
- 상태 전환·발송 없이 진행 플래그만 해제하는 구조라 예약·매출 등 전환 지표에 영향 없음

## 구현

### 유저 플로우

진입점(마이페이지 예약 카드) 관점:

- 사용자는 마이페이지 예약 화면의 각 예약 카드에서 **'Mark As Finished'** 버튼 아래에 노출되는 **예약 변경** 버튼으로 예약일 변경 기능에 접근
- 사용자가 해당 예약에 대해 **진행 중인 본인 발 변경 요청이 없는** 상태 → 버튼은 **예약 변경**으로 노출, 클릭 시 기존 유저 예약일 변경 요청 화면(플로우)으로 진입
- 사용자가 해당 예약에 대해 **진행 중인 본인 발 변경 요청이 있는** 상태 → 동일 버튼이 **예약 변경 취소**로 전환 노출, 클릭 시 해당 요청을 철회
- 버튼은 예약 변경 요청이 가능한 모든 예약 상태(확정·결제완료 등)에서 노출 — 변경 요청 자체가 불가한 상태(취소·환불·이용완료 등)에서는 미노출
- 한 예약 카드에는 시점에 따라 **예약 변경** 또는 **예약 변경 취소** 중 하나만 노출 — 진행 중 요청 유무로 라벨·동작 결정

철회 동작 관점:

- 사용자는 사용자 본인이 **직접 보낸 진행 중 변경 요청**만 이 버튼으로 철회 가능
- 관리자·파트너가 보낸 요청, 이메일 링크 등 다른 경로 요청은 이 버튼의 철회 대상 아님 — 본인이 직접 보낸 진행 중 요청 1건에 한정
- 철회 시 예약의 변경 요청 **진행 상태만 해제(요청 없던 상태로 복귀)** → 사용자는 새 변경 요청을 즉시 다시 요청 가능
- 진행 상태를 별도 '철회됨' 상태로 남기지 않음 — 사용자 셀프 철회는 쿨다운·거절 흔적 등 후속 로직이 없어 진행 플래그를 비우는 것으로 충분(기존 관리자·파트너 철회 로직과 대칭)
- 철회 시 상대(파트너·관리자/CX)에게 별도 알림 발송 없음 — 진행 플래그 해제까지만 수행
- 철회 직후 동일 카드의 버튼은 **예약 변경**으로 즉시 되돌아가 재요청 진입 가능

기록 관점:

- 사용자가 마이페이지 진입점 등으로 예약일 변경을 요청 → 예약의 최근 수정내역·요청 이력에 **예약일 변경 요청**으로 기록, 수정자 **사용자**
- 사용자 셀프 철회도 예약의 최근 수정내역·요청 이력에 **예약일 변경 요청 철회**로 기록, 수정자 **사용자**
- 진행 상태값을 비워도 철회 사실 기록은 별개로 보존 — '요청 없던 상태로 복귀'는 진행 플래그에 한정되며 데이터 삭제가 아님
- 요청 이력 record는 철회 종료로 표시(응답 대기 해제)하되 삭제하지 않음
- 수정자 태그·수정 내용 문구 체계는 기존 철회 이력 규칙(`[260803]`)을 그대로 따름 — 사용자 발 철회는 수정자 **사용자**(하늘색) 태그로 노출

예외·범위:

- 철회 가능 조건 — 요청이 아직 진행 중(적용·거절·철회 전)인 상태에 한해 철회 허용, 이미 적용·거절·철회된 요청은 철회 불가
- 진행 중 요청이 철회 불가 상태로 넘어간 직후 사용자가 **예약 변경 취소**를 눌렀을 때 → **이미 변경이 완료되어 취소할 수 없습니다.** 안내 노출 후 화면 새로고침으로 버튼을 최신 상태로 갱신
- 관리자·파트너 발 요청에 대한 사용자 측 대응(승낙·거절)은 기존 플로우 유지 — 이번 범위 밖

### 프론트엔드 요구사항

- 마이페이지 예약 카드 **'Mark As Finished'** 버튼 아래에 예약 변경 진입 버튼 신설
- 버튼 라벨·동작은 해당 예약의 진행 중 본인 발 변경 요청 유무로 분기
  - 진행 중 요청 없음 → **예약 변경** (클릭 시 기존 유저 예약일 변경 요청 화면으로 이동)
  - 진행 중 요청 있음 → **예약 변경 취소** (클릭 시 철회 처리)
- 예약 변경 요청 가능 상태(확정·결제완료 등)에서만 버튼 노출, 그 외 상태에서는 버튼 미노출
- **예약 변경 취소** 클릭 시 재확인 모달 노출 — **변경 요청을 취소하시겠습니까?** 문구, 확인 시 철회 처리·취소 시 모달 종료
- 철회 완료 후 별도 페이지 이동 없이 카드 내 버튼을 **예약 변경**으로 갱신
- 이미 처리된 요청을 철회 시도한 경우 **이미 변경이 완료되어 취소할 수 없습니다.** 안내 노출 후 화면 새로고침으로 최신 상태 반영
- 카드 컴포넌트 재사용 — 기존 'Mark As Finished' 버튼 영역 하단에 버튼 1개 추가 배치, 두 라벨은 동일 버튼 위치에서 상태별로 교체

### 백엔드 요구사항

- 예약 카드(마이페이지 예약 목록/상세) 응답에 해당 예약의 **진행 중 본인 발 변경 요청 유무** 판별값 포함 — 프론트 버튼 라벨·동작 분기에 사용
- 판별은 예약의 **현재 활성 변경 요청 사이클** 기준 + **요청 주체=사용자** + **요청 경로=사용자 직접 요청**으로 스코핑 — 과거 종료 사이클, 관리자·파트너 발 요청, 타 경로 요청이 오탐되지 않도록 방어
- 사용자 예약일 변경 요청 생성 시 최근 수정내역·요청 이력 기록 발생, 수정자 유형을 사용자로 지정(기존 수정 내용 유형 **예약일 변경 요청** 재사용, 마이페이지 진입점 포함 사용자 직접 요청 경로 전체에 적용)
- 사용자 셀프 철회 처리 신규 구축
  - 사용자 본인이 직접 보낸 진행 중 변경 요청을 철회하는 처리 신설
  - 철회 시 예약의 변경 요청 진행 상태(진행 중 플래그)를 해제(요청 없던 상태로 복귀) → 재요청 가능. 별도 '철회됨' 잔존 상태로 남기지 않음
  - 본인이 직접 보낸 요청만 철회 가능하도록 권한·소유 검증 — 다른 주체·다른 경로 요청 철회 차단
  - 철회 처리 시 최근 수정내역·요청 이력 기록 발생, 수정자 유형을 사용자로 지정(기존 철회 유형 **예약일 변경 요청 철회** 재사용)
  - 요청 이력 record는 철회 종료로 표시하되 삭제하지 않음
  - 이미 적용·거절·철회된 요청에 대한 철회 요청은 거부하고 현재 상태 반환(동시성·중복 클릭 방어)
- 철회 시 상대측 알림·메일·Slack 발송 없음 — 진행 플래그 해제 및 이력 적재까지만 수행(관리자·파트너 철회는 유저 안내 메일을 보내지만, 사용자 셀프 철회는 발송 대상 부재로 미발송)
- 기존 유저 예약일 변경 요청 API·플로우는 변경 없이 재사용 — 마이페이지 버튼은 해당 진입점만 추가
