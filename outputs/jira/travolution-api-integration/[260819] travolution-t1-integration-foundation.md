# 세부 기획안 요구사항 문서 — [T1] 트래볼루션 API 연동 기반 구축

> 에픽 `[260819] travolution-api-integration-epic.md` 하위 T1. 후속 T2~T4가 올라설 공통 기반(API 클라이언트·웹훅 수신·매핑).

## 배경

### 문제 정의
- 트래볼루션(공급사, API 브랜드 Bank of Trip)이 공급하는 티켓·예약 상품을 현재 **어드민이 공급사 콘솔에 수동 부킹** 처리, 반영까지 6시간~+1일 지연
- 자동화를 위한 **API 호출·웹훅 수신·상품 매핑의 공통 기반**이 없으면 주문/예약/취소 자동화(T2~T4)를 시작할 수 없음
- 공급사 API(v1.1.4) 연동으로 이 기반을 구축

### 가설적 임팩트
- 기반 자체는 직접 지표 임팩트 없음 — **후속 자동화의 선행 조건**
- 이 기반 위에서 수동 부킹(연 약 300건 규모) 제거·즉시발권 실시간 바우처가 가능해짐

## 구현

### 유저 플로우
- 해당 없음 — 유저 노출 변화 없는 백엔드 기반 작업

### 프론트엔드 요구사항
- 해당 없음

### 백엔드 요구사항

**① API 클라이언트·인증·조회**
- 공급사 API 클라이언트 모듈 구현(기존 외부 연동 패턴 준용)
- 인증 — `Authorization` 헤더에 인증 키 전달, **`Bearer` 접두어 없이 키 값만**(공급사 확정). 웹훅 수신은 접두어 포함이라 방향별 구분
- 환경 분리 — baseURL(dev `dev.bankoftrip.com` / prod `www.bankoftrip.com`)·인증 키·웹훅 URL을 **환경설정으로 관리**(하드코딩 금지)
- 조회 연동 — 상품·옵션·가격/단위 조회
- Rate limit 대응 — 분당 600회, 초과 시 `HTTP 429` → **백오프·재시도**

**② 웹훅 수신 엔드포인트 + 멱등·대사 + 사용/취소 상태 반영**
- 공급사 → 크리에이트립 상태변경 통지를 받는 **HTTPS·JSON 엔드포인트** 구현
- **dev 웹훅 URL을 공급사에 메일 등록**(`dev@bankoftrip.com`, 영업일 1일 이내 반영)
- 보안 — `x-nonce`(일회성 난수) 기반 **중복 수신 방지(멱등)**, Authorization 토큰(옵션) 검증
- 최소 페이로드 대응 — 수신 즉시 **주문 재조회로 상세 대사** 후 반영 (공급사 웹훅 자동 재전송 없음 → 폴링·대사로 누락 보정)
- 사용/취소 이벤트 반영 — 사용완료(REDEEMED → 사용완료 AP)·복구(RESTORED → 미사용)·전체취소(CANCELED)·부분취소(PARTIAL_CANCELED) (예약 승인/거절은 T3)
- 웹훅 수신 로깅(기존 패턴 활용)

**③ 매핑 테이블 설계·구축 + dev 매핑 등록**
- 공급사 **3단 UID(product/option/unit)** ↔ 크리에이트립 상품·옵션·요금 단위 매핑 테이블 설계·구축
- 매핑 앵커 — **트래볼루션 unit UID ↔ 크리에이트립 리프 SpotItem**(가격·예약이 붙는 단위), product·option은 그룹핑 맥락 (자리 고정 매핑 아님, 노드별 리프 판정)
- 상품 유형(TK/BK)은 조회 응답 `type`으로 확인 → 매핑엔 UID 대응만 보관
- 상품 추가·변경 대비 **데이터로 관리**(하드코딩 금지)
- dev 연동 가능 상품 매핑 등록 (prod 매핑은 T6에서 UID 재검증 후)

**③-1 상품 설정 정합 (TK/BK)**
- 크리에이트립엔 TK/BK 단일 플래그 없음 → `spot_options`의 `is_reserve`·`is_use_item_schedule`·`is_auto_reservable`·`is_voucher_auto_issued` 조합으로 동작 결정
- **현행 실측(2026-08-19)**: 트래볼루션 245개 스팟 전량 `is_auto_reservable=0`(수동 확정), `is_voucher_auto_issued=1`은 7개뿐 = 전부 수동 처리 상태
- 매핑 시 트래볼루션 `type`에 맞게 정합 — **TK(즉시발권)=즉시 확정 + 바우처 자동발급** / **BK(예약)=예약형 유지, 승인 웹훅(PD→AC)으로 확정**
- 유형↔상품설정 불일치 시 유저 화면·실제 처리가 어긋남 → 매핑 등록 시 확인
- ※ 자동화가 기존 플래그를 그대로 쓸지 vs 매핑+API `type` 기반 신규 경로로 처리할지는 구현 시 결정

**완료조건**
- dev에서 상품·옵션·가격 조회 정상 응답(429 재시도 동작)
- 웹훅 중복 이벤트 1회만 처리·재조회 대사로 상태 반영(로컬은 ngrok)
- 크리에이트립 주문 → 공급사 3단 UID 정확 변환, 매핑 추가가 데이터 작업만으로 가능

### [참고] 매핑 대응 구조 — 크리에이트립 데이터 모델 실측 (2026-08-13)
- **SpotItem = 테이블 `spot_options`**(엔티티명만 SpotItem, FK `option_code`). 자기참조 부모-자식(`p_code`)으로 중첩. 예약 최소 단위 = `ReservedItem.option_code`(=리프 SpotItem), 여기에 `price`/`settlement_price` 부착
- 3단 UID 대응: **product↔Spot / option↔SpotItem 부모 / unit↔SpotItem 리프**(가격 있는 예약 단위). option·unit은 둘 다 `spot_options`에 떨어짐
- 매핑 1:1 키 = **트래볼루션 unit UID ↔ 크리에이트립 리프 SpotItem**. 선례: 기프티콘 `spot_item_gifcon_mapping`도 권종 단위 SpotItem마다 공급사 코드 1:1
- 깊이 실측(prod 245개, `partnership_code=69`): 상품에서 끝남 155개(63%) / 옵션까지 82개(33%) / 하위옵션까지 8개(3%). 리프 총 842개. 한 스팟 안에서도 리프 깊이 혼재 → **노드별 리프 판정**으로 unit 매핑
- 운영 흐름: 트래볼루션이 상품+UID 전달 → 운영이 개발자에 등록 요청 → **개발이 DB 등록**. product UID만 알면 option·unit은 API 목록 자동 조회
