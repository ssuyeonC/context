## 0단계 — 기반 구축

### [T1] 연동 기반 구축 — API 클라이언트 + 웹훅 수신 + 매핑 테이블 (BE)
> 연동의 3개 기반 영역. 서로 독립이라 병렬 진행 가능하며, 규모가 크면 ①API 클라이언트 / ②웹훅 수신 / ③매핑 서브태스크로 쪼갤 수 있음

**① API 클라이언트·인증·조회**
- 공급사 API 클라이언트 모듈 구현(기존 외부 연동 패턴 준용)
- 인증 — `Authorization` 헤더에 인증 키 전달, **`Bearer` 접두어 없이 키 값만**(공급사 확정). 웹훅 수신은 접두어 포함이므로 방향별 구분
- 환경 분리 — baseURL(dev `dev.bankoftrip.com` / prod `www.bankoftrip.com`)·인증 키·웹훅 URL을 **환경설정으로 관리**(하드코딩 금지)
- 조회 연동 — 상품·옵션·가격/단위 조회
- Rate limit 대응 — 분당 600회, 초과 시 `HTTP 429` → **백오프·재시도**

**② 웹훅 수신 엔드포인트 + 멱등·대사 + 사용/취소 상태 반영**
- 공급사 → 크리에이트립 상태변경 통지를 받는 **HTTPS·JSON 엔드포인트** 구현
- **dev 웹훅 URL을 공급사에 메일 등록**(`dev@bankoftrip.com`, 영업일 1일 이내 반영)
- 보안 — `x-nonce`(일회성 난수) 기반 **중복 수신 방지(멱등)**, Authorization 토큰(옵션) 검증
- 최소 페이로드 대응 — 수신 즉시 **주문 재조회로 상세 대사** 후 반영 (공급사 웹훅 자동 재전송 없음 → 폴링·대사로 누락 보정)
- 사용/취소 이벤트 상태 반영 — 사용완료(REDEEMED → 사용완료 AP)·복구(RESTORED → 미사용)·전체취소(CANCELED)·부분취소(PARTIAL_CANCELED) (예약 승인/거절은 T3)
- 웹훅 수신 로깅(기존 패턴 활용)

**③ 매핑 테이블 설계·구축 + dev 매핑 등록**
- 공급사 **3단 UID(product/option/unit)** ↔ 크리에이트립 상품·옵션·요금 단위 매핑 테이블 설계·구축
- 매핑 앵커 — **트래볼루션 unit UID ↔ 크리에이트립 리프 SpotItem**(가격·예약이 붙는 단위), product·option은 그룹핑 맥락 (자리 고정 매핑 아님, 노드별 리프 판정)
- 상품 유형(TK/BK)은 조회 응답 `type`으로 확인 → 매핑엔 UID 대응만 보관
- 상품 추가·변경 대비 **데이터로 관리**(하드코딩 금지)
- dev 연동 가능 상품 매핑 등록 (prod 매핑은 T6에서 UID 재검증 후)
- **상품 설정 정합(TK/BK)** — 크리에이트립엔 TK/BK 단일 플래그가 없고 `spot_options`의 `is_reserve`·`is_use_item_schedule`·`is_auto_reservable`·`is_voucher_auto_issued` 조합으로 동작이 결정됨. **현행 실측(2026-08-19): 트래볼루션 245개 스팟 전량 `is_auto_reservable=0`(수동 확정), `is_voucher_auto_issued=1`은 7개뿐** = 전부 수동 처리 상태. 매핑 시 트래볼루션 `type`에 맞게 정합:
  - **TK(즉시발권)** → 즉시 확정 + 바우처 자동발급 경로로 설정
  - **BK(예약)** → 예약형 유지, 자동확정 대신 승인 웹훅(PD→AC)으로 확정
  - 유형과 상품 설정이 어긋나면 유저 화면·실제 처리가 불일치 → 매핑 등록 시 반드시 확인
  - ※ 자동화가 기존 플래그를 그대로 쓸지(플래그 세팅) vs 매핑+API `type` 기반 신규 경로로 처리할지는 T1 구현 시 결정

**완료조건**: dev에서 상품·옵션·가격 조회 정상 응답(429 재시도 동작) · 웹훅 중복 이벤트 1회만 처리·재조회 대사로 상태 반영(로컬은 ngrok) · 크리에이트립 주문 → 공급사 3단 UID 정확 변환, 매핑 추가가 데이터 작업만으로 가능

> **[T1-③ 설계 노트] 매핑 대응 구조 — 크리에이트립 데이터 모델 실측 (2026-08-13)**
>
> **주의**: 크리에이트립엔 SpotItem과 별개인 "option" 엔티티가 없다 — **SpotItem = 테이블 `spot_options`**(엔티티명만 SpotItem, FK `option_code`). SpotItem은 자기참조 부모-자식(`p_code`)으로 중첩. 예약이 실제 잡는 최소 단위 = `ReservedItem.option_code`(=리프 SpotItem), 여기에 `price`/`settlement_price`가 붙는다.
>
> **3단 UID 대응**:
> | 트래볼루션 | 크리에이트립 |
> |---|---|
> | product (상품) | **Spot** |
> | option (옵션 그룹) | **SpotItem 부모**(`p_code` 상위 노드) |
> | unit (요금·좌석 단위, B2B/B2C 가격) | **SpotItem 리프**(`price` 있는 예약 단위) |
>
> → 트래볼루션 option·unit은 **둘 다 SpotItem(`spot_options`)** 에 떨어진다(별도 option 엔티티 없음). 크리에이트립 스팟마다 중첩 깊이가 달라 option+unit이 리프 하나로 합쳐질 수도·부모+자식 2단으로 갈릴 수도 있음.
> - **매핑 1:1 키 = 트래볼루션 unit UID ↔ 크리에이트립 리프 SpotItem**(가격·예약이 붙는 단위). product·option은 그룹핑 맥락.
> - **선례**: 기프티콘 연동 `spot_item_gifcon_mapping` 도 권종 단위 SpotItem마다 공급사 코드 1:1 매핑(face_value도 SpotItem에 부착) → 트래볼루션도 동일 패턴.
> - **깊이 실측(prod 245개, `spot.partnership_code=69`, 2026-08-19)**: 상품에서 끝남 155개(63%) / 옵션까지 82개(33%) / 하위옵션까지 8개(3%). 리프 총 842개. 한 스팟 안에서도 리프 깊이가 섞임(리프 보유 164 > 최대깊이1 155) → **노드별 리프 판정**으로 unit 매핑.
>
> **운영 흐름 (확정)**: 트래볼루션이 상품+UID 코드 전달 → 운영이 개발자에게 등록 요청 → **개발이 DB 등록**(어드민 셀프입력 UI 미구축). product UID 하나만 알면 option·unit은 API 목록 자동 조회(`GET options`/`GET units`) 가능 → 운영은 "이 스팟 = 트래볼루션 product 몇 번"만 제공.

## 1단계 — 핵심 구현

### [T2] 주문 생성(TK) + 바우처 + 취소 연동 (BE) · 선행 T1
**주문 생성(TK) + 바우처 자동 발급**
- TK 상품 — 가격/단위 확인 후 주문 생성 호출 → **즉시 확정**, 응답 바우처 정보로 발급 트리거
- 주문 생성 시 크리에이트립 주문번호를 참조번호(referenceNumber, 최대 64자)로 전달 → 웹훅·조회 매칭 키
- 바우처 자동 발급 — 주문 응답 `orderNumber`(TV번호) 자동 주입 → **기존 크리에이트립 브랜딩 PDF 템플릿 자동 렌더**(로고·QR 로직 재사용, 신규 디자인 불필요) → 예약 페이지 노출 + 확정 메일
- 발송 정책 — **크리에이트립 자체 발송(`voucherSendType=0`)** (공급사 직발송은 Bank of Trip 브랜딩이라 불가)
- 바우처 구조 분기 — 코드형(주문당 1코드 / unit당 1코드) / 파일·예약번호형. **코드·파일 없는 수동(ONVL)형은 현행 라이브 0건이라 예외 처리 불필요**

**주문 취소 연동 (TK·BK 공통)**
- 크리에이트립발 취소 시 공급사 주문 취소 호출(**주문 전체 단위만** — 부분취소 API 미지원, 공급사 확정)
- 취소 불가 조건 에러 분기 — 주문없음/만료/사용됨/이미취소됨/취소불가/코레일패스오류 → 케이스별 유저·어드민 처리
- **부분환불/부분취소** — API 미지원 → **양사 오퍼레이션팀 커뮤니케이션으로 처리**(현행 유지, 운영팀 확인 완료 2026-08-18). 결과는 `PARTIAL_CANCELED` 웹훅으로 수신(T1 웹훅). 자동화 대상 아님

- **완료조건**: dev에서 TK 주문 생성 시 바우처 즉시 발급까지 연결 · 전체취소 정상 연동, 취소 불가 케이스가 에러 기준으로 분기 처리

> **[T2 설계 노트] 바우처 자동 발송 — 현행 실측 기반 (2026-08-13 조사)**
>
> **현행 상태(BigQuery·PDF 실측)**: 트래볼루션(파트너 code 69)은 바우처 템플릿 253개, 발급 바우처 IMAGE 8,664 + TEXT 7. 거의 전부 자동 생성 플래그 0 + `docs_gen_template_slug` 없음 = **자동 생성 로직이 안 붙은 수동 사전재고 IMAGE(PDF)** 모델. 발급 시 재고 PDF를 예약 폴더(`reservations/{id}/voucher/*.pdf`)에 복사.
> **현행 바우처 실물**: **크리에이트립 로고(초록 워드마크) 박힌 PDF** + QR + PASS Number. **QR 디코딩 결과 = 트래볼루션 주문번호 `TV...`(순수 텍스트) = API `orderNumber`**(예: `TV2668626101`, `voucherCode` 아님). → **로고 요구는 이미 충족**돼 있으나 PDF를 사람이 수동 생성·업로드하는 구조.
>
> **자동화 설계**: 사람이 콘솔에서 받아 손으로 넣던 TV번호를 **API `orderNumber`(주문 생성 응답)로 자동 주입** → 기존 브랜딩 PDF 템플릿(로고·QR 로직 이미 존재) 자동 렌더 → `issueExternalVoucher`(IMAGE) 발급 → 예약 페이지 노출 + 확정 메일. **템플릿 신규 디자인 불필요, 재사용.**
> - **유일한 신규 빌드**: "API 데이터 → 브랜딩 PDF 자동 생성" 스텝 배선(docs-gen 템플릿 slug 신설 vs barcode-voucher 로고오버레이 중 택1).
> - **유형별 범위**: TK = 주문 응답 즉시 완전 자동 / BK = 승인 웹훅(BOOKING_ACCEPTED→AC) 수신 후 자동 생성·발급(T3).
> - **ONVL(코드·파일 없는 수동) = 현행 라이브 0건**(2026-08-13 전수 스캔): 파트너 69 발급 실적 스팟 165개 전부 TV번호 QR 보유. 난타(117)는 dev 테스트 상품일 뿐 라이브 아님 → 자동 QR 불가 예외 **현재 없음**(향후 ONVL 신규 시에만 검토).
> - **발송 채널**: 예약 페이지 노출 + 확정 메일 홀드-후-발송. 전용 바우처 카톡·SMS 채널 없음(별도 푸시 원하면 신규 구축).
>
> **공급사 확인 불필요(닫힘)**: 로고·자체발송(`voucherSendType=0`)·QR값 전부 우리 쪽. QR 리딤값은 자체 디코딩으로 `orderNumber` 확정, 현행 운영에서 이미 검증. 잔여: 신규 TK/QR 상품 리딤값은 상품 추가 시 API 응답 디코딩으로 건별 확인(공급사 문의 아님).

### [T3] 예약(BK) 연동 — 조회 + 주문 + 승인/거절 상태 반영 (BE) · 선행 T1
- **스케줄·재고 조회** — 옵션별 예약 가능 날짜·시간·실시간 재고 조회(날짜 필터), 스케줄 없음(404) 처리
- **필수 추가정보 조회** — 옵션 추가정보 항목 목록 조회 → 항목별 유형(공통 1회 BAC / 여행자별 TRV)·응답유형(선택형 SEL / 입력형 IPU)·선택지 파악
- **주문 생성** — 스케줄·추가정보 확인 후 주문 생성(예약일시·추가정보 포함) → **생성 직후 승인 대기(PD)** 로 보류. 재고 부족·마감 에러 처리(재고부족 / 스케줄 재고부족 / 스케줄 마감)
- **승인/거절 상태 반영** — 승인 웹훅(BOOKING_ACCEPTED → 확정 AC) / 거절 웹훅(BOOKING_REJECTED → RJ, 환불·CS 연계) 수신·반영. 기존 수동 부킹 상태 모델과 정합(자동·수동 공존 과도기 고려)
- 바우처 자동 발급은 승인(AC) 시점에 T2 발급 로직 재사용
- **완료조건**: dev에서 BK 상품의 슬롯·재고·추가정보 조회 → 주문이 PD로 생성 → 승인/거절 웹훅에 따라 AC/RJ로 전환
> 규모가 크면 하위 서브태스크(①조회 / ②주문+상태반영)로 쪼갤 수 있음

### [T4] 어드민 자동/수동 구분 + 폴백·Slack 알림 (BE/어드민) · 선행 T2·T3
- **자동/수동 구분** — 어드민 예약내역 테이블에 **API 연동 여부** 컬럼 추가 또는 상위 필터에 **API 연동 여부** 필터 추가(택1). 예약 승인대기(PD)·거절(RJ) 건 상태 확인·개입 가능
- **폴백 경로** — 연동 실패(호출 오류·타임아웃·거절) 시 수동 처리 경로 유지, 자동 전환 상품도 예외 건은 담당자 확인·개입
- **알림** — 실패·거절·타임아웃 건 담당자 확인·수동 처리, 알림은 **Slack** 발송(기존 알림 패턴 활용)
- **완료조건**: 어드민에서 자동/수동 주문이 구분 노출·PD/RJ 확인 가능, 연동 실패 시 Slack 알림 + 수동 폴백 동작

### 프론트엔드 — 신규 작업 없음 (기존 예약 UI 재사용)
> 별도 FE 티켓 없음. 유저 노출 화면은 기존 크리에이트립 예약 흐름을 그대로 재사용(실측 확인 2026-08-19):
> - **바우처 노출·확정 메일** — 기존 템플릿·기존 예약 페이지 노출 메커니즘 재사용. 백엔드 자동 생성만 바뀌고 유저 화면 동일
> - **날짜·시간 선택** — 기존 예약 날짜 모달(날짜별 타임슬롯) 재사용
> - **추가정보 입력** — 기존 예약 추가정보 폼(입력창 / SELECT) 재사용 → 트래볼루션 IPU/SEL과 매칭
> - **승인 대기 상태** — 기존 예약 "확정 대기(1영업일 내 확정)" 상태 노출 재사용 → BK PD 상태와 매칭
>
> **⚠️ TK/BK 유형 정합 주의**: 크리에이트립은 트래볼루션처럼 상품을 **'예약형(BK)'·'티켓형(TK)'으로 구분하지 않는다**(날짜 선택·추가정보·승인 대기 노출은 상품별 개별 설정). → **주문 처리 흐름(즉시확정 vs 승인대기)은 백엔드가 트래볼루션 API `type`으로 판정·분기(T2/T3)** 하고, 크리에이트립 상품 설정은 상품 생성·매핑 시 그 유형에 맞게 정합(TK=즉시확정·날짜불필요 / BK=날짜·추가정보·승인대기)을 맞춘다. 유형 불일치 시 유저 화면과 실제 처리가 어긋날 수 있으므로 매핑(T1) 시 확인.
