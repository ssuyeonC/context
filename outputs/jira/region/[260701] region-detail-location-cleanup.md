# 세부 기획안 요구사항 문서

> ⚠️ **2026-07-02 구조 재정렬 (이해관계자 동의 대기)** — `[260701] region-geo-model-decision.md` §0 기준으로 두 지점이 갱신됨:
> 1. **상세지역↔법정동 연결 = 어드민 선택 기능 + 초기 스크립트 시딩** (기존 "스크립트 only / 어드민 기능 없음" 폐기 — §백엔드 참조). 어드민이 상세지역 생성 시 LEGAL_LOCATION(시군구, L2)을 직접 선택한다.
> 2. **CITY = 시도(L1)로 승격** (기존 시/군). 상세지역의 상위 도시가 시도가 됨. **스팟에 직접 노출되는 값(스팟 카드 라벨)이라 회사 이해관계자 승인 후 확정** — 승인 전엔 방향으로 표기. 광역시 외 CITY 스팟 일괄 마이그레이션 동반.

## 배경

### 문제 정의

지역 도메인의 '상세지역(DETAIL_LOCATION)'은 스팟이 실제로 매달리는 분류 단위인데, 지금은 성격이 다른 값이 한 바구니에 섞여 있어 분류 기준이 일관되지 않는다.

- **행정구(강남구·종로구)와 관광지·동(명동·홍대·성수동)이 혼재**한다. 관리자는 "이 스팟은 어느 지역인가"를 일관된 기준으로 넣지 못한다.
- 상세지역 158개 중 **105개(66%)가 상위 도시 없이 생성된 고아**이고, **이름 중복**(서면 3개·성수동 2개)과 **아무 데도 연결되지 않은 잔재**가 남아 있다.
- 상세지역 생성 화면에 **상위 도시를 넣는 입력이 없어**, 관리자가 만들 때마다 고아가 다시 생겨난다(재오염).

이 상태에서는 지역(REGION) 기능이 상세지역 위에 세워질 때 '구역 필터'가 빈 값·엉뚱한 값을 내게 된다. 따라서 지역 기능에 앞서 **상세지역을 행정구(구·시·군) 단위로 단일화**하는 정비가 선행돼야 한다.

정비 방향은 다음과 같다.

- 상세지역은 **행정구(구·시·군)만 남긴다.**
- 관광지·동은 상세지역에서 **제거**하고, 그 개념은 이후 지역(REGION)에서 다룬다. (본 문서 범위 밖 · 후속)
- 제거되는 상세지역에 걸린 **스팟·블로그·어학당 연결은 소속 행정구로 옮긴 뒤** 제거한다.
- 모든 행정구 상세지역을 **상위 도시(CITY)와 법정동(LEGAL_LOCATION)에 연결**한다.

> **본 문서 범위**: 상세지역(DETAIL_LOCATION) 정리 + 상세지역↔법정동(LEGAL_LOCATION) 연결까지. 지역(REGION) 생성·연결, 비공개 지역 삭제는 후속 트랙으로 별도 진행한다.

### 가설적 임팩트

- 상세지역이 행정구 단위로 정합되면, 이후 지역(REGION)을 "행정구 연결 + 그 구의 법정동 선택"으로 구성할 수 있는 **신뢰 가능한 기반**이 된다.
- 스팟은 이미 보유한 법정동 코드(**전체 스팟의 97.5%, 위치 정확도 유효 99.7%** — prod 실측)로 지역에 정확히 노출되므로, 관광지 단위 상세지역을 별도로 유지하지 않아도 세부 노출이 유지된다.
- 정비 결과(정량): 상세지역 158개 → **행정구 55개 유지 / 비-행정구 103개 제거.**
- 사용자 노출 지표(지역 페이지 유입·체류 등)는 후속 REGION 트랙에서 측정한다. 본 작업 자체의 목표는 **데이터 정합성 확보**이며, 사용자 대상 KPI는 `TBD`.

## 구현

### 유저 플로우

> 본 작업의 주 행위자는 **관리자**이며, 일반 사용자에게는 정비 완료 후 스팟의 지역 표기가 구 단위로 정합되는 결과만 반영된다.

- 관리자는 상세지역을 **행정구(구·시·군) 단위로만** 관리한다. (관광지·동은 지역(REGION)에서 다루며 상세지역에 만들지 않는다.)
- 관리자는 상세지역을 새로 만들 때 **상위 도시(CITY)를 반드시 지정**한다. 상위 도시를 비운 채 저장하려 하면 안내를 본다. **"상위 도시를 선택해야 상세지역을 저장할 수 있어요."** (문구 확정 `TBD`)
- 관리자는 상세지역 상세 모달에서 그 구에 **연결된 법정동(동) 목록을 확인**할 수 있다. 이 목록은 코드 체계로 자동 도출되어 **읽기 전용으로 노출**되며, 관리자가 수동으로 연결·편집하지 않는다.
- 관리자는 상세지역 관리 화면에서 상세지역 외 종류(도시·지하철 등)를 이 화면으로 **생성할 수 없다.**
- (정비 일회성 작업으로) 관광지·동 상세지역에 연결돼 있던 스팟은 소속 행정구로 옮겨지며, 사용자는 스팟에서 **{도시} {행정구}** 형태의 지역 표기를 본다.

### 프론트엔드 요구사항

**어드민 — 상세지역 관리(/location)**

- 상세지역 생성·수정 모달에 **상위 도시 선택 필드**를 추가한다. 상위 도시는 필수값으로, 미선택 시 저장을 막고 안내 문구를 노출한다. (🔄 2026-07-02: 상위 도시 = 시도 L1)
- 🔄 **2026-07-02**: 상세지역 생성·수정 모달에 **LEGAL_LOCATION(시군구, L2) 선택 필드**를 추가한다. 관리자는 이름 자유입력 + 상위 도시(시도) + 이 시군구를 골라 상세지역을 만든다(예: 이름 "분당구" + 도시 "경기도" + legal "성남시 분당구"). 하위 동(L3)은 이 시군구 코드에서 자동 도출된다.
- 상세지역이 아닌 종류를 생성하는 진입점은 이 화면에 노출하지 않는다.
- 상세지역 상세 모달에 그 구에 속한 **법정동(동) 목록을 읽기 전용으로 노출**한다. 이 목록은 저장된 값이 아니라 **조회 시 자동 도출**한 결과이며(§백엔드), 관리자는 확인만 하고 편집하지 않는다. **법정동을 수동으로 연결하는 입력은 두지 않는다.** 인지구역 단위의 법정동 선택은 이후 지역(REGION) 구성 화면에서 다룬다(후속 트랙).

### 백엔드 요구사항

**상세지역 생성/수정 — 상위 도시·재오염 차단**

- 상세지역 생성·수정 시 **상위 도시(parent)를 저장**할 수 있도록 한다. (현재는 상위 도시를 받는 입력이 없어 고아로 생성된다.)
- 카테고리 생성 시 **통제된 진입점으로만 생성 허용**하도록 종류 화이트리스트를 적용한다. 임의의 `createCategory` 직접 호출로 도시·지하철 등이 무분별하게 생성되는 것을 차단하되, **상세지역(DETAIL_LOCATION)은 상세지역 관리 화면에서, 도시(CITY)는 전용 도시 생성 채널**(LEGAL L1 선택 + 자유 텍스트 입력 — `[260701] region-geo-model-decision.md` §0 D4)에서 생성한다. (🔄 2026-07-02: "상세지역만 허용"에서 "통제된 진입점만 허용"으로 조정 — CITY 생성 채널 신설 반영. 상세지역 관리 화면 자체에서는 여전히 도시·지하철을 만들 수 없다.)

**상세지역 ↔ 법정동 연결 (어드민 선택 기능 + 초기 스크립트 시딩)**

> 🔄 **2026-07-02 갱신** — 아래 "일회성 스크립트 / 어드민 기능 없음"을 **어드민 선택 기능 + 초기 스크립트 시딩**으로 대체한다. 상세지역 생성·수정 모달에서 관리자가 **LEGAL_LOCATION(시군구, L2)을 직접 선택**해 연결하고, 최초 정비분(55+)은 스크립트로 일괄 시딩한다. 이후 신규 시군구(분당구·영통구·강릉시…)는 어드민에서 legal 선택으로 생성 가능. 이유: 광역시 6개에 한정됐던 상세지역을 전국 시군구로 확장하려면 상시 생성이 필요하고, legal에서 선택하면 고아·오매칭이 원천 차단된다.

- 행정구 상세지역에 자신의 **시군구 단위 법정동 코드(1:1, 지도 폴리곤용)**를 저장하는 값을 신설한다. 값의 소스는 **LEGAL_LOCATION(L2) 선택**이며, 최초 연결은 스크립트로 시딩(이름 자동매칭 49건 / 동명 시군구로 모호한 6건은 수동 지정), 이후는 어드민 모달에서 선택한다.
- 각 구에 속한 **하위 법정동 목록(pool)은 저장·연결하지 않는다.** 법정동 코드가 **구 코드로 시작**하는 성질을 이용해 **조회 시점에 자동 도출**한다. 구의 시군구 법정동 코드가 설정되는 순간(=생성/정비 시점)부터 도출 가능하다. 별도 스냅샷을 저장하지 않으므로 **`legal_location`이 갱신되면(재적재 시) 우리 쪽 재동기화 없이 그대로 반영**된다. (별도로 저장하면 스냅샷이 어긋나 재동기화가 필요하므로 저장하지 않는다.) ※ 단 `legal_location` 자체는 현재 **일회성 적재(2025-01-16)이며 상시 sync가 없다.** 위 '자동 반영'은 "우리가 병렬 매핑을 손수 유지하지 않는다"는 뜻이지 "정부 변경이 저절로 들어온다"는 뜻이 아니다 — 정부 최신화를 위한 정기 재적재는 **별도 후속 과제**(필요 시).
- 어드민 상세지역 모달의 '연결된 법정동 목록'도 이 도출 결과를 **읽기 전용으로** 반환한다.
- (이 법정동 목록은 이후 지역(REGION) 구성에서 법정동을 고르는 후보로도 쓰인다 — 후속 트랙)

**데이터 정비 (일회성 마이그레이션)**

아래 순서로 수행한다. **연결 재지정(스팟·블로그·어학당) 전에 상세지역을 삭제하지 않는다.**

1. **분류** — 상세지역 158개를 행정구(구·시·군)와 비-행정구로 구분한다. (행정구 55 / 비-행정구 103)
2. **완전 무연결 제거** — 비-행정구 중 스팟·블로그·어학당·지역(region) 연결이 **모두 없는 것**을 제거한다. (현재 대상: 청주공항 1건 — 실행 시점 재확인)
3. **연결 재지정** — 비-행정구에 연결된 **스팟·블로그·어학당을 소속 행정구로 이관**한다. 소속 행정구는 스팟의 법정동 코드(구 단위 접두어)로 도출한다. 소속 행정단위가 상세지역에 아직 없으면(예: 강릉시) **생성**한다.
4. **비-행정구 제거** — 재지정을 마친 비-행정구 상세지역을 제거한다.
5. **행정구 연결** — 남은 모든 행정구 상세지역에 **상위 도시**를 연결하고, 각 구에 **자신의 시군구 법정동 코드(1:1, 폴리곤용)**를 설정한다. (이름 자동매칭 49건 / 동명 시군구로 모호한 6건은 수동 지정) 하위 법정동 목록은 저장하지 않고 코드 접두어로 도출한다.

- 재지정 시 삭제 대상에 걸린 세 종류 연결(스팟·블로그·어학당)을 모두 옮긴다. **스팟만 옮기고 삭제하면 블로그 연결이 끊긴다.** (실측: 스팟이 없는 관광지 상세지역 11개가 블로그를 보유)

## 사람이 수행할 작업 (운영·기획 수동)

자동(스크립트) 처리와 별개로, 사람이 판단·검수·승인해야 하는 항목이다.

- **분류 검수** — 행정구/비-행정구 자동 분류 결과를 확인하고, 이름만으로 오분류되는 2건을 재분류 확정한다. (**서울대입구** — 접미사 '구'로 행정구처럼 보이나 지하철역 상권이므로 비-행정구 / **서면** — 접미사 '면'이나 행정 읍·면이 아닌 부산 상권이므로 비-행정구)
- **생성 필요 행정단위 범위 확정** — 비-행정구 스팟의 소속 행정단위 중, 상세지역에 아직 없는 시/군을 검토·승인한다. (예: 경포대·정동진·주문진의 소속 **강릉시**는 현재 상세지역에 없어 생성 필요. 제주시·서귀포시는 이미 존재)
- **구 법정동 코드 수동 지정 6건 (일회성)** — 동명 시군구가 여러 도시에 존재해 이름 자동매칭이 안 되는 구의 시군구 법정동 코드를 지정한다. 어드민 상시 기능이 아니라 정비 시점 1회 판단이다. (중구·동구·서구·남구·북구 — 상위 도시로 판별 / 강서구 — 서울로 판별)
- **연결 재지정 결과 검수** — 관광지 스팟이 엉뚱한 구로 옮겨지지 않았는지 표본 확인한다. 특히 구 경계에 걸친 스팟(법정동 경계 ±55m 이내)과 위치가 크게 어긋난 소수 스팟(20건)을 우선 확인한다.
- **실행 방식 결정** — 정비를 스크립트로 일괄 처리할지, 어드민에서 수동으로 할지 정한다. 수동으로 한다면 어드민의 상위 도시·법정동 연결 기능이 정비 작업보다 먼저 배포돼야 한다.
- **삭제 최종 승인** — 비-행정구 103개 제거 실행 전, 최종 목록을 승인한다.
