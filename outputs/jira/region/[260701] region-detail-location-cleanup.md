# 세부 기획안 요구사항 문서

작성일: 2026-07-01 · **재개정: 2026-07-06 (LEGAL 정합·비파괴 방식 확정)**
상태: **확정 방향** — 단 CITY 승격(시/군→시도)은 스팟 라벨을 바꾸므로 **회사 이해관계자 승인 후 실행.**
관련 문서: `[260701] region-geo-model-decision.md` §0·§0-3 · `[260701] region-domain-improvement-master.md` · `[260630] region-data-cleanup-spec.md`

> **한 줄 요약** — 도시(CITY)·상세지역(DETAIL_LOCATION)을 정부 법정동 체계(시도/시군구)에 정합한다. **비파괴**를 기본으로, 링크가 있는 값은 지우지 않고 레벨이 어긋나면 종류만 바꾸며(코드 보존), 법정동에 있는데 우리에게 없는 값만 새로 만들고, 스팟은 이미 가진 좌표(법정동 코드)로 도시·상세지역을 일괄 세팅한다. 관광지·동 상세지역(명동·홍대)은 **즉시 지우지 않고**, 대응 지역(REGION)이 생긴 뒤 넘겨받아 정리한다(관광지명 탐색 무중단).

## 배경

### 문제 정의

지역 도메인의 '도시(CITY)'와 '상세지역(DETAIL_LOCATION)'은 스팟이 실제로 매달리는 분류 단위인데, 지금은 하나의 기준으로 정렬돼 있지 않다.

- **레벨이 뒤섞여 있다.** 광역시는 '서울시'가 최상위 도시인데, 일반 도(경기·강원 등)에서는 '강릉시·의왕시' 같은 시가 최상위 도시로 들어가 있다. 같은 '도시' 칸에 시도급과 시/군급이 섞여, "이 스팟이 어디에 있다"를 일관된 기준으로 말할 수 없다.
- **안 쓰이는 값이 섞여 있다.** 도시에 '평양'(북한)·'타이페이·대만' 같은 값이 정제 없이 쌓여 있다.
- **상세지역은 성격이 다른 값이 한 바구니에 섞여 있다.** 행정구(강남구·종로구)와 관광지·동(명동·홍대·성수동)이 혼재하고, 상세지역 158개 중 **105개(66%)가 상위 도시 없는 고아**이며, **이름 중복**(서면 3개·성수동 2개)과 잔재가 남아 있다.
- **재오염 구조.** 상세지역 생성 화면에 상위 도시를 넣는 입력이 없어, 관리자가 만들 때마다 고아가 다시 생겨난다.

이 상태는 두 문제를 낳는다. ① 사용자에게 보이는 지역 표기가 들쭉날쭉하다(어떤 스팟은 '강릉시', 어떤 스팟은 '서울시 강남구'). ② 진행 중인 지역(REGION) 페이지 개편이 이 분류 위에 서는데, 토대가 일관적이지 않아 '구역 필터'가 빈 값·엉뚱한 값을 낸다. 따라서 지역 기능에 앞서 **도시·상세지역을 법정동 체계에 정합**하는 정비가 선행돼야 한다.

정비 방향은 다음과 같다(**LEGAL 정합·비파괴**).

- **도시(CITY) = 시도**(서울특별시·강원특별자치도), **상세지역(DETAIL_LOCATION) = 시군구**(강남구·강릉시)로 법정동 체계에 맞춘다.
- **비파괴** — 링크(스팟·블로그·어학당·지역)가 있는 값은 삭제하지 않는다. 레벨이 어긋나면 종류만 바꾼다(코드 보존). 예: 현재 도시로 있는 '강릉시'는 지우지 않고 **상세지역으로 재타입**하고, 그 상위 도시는 '강원특별자치도'가 대신한다.
- **없는 값만 생성** — 법정동에는 있는데 우리 데이터에 없는 시도·시군구만 새로 만든다(이미 있는 값은 재사용).
- **지역(REGION) 생성·보완 및 연결 (스팟 세팅보다 앞)** — 관광지명(홍대·명동) 등은 대응 지역(REGION)을 만들어 구 연결 + 법정동을 선택해 둔다. 이게 스팟 세팅보다 **앞서야**, 스팟을 시군구로 옮겨도 관광지명 탐색이 REGION으로 보존돼 끊기지 않는다. REGION은 스팟의 좌표(법정동 코드)로 노출되므로 스팟의 상세지역 값과 무관하게 먼저 만들 수 있다. (REGION 데이터 필드·어드민 개선이 그 선행 — 후속 트랙)
- **스팟 일괄 세팅** — 스팟의 도시·상세지역은 좌표(법정동 코드)로 도출해 일괄 세팅한다. **관광지 스팟의 이동은 위 REGION 준비 이후** 수행한다.
- **완전 무연결만 제거** — 어떤 링크도 없는 값만 지운다('한국'은 전국 fallback으로 유지, '평양'은 제거).
- **관광지·동은 상세지역에 새로 만들지 않는다.** 그 개념은 지역(REGION)에서 다룬다. 기존 관광지·동 상세지역은 즉시 지우지 않고, 대응 REGION이 생긴 뒤 정리한다(후속·아래 범위 참조).

> **본 문서 범위**: 도시·상세지역의 **법정동 정합**(재타입·생성·완전무연결 제거) + 상세지역↔법정동 연결 + **스팟 도시/상세지역 일괄 재태깅**까지. 단 **스팟 재태깅 중 관광지 스팟의 이동은 대응 REGION 준비를 선행조건으로** 하며(무중단), 그 REGION 생성은 후속 트랙이다. **후속 트랙(본 문서 밖)**: 지역(REGION) 생성·연결 및 **REGION 데이터 필드·어드민 개선(법정동 선택 — 관광지 스팟 이동의 선행)**, 관광지·동 상세지역의 **최종 삭제(REGION cutover)**, 스팟 법정동 코드 미보유분 보정, 비공개 지역 삭제.

### 가설적 임팩트

- 전 스팟이 동일한 기준(시도 / 시군구)의 지역 표기를 갖는다(표기 일관성 회복).
- 이후 지역(REGION)을 "구 연결 + 그 구의 법정동 선택"으로 구성할 수 있는 **신뢰 가능한 기반**이 된다(개편 잠금 해제).
- 스팟은 이미 보유한 법정동 코드(**전체 스팟의 97.5%, 위치 정확도 유효 99.7%** — prod 실측)로 도시·상세지역·지역 노출이 도출되므로, 관광지 단위 상세지역을 별도로 유지하지 않아도 세부 노출이 유지된다.
- 이 작업은 직접적인 유입·전환 지표를 겨냥한 성장 작업이 아니라 **토대 정비**다. 사용자 노출 지표(지역 페이지 유입·체류 등)는 후속 REGION 트랙에서 측정하며, 본 작업 자체의 목표는 **데이터 정합성 확보**다. 사용자 대상 KPI는 `TBD`.
- 스팟 라벨 체감 변화: 광역시 스팟(약 5,049개)은 사실상 불변('서울시'→'서울특별시' 수준), **도 소속 스팟(약 1,238개, 전체의 19%)은 '강릉시'→'강원특별자치도 강릉시'** 로 바뀐다.

## 구현

### 유저 플로우

> 본 작업의 주 행위자는 **관리자**이며, 일반 사용자에게는 정비 완료 후 스팟의 지역 표기가 시도/시군구 기준으로 정합되는 결과가 반영된다.

- 관리자는 **도시를 시도 단위**로, **상세지역을 시군구 단위**로 관리한다.
- 관리자는 지역 관리(/location) 화면의 **'도시' 탭에서 '추가'** 로 도시를 새로 만든다. 이때 **법정동(시도)에서 선택**하거나, 법정동에 없는 값(한국·해외 등)은 **자유 텍스트로 입력**한다.
- 관리자는 상세지역을 새로 만들 때 **상위 도시(시도)를 반드시 지정**하고 **법정동(시군구)을 선택**하며 이름은 자유입력(다국어)한다. 상위 도시를 비운 채 저장하려 하면 안내를 본다. **"상위 도시를 선택해야 상세지역을 저장할 수 있어요."** (문구 확정 `TBD`)
- 관리자는 상세지역 상세 화면에서 그 구에 **속한 법정동(동) 목록을 확인**할 수 있다. 이 목록은 코드 체계로 자동 도출되어 **읽기 전용으로 노출**되며, 관리자가 수동으로 연결·편집하지 않는다.
- 관리자는 상세지역 관리 화면에서 상세지역 외 종류(도시·지하철 등)를 이 화면으로 **생성할 수 없다.**
- 관리자는 관광지·동을 상세지역으로 **새로 만들지 않는다.** (해당 개념은 지역(REGION)에서 다룬다.)
- 관리자는 스팟을 등록·수정할 때 좌표로 연결된 지역에서 **도시·상세지역이 자동으로 채워지는 것**을 보며, 필요하면 드롭다운으로 **직접 수정**할 수 있다.
- 사용자는 정비 후 스팟에서 **{시도} {시군구}** 형태의 지역 표기를 본다. (예: '강원특별자치도 강릉시')

### 프론트엔드 요구사항

**어드민 — 도시(CITY) 관리 (/location '도시' 탭)**

- 지역 관리(/location) 화면은 **'도시' / '상세지역' / '법정지역'** 탭으로 나뉜다. 현재 생성·수정·삭제는 **'상세지역' 탭에만** 있고 '도시' 탭은 조회·순서변경만 가능하다. **'도시' 탭이 선택된 상태에 '추가' 버튼과 생성 모달을 둔다.** (도시 전용 생성 채널을 따로 만들지 않고 이 탭에 붙인다.)
- 도시 생성 모달에서 관리자는 **법정동(시도, L1)에서 선택**하거나, 법정동에 없는 전국·해외값('한국'·'타이페이' 등)은 **자유 텍스트로 입력**해 도시를 만든다. (현재 도시는 어드민에서 생성할 수 없어 백엔드/DB로만 주입돼 잡값이 쌓였다.)
- '법정지역' 탭은 지금처럼 읽기 전용을 유지한다.

**어드민 — 상세지역 관리(/location)**

- 상세지역 생성·수정 모달에 **상위 도시(시도) 선택 필드**를 추가한다. 필수값으로, 미선택 시 저장을 막고 안내 문구를 노출한다.
- 상세지역 생성·수정 모달에 **법정동(시군구, L2) 선택 필드**를 추가한다. 관리자는 이름 자유입력 + 상위 도시(시도) + 이 시군구를 골라 상세지역을 만든다. (예: 이름 "분당구" + 도시 "경기도" + 법정동 "성남시 분당구") 하위 동(L3)은 이 시군구 코드에서 자동 도출된다.
- 상세지역 상세 모달에 그 구에 속한 **법정동(동) 목록을 읽기 전용으로 노출**한다. 이 목록은 저장된 값이 아니라 **조회 시 자동 도출**한 결과이며(§백엔드), 관리자는 확인만 하고 편집하지 않는다. **법정동을 수동으로 연결하는 입력은 두지 않는다.** 인지구역 단위의 법정동 선택은 이후 지역(REGION) 구성 화면에서 다룬다(후속 트랙).
- 상세지역이 아닌 종류(도시·지하철)를 생성하는 진입점은 이 화면에 노출하지 않는다.

**어드민 — 스팟 지역 태깅**

- 스팟 등록·수정 화면에서 도시·상세지역을 **좌표(법정동)로 자동 도출·연결**하고, 관리자가 드롭다운으로 **직접 수정**할 수 있게 한다. 좌표 방향 주의: 도시(시도)는 시군구를 못 좁히므로 "상세지역(시군구) 결정 → 도시(부모) 자동" 또는 "좌표에서 둘 다 자동" 순으로 채운다.

### 백엔드 요구사항

**도시·상세지역 생성 — 상위 연결·재오염 차단**

- 상세지역 생성·수정 시 **상위 도시(parent)를 저장**할 수 있도록 한다. (현재는 상위 도시를 받는 입력이 없어 고아로 생성된다.)
- 카테고리 생성 시 **통제된 진입점으로만 생성 허용**하도록 종류 화이트리스트를 적용한다. 임의 호출로 지하철 등이 무분별하게 생성되는 것을 차단하되, **도시·상세지역은 각각 /location의 '도시' 탭 · '상세지역' 탭**에서 생성한다(법정동 선택 + 필요 시 자유 텍스트). 각 탭은 자기 종류만 만들 수 있다(도시 탭에서 상세지역·지하철 생성 불가, 반대도 동일).

**상세지역 ↔ 법정동 연결 (어드민 선택 + 초기 스크립트 시딩)**

- 상세지역에 자신의 **시군구 단위 법정동 코드(1:1, 지도 폴리곤용)**를 저장하는 값을 둔다. 값의 소스는 **법정동(L2) 선택**이며, 최초 정비분은 스크립트로 일괄 시딩(이름 자동매칭 / 동명 시군구로 모호한 건은 수동 지정), 이후 신규 시군구는 어드민 모달에서 선택한다.
- 각 구에 속한 **하위 법정동 목록(pool)은 저장·연결하지 않는다.** 법정동 코드가 **구 코드로 시작**하는 성질을 이용해 **조회 시점에 자동 도출**한다. 별도 스냅샷을 저장하지 않으므로 법정동 원천이 갱신돼도 우리 쪽 병렬 매핑을 손수 유지하지 않는다. (단 법정동 원천 자체는 현재 일회성 적재이며 상시 sync는 별도 후속 과제.)
- 어드민 상세지역 모달의 '연결된 법정동 목록'도 이 도출 결과를 **읽기 전용으로** 반환한다.

**스팟 도시·상세지역 자동 태깅**

- 스팟의 도시(시도)·상세지역(시군구)을 좌표로 연결된 법정동에서 **자동 도출·저장**한다. 신규 스팟도 위치만 있으면 자동으로 채워지며, 좌표 없는 스팟·오배정 스팟은 수동 지정한다.

**데이터 정비 (일회성 마이그레이션) — 실행 순서**

아래 순서로 수행한다. **비파괴가 기본이며, 링크 재지정 전에 값을 삭제하지 않는다.**

1. **완전 무연결 제거** — 도시·상세지역 중 스팟·블로그·어학당·지역(region) 연결이 **모두 없는 것**만 제거한다. ('한국'은 유지, '평양'(북한)은 제거. 상세지역 완전 무연결은 현재 청주공항 1건 — 실행 시점 재확인.)
2. **레벨 재타입 (코드 보존)** — 현재 도시로 있으나 시군구(L2)에 해당하는 값(강릉시·의왕시·춘천시 등)은 **삭제하지 않고 상세지역으로 종류만 바꾸고**, 상위 도시를 소속 시도로 재지정한다. 코드를 보존하므로 블로그·어학당 링크가 그대로 살아 재작업이 없다.
3. **법정동 기준 생성 (없는 값만)** — 도시 = 법정동 시도(L1), 상세지역 = 법정동 시군구(L2)를 확보한다. 이미 있는 값(광역시·특별시 도시, 행정구·재타입 시군구 상세지역)은 재사용하고, 없는 값(강원특별자치도 등 시도, 미보유 시군구)만 생성한다.
4. **지역(REGION) 생성·보완 및 연결 (후속 트랙 · 5의 선행)** — 관광지명 상세지역(홍대·명동)을 대응 지역(REGION)으로 만들어 구 연결 + 법정동을 선택해 둔다. **스팟 세팅보다 앞서야** 관광지명 탐색이 REGION으로 보존돼 무중단이 성립한다. REGION은 스팟의 좌표(법정동 코드)로 노출되므로 스팟의 상세지역 값과 무관하게 먼저 만들 수 있다. (선행: **REGION 데이터 필드·어드민 개선 — 법정동 선택.** 아래 후속 트랙 참조.)
5. **스팟 일괄 세팅** — 스팟의 도시·상세지역을 좌표(법정동 코드)의 시도·시군구로 일괄 세팅한다. 도시(시도)·일반 스팟은 3까지의 정합 위에서 세팅 가능하고, **관광지 스팟의 이동(홍대→마포구)은 4의 대응 REGION 준비 이후** 수행한다.

**관광지·동 상세지역 처리 (즉시 삭제 금지 · REGION 트랙으로 이동)**

- 관광지·동 상세지역(명동·홍대 등)은 정합 집합(시군구)에서 빠지지만 **즉시 삭제하지 않는다.** 정비~대응 지역(REGION) 추가 사이 기간에도 **관광지명으로 스팟을 찾는 사용자**가 있어, 미리 지우면 그 창 동안 탐색이 끊긴다(**유저 무중단**).
- 순서는 **지역(REGION) 생성·연결이 스팟 세팅(관광지 링크 제거)보다 앞선다** (홍대 예시): ① 마포구 상세지역 확보 → ② '홍대' 지역(REGION) 생성(마포구 연결 + 홍대권 법정동 선택) → ③ 스팟 세팅: 스팟의 '홍대' 링크를 마포구로 정리 + 홍대 상세지역의 **블로그·어학당을 마포구로 수동 이관**(법정동 코드가 없어 자동 도출 불가) → ④ 홍대 상세지역 삭제.
- ①~②에서 홍대 지역이 관광지명 탐색을 먼저 넘겨받으므로, ③에서 스팟을 마포구로 옮겨도 탐색이 끊기지 않는다(별도 전이 상태 불필요). ④ 삭제는 **REGION 이관 트랙(후속)** 에서 수행한다.
- 단 ③의 '홍대' 링크 제거·④ 삭제는 대응 REGION이 **유저에게 노출된 시점**(페이지 배포 포함) 이후에 수행한다.

## 사람이 수행할 작업 (운영·기획 수동)

자동(스크립트) 처리와 별개로, 사람이 판단·검수·승인해야 하는 항목이다.

- **CITY 승격 승인 (게이트)** — 도시를 시/군에서 시도로 올리면 스팟 카드 라벨이 바뀌므로, 실행 전 **회사 이해관계자 승인**을 받는다. 승인 전에는 준비만 하고 착수하지 않는다.
- **분류 검수** — 이름만으로 오분류되는 2건을 재분류 확정한다. (**서울대입구** — 접미사 '구'이나 지하철역 상권이므로 관광지형 / **서면** — 접미사 '면'이나 부산 상권이므로 관광지형)
- **동명 시군구 수동 매칭 6건 (일회성)** — 이름 자동매칭이 안 되는 구의 법정동 코드를 지정한다. (중구·동구·서구·남구·북구 — 상위 도시로 판별 / 강서구 — 서울로 판별)
- **재태깅 결과 검수** — 스팟이 엉뚱한 구로 옮겨지지 않았는지 표본 확인한다. 특히 구 경계에 걸친 스팟(법정동 경계 ±55m 이내)과 위치가 크게 어긋난 소수 스팟(20건)을 우선 확인한다.
- **잡값 처리 확인** — '한국'·해외값(타이페이·대만) 유지, '평양' 제거를 확정한다.
- **실행 방식 결정** — 정비를 스크립트로 일괄 처리할지, 어드민에서 수동으로 할지 정한다. 수동으로 한다면 어드민의 도시 생성 채널·상세지역 상위/법정동 연결 기능이 정비 작업보다 먼저 배포돼야 한다.
- **관광지·동 상세지역 삭제 승인** — 대응 지역(REGION)이 라이브된 뒤, 삭제 대상 목록을 최종 승인한다. (REGION 트랙에서 수행)
