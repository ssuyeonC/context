# 파트너 어드민 예약내역 페이지(리스트·상세) 개선 요구사항

## 배경

### 문제 정의

현재 파트너 어드민의 예약내역 페이지(리스트·상세)는 다음과 같은 한계가 있다.

**리스트 페이지**

- 매일 수십 건의 예약을 다루는 파트너 입장에서 한 화면에 노출되는 컬럼이 과도하게 많고, 특히 스팟 컬럼은 단일 스팟만 운영하는 파트너이거나 이미 특정 스팟을 필터로 좁혀본 상태에서는 매 행마다 같은 값이 반복되어 가독성을 떨어뜨린다.
- 예약 상태(결제 대기·승인 대기·확정·사용 완료·취소 등)가 텍스트로만 구분되어 있어, 처리 필요한 건과 그렇지 않은 건이 한눈에 식별되지 않는다.
- 컬럼별 소팅이 지원되지 않아, 방문 시간 빠른 순·상태 순 등 운영자가 원하는 기준으로 정렬할 수 없다.
- 다수의 스팟·다수의 상품을 운영하는 파트너에게 리스트 내 검색·필터 도구가 빈약해, 특정 상품·기간·고객의 예약을 찾는 데 인터랙션 수가 많다.
- 동일 상태의 예약이 다수 누적되어 있어도 1건씩 반복 처리해야 하며, 다건을 한 번에 처리할 수 있는 도구가 없다.

**상세 페이지**

- 예약 상세에 진입한 시점에서 파트너가 바로 취할 수 있는 액션(승인·취소·변경 요청 등)이 페이지 내에 분산되어 있거나 인지가 어렵다. 직접 취소·고객 안내 같은 기존 기능이 이미 있음에도 사용하지 않는 파트너가 다수 확인됨.
- 상세 페이지가 정보 표시에 머물고 처리 액션으로 자연스럽게 이어지지 않아, 파트너가 다시 카톡으로 우회하는 흐름이 반복된다.
- 유저·관리자가 보낸 예약 변경 요청, 파트너가 발송한 변경·취소 요청 등 여러 종류의 요청이 한 예약에 얽히는데, 현재는 이를 한 화면에서 일관되게 인지·처리할 수 있는 영역이 없다.
- 예약상품 세부·요구정보·바우처·수정 이력 같은 운영 정보가 흩어져 있어, 파트너가 처리에 필요한 맥락을 한 화면에서 파악하기 어렵다.

### 가설적 임팩트

- 리스트 컬럼·컬러·소팅 정비로 매일 누적되던 인지 부담이 감소하여, 어드민 활용도가 높은 파트너(아리한복류)의 페인이 해소되고 신규 파트너의 학습 비용도 낮아진다.
- 검색·필터·다건 처리 도구 보강으로 다스팟 운영 파트너(투어스토리·호수도산 등)의 어드민 활용도가 상승하여, 카테고리 표준(KKday 등) 대비 격차가 좁혀진다.
- 상세 페이지에서 액션 진입점이 명확해지고 요청 처리 배너가 통합되면 "있는 기능을 모르고 안 쓰는" 패턴이 줄어들어, 직접 처리 가능한 건이 어드민 내에서 마무리된다 — 운영팀으로 가는 카톡 트래픽 감소.
- 변경·취소 요청 진입점과 처리 배너를 한 화면에 정렬해 두어, 파트너가 한 시점에 하나의 요청 흐름만 명확히 따라가도록 유도한다.

## 구현

### 유저 플로우

**리스트 페이지 진입**

- 파트너가 예약내역 메뉴에 진입하면 정리된 예약 테이블이 노출된다.
- 기본 컬럼은 다음과 같다: 스팟 / 옵션 / 예약일 / 예약 시간 / 예약자 / 인원 / 상태 / 예약 코드.
- 스팟 컬럼은 스팟 필터 상태에 따라 자동으로 표시/숨김된다 (아래 '스팟 컬럼 적응형 표시' 항목 참조).
- 기존에 노출되던 운영상 불필요한 컬럼은 기본 노출에서 제거된다.

**스팟 컬럼 적응형 표시**

- 스팟 필터가 '전체'인 경우 → 스팟 컬럼 노출 (기본).
- 스팟 필터가 특정 스팟 1개로 좁혀진 경우 → 스팟 컬럼 자동 숨김 (모든 행이 같은 값이므로 중복 제거).
- 스팟 컬럼이 숨겨질 때, 테이블 상단에 현재 보고 있는 스팟을 한 줄로 명시한다: **{스팟명} 스팟의 예약 ({n}건)**.
- 사용자가 어느 스팟의 데이터를 보고 있는지 즉시 인지할 수 있도록 한다.
- 이 적응형 동작은 스팟 컬럼에만 적용한다. 옵션·상태·기간 등 다른 필터에 의해 컬럼이 사라지지는 않는다.

**상태 컬러 코딩 및 행 시각 구분**

- 예약 상태별로 색상이 부여되어 한눈에 식별 가능하다.
  - **승인 대기**: 강조 색(처리 필요 신호)
  - **확정 완료**: 중립 색
  - **사용 완료**: 비활성 톤
  - **취소**: 약화 톤(회색·취소선 등)
  - **결제 대기**: 약한 중립 톤(아직 파트너 처리 대상이 아님)
- 행 간 시각 구분(zebra striping)으로 행 단위 가독성을 보강한다.
- 예약자 셀에는 처리 대기 중인 요청이 있는 예약에 ⚠️를 표시한다. (특이사항 유무는 ⚠️ 표시와 무관하다.)

**검색·필터**

- 필터 영역은 다음 항목으로 구성된다.
  - 키워드 검색 — 예약 ID, 예약 코드, 이름, 이메일, 회원 코드 부분 일치.
  - 예약 언어 필터 — 언어 전체(기본) / 한국어 / 중국어 / 영어 / 일본어 / 베트남어 등.
  - 기간 — 기간 기준 토글(예약 일자 / 예약 생성일) + 직접 기간 입력 + 빠른 프리셋(오늘 / 7일 / 30일 / 이번 달 / 전체 기간). 기본값은 이번 달.
  - 주문상태 필터 — 전체 / 결제 대기 / 승인 대기 / 확정 완료 / 취소 / 사용 완료.
  - 특이사항 필터 — 특이사항 모두(기본) / 특이사항 O / 특이사항 X.
  - 변경요청 필터 — 전체 / 유저 예약 변경 요청 / 관리자 예약 변경 요청 / 파트너 예약 변경 요청 / 파트너 취소 요청. 각 유형별 건수를 카운트 뱃지로 함께 노출한다.
- 필터 초기화 버튼 1개를 노출한다.
- 적용된 필터는 제거 가능한 필터 칩으로 필터 영역 하단에 노출되어, 현재 어떤 조건이 걸려 있는지 한눈에 보이고 개별 해제가 가능하다.
- 스팟 selector는 위 필터 영역이 아니라 테이블 헤더 바로 위로 위치를 옮긴다 (FR-5 참조).

**리스트 상단 도구**

- 테이블 상단에 전체 {n}건 카운트를 노출한다.
- 리스트 뷰 / 캘린더 뷰 토글을 제공한다. (캘린더 뷰 자체는 기존 배포분 활용)
- 예약내역 엑셀 / 패키지 예약 엑셀 내보내기 버튼을 제공한다.

**다건 선택 및 일괄 액션**

- 리스트 좌측 끝에 행 선택 체크박스 컬럼이 추가된다. 헤더 체크박스로 현재 페이지 전체 선택이 가능하다.
- 1건 이상 선택되면 리스트 상단에 일괄 액션 바가 노출되고, 선택 카운트와 선택 해제가 표시된다.
- 액션 바에 선택한 예약 승인 버튼이 노출된다.
  - 클릭 시 확인 모달을 거쳐 일괄 처리된다. 확인 모달은 선택 {n}건 중 승인 가능한 {m}건을 명시하고, 승인 불가 건은 "이미 확정·취소·사용 완료 상태로 자동으로 건너뜁니다"를 안내한다.
  - 처리 후 성공·실패 카운트를 토스트로 안내한다.
  - 승인 가능하지 않은 상태(이미 확정·취소 등)가 섞여 있으면 가능한 건만 처리되고, 실패 건은 사유와 함께 결과에 반환된다.

**인라인 승인**

- 리스트 행 마지막 액션 컬럼에서 승인 대기 행에 한해 승인 버튼이 활성화된다.
- 단, 해당 예약에 처리 대기 중인 요청이 있는 경우 인라인 승인 버튼은 비활성화되고, **얼럿이 있는 예약은 상세 페이지에서 처리해주세요.** 안내를 노출한다. 파트너가 맥락을 확인한 뒤 상세에서 처리하도록 유도한다.

**상세 페이지 진입**

- 리스트의 행 또는 예약 코드 클릭으로 예약 상세에 진입한다. 상세는 오버레이(모달) 형태로 열리며, 상단 액션 영역이 고정(sticky)된다.
- 상세 상단에 핵심 정보가 묶여 노출된다: 상태 배지, 스팟·상품·옵션, 예약 ID, 재예약 횟수·멤버십 결제 등 뱃지.
- 상태 배지는 리스트와 동일한 컬러 코딩을 사용한다.

**상세 페이지 정보 구조(IA) 재편**

- 기존 상세는 '상점 정보 / 계정 정보 / 예약 정보'가 비슷한 비중의 테이블로 평면적으로 나열되어, 파트너가 지금 처리에 필요한 정보를 한눈에 파악하기 어려웠다. 본 개선에서 정보 구조를 다음과 같이 위계화·섹션화한다.
- 화면을 위에서 아래로 다음 3개 층으로 재편한다.
  1. **처리 층 (상단 고정)** — 액션 바(승인/사용 완료 처리 · 취소 요청 · 변경 요청)와 그 아래 요청 처리·진행 배너. 파트너가 진입 직후 처리 액션과 진행 중 요청을 가장 먼저 인지하도록 최상단에 고정한다.
  2. **요약 층** — 예약을 식별하는 헤더(상태 배지 → 스팟·상품·옵션의 타이포그래피 위계, 예약 ID 인라인, 재예약 횟수·멤버십 결제 뱃지 우측 정렬)와, 바로 아래 주요 정보 요약 카드(방문일시 · 예약자 · 방문 인원 · 결제 금액). 한 예약의 핵심을 카드 1개로 압축한다.
  3. **세부 층** — 섹션 단위로 그룹핑된 운영 정보 블록. 각 블록은 공통 섹션 헤더 스타일로 구분되며 순서는 다음과 같다: 예약상품 세부 정보 → 예약자 세부 정보 → 결제 정보 → 바우처 관리 → 기타사항.
- 정보를 평면적 테이블에서 '요약 카드 + 섹션형 블록' 구조로 전환하여, 파트너가 처리(상단) → 요약(중단) → 세부(하단) 순으로 자연스럽게 시선을 옮기도록 한다.
- 각 세부 블록 내부는 라벨-값 쌍의 카드형 그리드로 구성하며, 단순 나열보다 그룹·여백으로 가독성을 확보한다 (구체 컬럼 수·간격은 디자인 단계에서 확정).
- 위 정보 구조의 시각적 레이아웃 기준은 와이어프레임을 따른다 (FR-8 와이어프레임 링크 참조).

**상세 페이지 액션 영역**

- 상세 페이지 상단(고정 영역)에 다음 액션이 1뎁스로 노출된다.
  - **승인하기** — 단, 예약 상태가 확정 완료인 경우 같은 자리의 버튼이 **사용 완료 처리**로 노출된다 (승인 대기 → 승인, 확정 완료 → 사용 완료 처리).
  - **예약 취소 요청하기** — 클릭 시 예약 취소 요청 모달 진입 (아래 항목 참조).
  - **예약 변경 요청하기** — 클릭 시 예약 변경 요청 모달 진입 (아래 항목 참조).
- 모달 셸·헤더·취소/확인 버튼 배치는 세 액션 공통 패턴을 따른다 (디자인 일관성).
- 각 액션 버튼은 현재 상태에 따라 활성/비활성으로 표현된다.
  - 승인하기/사용 완료 처리는 처리 대상 상태가 아니거나, 처리해야 할 얼럿(진행 중 요청)이 있는 경우 비활성된다.
  - 예약 취소 요청·예약 변경 요청은 확정 완료 또는 승인 대기 상태에서만 활성된다.
  - 해당 예약에 처리 대기 중인 변경 요청 또는 취소 요청이 있는 경우 예약 변경 요청하기·예약 취소 요청하기 버튼은 모두 비활성 처리된다. 한 시점에 하나의 요청만 처리 대기할 수 있다.
  - 비활성 시 사유를 안내한다 (예: **진행 중인 요청이 종결된 후 변경/취소 요청을 다시 보낼 수 있습니다.**).

**요청 처리·진행 배너**

- 상세 상단 액션 영역과 본문 사이에, 해당 예약에 얽힌 요청을 한 줄로 보여주는 배너 영역을 둔다. 처리 대기 중인 요청이 없으면 배너는 렌더되지 않는다.
- 배너는 요청 유형에 따라 동일한 시각적 컴포넌트를 쓰되, 유형 칩·헤드라인·상세 라벨·액션이 달라진다.
  - **유저 예약 변경 요청** — 헤드라인 "유저가 예약일 변경을 요청했습니다", 상세 라벨 '유저 선택일'. 파트너가 그 자리에서 처리: 예약 변경 승인 / 예약 변경 거절 / 예약 변경 처리 무시.
    - 승인: 유저가 선택한 일정으로 방문일시가 반영, 예약 변경 요청 케이스 종료.
    - 거절: 기존 동작 유지, 예약 변경 요청 케이스 종료.
    - 무시: 기존 동작 유지, 예약 변경 요청 케이스 종료.
  - **관리자 예약 변경 요청** — 헤드라인 "관리자가 예약일 변경을 요청했습니다", 상세 라벨 '관리자 선택일'. 유저 응답 대기 상태로 표시한다.
  - **파트너 예약 변경 요청** — 헤드라인 "파트너가 예약일 변경 요청을 발송했습니다", 상세 라벨 '변경 요청일'.
    - 유저가 후보 중 하나를 선택해 응답한 경우, 선택일을 보여주고 파트너가 승인 / 거절할 수 있다.
    - 승인 시 해당 일정으로 방문일시가 반영된다.
    - 거절 시 변경없이 예약 요청 케이스가 종료된다.
    - 아직 유저 응답 전이면 유저 응답 대기 중으로 표시한다.
  - **파트너 취소 요청** — 헤드라인 "파트너가 예약 취소 요청을 발송했습니다", 상세 라벨 '취소 사유'. 관리자 처리 대기 중으로 표시한다.
- 요청이 종결되면(승인·거절·무시·관리자 처리 등) 배너는 자동으로 사라지고, 비활성되어 있던 변경/취소 요청 버튼이 다시 활성된다.

**예약 변경 요청 모달**

- 모달 타이틀: **예약 변경 요청**.
- 본문 구성 요소 (위에서 아래 순서):
  1. **변경 요청 예약일** — 변경 후보 날짜 선택(복수 가능). 입력 영역의 언어 표기(예: '예약언어: 영어')는 예약자 사용 언어를 안내한다.
  2. **템플릿 카테고리 드롭다운** — 옵션: 파트너용 / 직접 입력. 기본 선택값은 파트너용.
  3. **세부 템플릿 드롭다운** — 카테고리가 '파트너용'일 때만 노출. 마스터 템플릿 단위로 한국어 제목이 옵션으로 노출되며, 기본 선택값은 예약 마감으로 인한 날짜/시간 변경 안내.
  4. **제목 표시 영역** / **본문 표시 영역**
     - 파트너용: 선택된 템플릿의 예약자 언어 번역이 자동으로 채워지고 그 자리에서 수정 불가(readonly).
     - 직접 입력: 세부 템플릿 드롭다운이 숨겨지고 제목·본문 영역이 빈 상태의 자유 입력으로 전환된다.
- 모달 하단 액션: 취소 / 확인(메일 보내기). '확인' 클릭 시 파트너용은 시스템이 변수(스팟명·예약 코드·예약자명·패키지·마이페이지 URL 등)를 자동 바인딩하여 발송한다. 직접 입력은 파트너가 작성한 제목·본문을 그대로 발송한다.
- 발송 완료 시 모달은 닫히고, 발송 결과는 상세의 요청 처리·진행 배너에 '파트너 예약 변경 요청'으로 반영된다.

**예약 취소 요청 모달**

- 모달 타이틀: **예약 취소 요청**.
- 본문 구성: 예약 정보 요약 + 취소 사유 선택. 확인 시 취소 요청 메일이 발송되며 예약은 취소 대기 상태로 전환됨을 안내한다.
- 발송 완료 시 상세의 요청 처리·진행 배너에 '파트너 취소 요청'으로 반영된다.

**방문일 직접 변경**

- 상세의 주요 정보 블록에서 방문일 변경 버튼으로 파트너가 방문일·방문 시간을 직접 변경할 수 있다 (요청 흐름과 별개의 직접 변경).
- 변경 시 **변경 시 예약자에게 변경된 방문 일시가 안내됩니다.** 를 안내한다.
- 파트너 등급에 따라 노출 여부가 결정된다.
  - TRAVEL_PARTNER_SUPERIOR만 노출.

**상세 본문 정보 블록**

- **주요 정보** — 방문일시(+방문일 변경), 예약자, 방문 인원, 결제 금액(멤버십 할인 안내 툴팁 포함).
- **예약상품 세부 정보** — 상품 정보·수량, 인원별 요구정보(여권명·생년월일·옵션 등). 복수 옵션/복수 인원 케이스를 인원 단위로 구분해 노출한다.
- **예약자 세부 정보** — 이름, 국적, 예약자 코드, SNS 계정, 이메일(+이메일 발송), 전화번호.
- **결제 정보** — 결제 타입, 통화, 총 결제 금액, 총 할인액(멤버십 할인 툴팁), 실결제 금액, 총 정산가.
- **바우처 관리** — 바우처 이름, 발급 현황, 발급 가능 수량, 생성(단일 생성 / 일괄 추가(이미지) / 일괄 엑셀 업로드(텍스트)).
- **기타사항** — 특이사항 편집(편집 → 저장) + 최근 수정내역(최근 수정 일시·내용·수정자) + 전체 수정내역 모달(수정 일시·내용·수정자, 수정자 역할 태그: 관리자/파트너/시스템/유저).

**이메일 발송**

- 예약자 세부 정보의 이메일 옆 이메일 발송으로, 변경 후보 날짜 입력 없이 템플릿 기반 안내 메일을 보낼 수 있다. 모달 구성은 예약 변경 요청 모달과 동일하되 날짜 후보 입력이 빠진다.

**모바일 환경**

- 모바일에서도 동일한 기능을 제공하되, 화면 폭에 맞춰 표현(레이아웃·컴포넌트)만 달라진다. 데이터·동작·요청 처리 로직은 데스크톱과 동일하다.

*리스트 — 카드 리스트*

- 테이블 대신 예약 1건당 카드 1개로 노출한다.
- 카드 구성: 상단에 상태 배지와 (진행 중 요청이 있으면) 요청 유형 칩(⚡) / 스팟 · 상품 · 옵션 / 예약자 · 인원, 방문 일시 / 하단에 예약 코드와 승인 버튼.
- 승인 버튼은 승인 대기 건에 한해 노출되며, 진행 중 요청이 있으면 비활성된다 (데스크톱 인라인 승인과 동일 규칙).

*필터 — 모바일 레이아웃 (데스크톱 대비 축소)*

- 모바일 리스트 화면에는 데스크톱보다 축소된 필터 세트를 노출한다.
- 노출 항목과 배치:
  - 검색 입력 + 예약 언어(드롭다운)를 한 줄에.
  - 기간 기준(예약 일자/생성일, 드롭다운) + 기간 표시를 한 줄에.
  - 주문상태 + 변경요청을 (데스크톱의 pill 대신) 드롭다운으로 한 줄에.
  - 스팟 selector는 필터 영역과 분리된 별도 줄에 풀폭 드롭다운으로.
  - 전체 {n}건 카운트.
- 데스크톱에는 있으나 모바일 리스트 화면에서는 생략하는 것: **특이사항 필터 / 빠른 기간 프리셋(오늘·7일·30일·이번 달·전체 기간) / 필터 초기화 버튼 / 적용 필터 칩**. 공간 제약을 고려한 축소이며, 기간은 직접 입력으로 지정한다.

*상세 — 풀스크린 시트*

- 상세는 오버레이 모달이 아니라 풀스크린 시트로 열린다.
- 헤더: 뒤로(←) + 예약 코드 + 상태 배지.
- 본문(세로 스크롤): 요청 처리·진행 배너 → 식별/주요 정보 카드 → 예약상품 세부 → 예약자 세부 → 결제 정보 → 바우처 관리 → 기타사항. 각 블록은 카드 형태로 쌓인다.
- 액션 바는 화면 하단에 고정(sticky footer)된다: 승인하기/사용 완료 처리(풀폭) + 취소 요청·변경 요청(2분할). 데스크톱이 상단 고정인 것과 달리 모바일은 하단 고정이다.
- 요청 처리·진행 배너의 처리(승인/거절/무시 등) 및 액션 버튼의 활성/비활성 규칙은 데스크톱과 동일하다.

*요청 모달 — 풀스크린 바텀시트*

- 예약 변경 요청·예약 취소 요청 모달은 풀스크린 시트로 열린다. 헤더(뒤로 + 타이틀), 본문, 하단 고정 푸터(취소 / 확인) 구조를 따르며, 본문 구성 항목은 데스크톱 모달과 동일하다.

### 프론트엔드 요구사항

**와이어프레임**: https://wireframes-lkb.pages.dev/#partner-admin-reservation-list-v2

**FR-1. 리스트 테이블 컬럼 재구성**

- 기본 컬럼을 다음 8개로 정리한다: 스팟 / 옵션 / 예약일 / 예약 시간 / 예약자 / 인원 / 상태 / 예약 코드.
- 행 마지막에 인라인 액션 컬럼을 둔다 (승인 대기 행에 한해 **승인** 버튼 활성).
- 예약자 셀에 진행 중 요청 여부를 ⚠️로 표시한다.

**FR-1-1. 스팟 컬럼 적응형 표시**

- 스팟 필터가 '전체'일 때 스팟 컬럼을 표시한다 (기본).
- 스팟 필터에서 특정 스팟이 선택되면 스팟 컬럼을 자동으로 숨긴다.
- 스팟 컬럼이 숨겨질 때 테이블 상단에 컨텍스트 안내 문구를 노출한다: **{스팟명} 스팟의 예약 ({n}건)**.
- 다른 필터(옵션·기간·상태 등) 변경은 컬럼 표시/숨김에 영향을 주지 않는다.

**FR-2. 상태값 뱃지로 노출**

- 상태별 색상 토큰을 정의하여 리스트와 상세에서 동일하게 사용한다.
- 색상 토큰 구분: 결제 대기(약한 중립) / 승인 대기(강조) / 확정 완료(중립) / 사용 완료(비활성) / 취소(약화).

**FR-3. 행 시각 구분**

- 행 간 시각 구분 처리(zebra striping)를 적용하여 다수 행이 누적되어도 가독성이 유지되도록 한다.

**FR-4. 컬럼 소팅**

- 방문 일시(예약일+예약 시간)·상태 컬럼은 헤더 클릭으로 오름차순·내림차순 토글된다.
- 기본 정렬은 방문 일시 오름차순.
- 기존 날짜 기준 소팅 드롭다운은 제거하고 헤더 클릭 정렬로 통합한다.

**FR-5. 필터 영역**

- 키워드 검색 / 예약 언어 / 기간 기준 토글 + 기간 + 빠른 프리셋 / 주문상태 / 특이사항 / 변경요청(+유형별 카운트) 필터를 제공한다.
- 필터 초기화 버튼과 적용 필터 칩(개별 해제 가능)을 제공한다.
- 스팟 selector는 리스트 영역 가장 아래(테이블 헤더 바로 위)로 이동하며 단일 선택만 지원한다.

**FR-6. 다건 선택 및 일괄 액션**

- 행 좌측에 체크박스 컬럼 추가. 헤더 체크박스로 현재 페이지 전체 선택 가능.
- 1건 이상 선택 시 리스트 상단에 일괄 액션 바가 등장하고, 선택 카운트·선택 해제·승인 버튼을 노출한다.
- 클릭 시 확인 모달 → 일괄 처리 → 결과 토스트(성공·실패 카운트). 확인 모달은 승인 가능 건수와 건너뛰는 건수를 명시한다.
- 부분 성공 안내 시 실패 건의 사유를 함께 노출한다 (예: **이미 확정된 예약은 승인할 수 없습니다**).

**FR-6-1. 인라인 승인 차단**

- 처리 대기 중 요청이 있는 예약은 인라인 승인 버튼을 비활성하고 **얼럿이 있는 예약은 상세 페이지에서 처리해주세요.** 를 안내한다.

**FR-7. 상단 도구 영역**

- 전체 {n}건 카운트, 리스트/캘린더 뷰 토글, 예약내역 엑셀·패키지 예약 엑셀 내보내기를 제공한다.

**FR-8. 상세 페이지 정보 구조(IA) 재편 및 정보 블록 정비**

- 상세 화면을 처리 층(상단 고정 액션 바 + 요청 처리·진행 배너) → 요약 층(식별 헤더 + 주요 정보 요약 카드) → 세부 층(섹션형 블록)의 3개 층으로 재편한다 (유저 플로우 '상세 페이지 정보 구조(IA) 재편' 참조).
- 식별 헤더: 상태 배지 → 스팟·상품·옵션 타이포그래피 위계, 예약 ID 인라인, 재예약 횟수·멤버십 결제 뱃지 우측 정렬.
- 요약 카드(주요 정보): 방문일시 · 예약자 · 방문 인원 · 결제 금액을 카드 1개로 압축.
- 세부 블록 순서: 예약상품 세부 정보 → 예약자 세부 정보 → 결제 정보 → 바우처 관리 → 기타사항. 각 블록은 공통 섹션 헤더로 구분하고 라벨-값 카드형 그리드로 구성한다.
- 기존의 '상점 정보 / 계정 정보 / 예약 정보' 평면 테이블 나열 구조는 위 구조로 대체된다.
- 상태 배지는 리스트와 동일한 컬러 코딩을 사용한다.
- 구체 레이아웃(컬럼 수·간격·타이포 스케일)은 와이어프레임 및 디자인 단계에서 확정한다.

**FR-9. 상세 페이지 상단 액션 영역 통합**

- 상세 상단에 액션 버튼을 1뎁스로 통합하고 영역을 상단 고정한다.
- 승인하기(확정 완료 시 사용 완료 처리) / 예약 취소 요청하기 / 예약 변경 요청하기.
- 취소 요청·변경 요청 클릭 시 각각 모달이 열린다 (FR-9-1, FR-9-2 참조).
- 모달 셸(헤더·취소·확인 버튼 배치·키보드 닫기 동작 등)은 공통 패턴으로 통일한다.
- 처리 대기 중인 변경 요청 또는 취소 요청이 있는 경우 변경/취소 요청 버튼은 모두 비활성으로 렌더되고, 버튼 영역 하단에 **진행 중인 요청이 종결된 후 변경/취소 요청을 다시 보낼 수 있습니다.** 를 표시한다.
- 비활성 판단은 BR-3 응답의 처리 대기 중 요청 유형 필드로 결정한다 — 클라이언트가 추가 호출 없이 즉시 분기할 수 있어야 한다.

**FR-9-1. 예약 변경 요청 모달**

- 모달 타이틀: 예약 변경 요청.
- 본문 구성 (위→아래): 변경 요청 예약일(복수 후보) / 템플릿 카테고리 드롭다운(파트너용 기본 / 직접 입력) / 세부 템플릿 드롭다운(파트너용일 때만, 기본값 예약 마감으로 인한 날짜/시간 변경 안내) / 제목·본문.
  - 파트너용: 예약자 언어 번역 자동 렌더, 수정 불가.
  - 직접 입력: 세부 템플릿 숨김, 제목·본문 자유 입력.
- 하단 액션: 취소 / 확인(메일 보내기). 파트너용은 변수 자동 바인딩 발송, 직접 입력은 작성값 그대로 발송.

**FR-9-2. 예약 취소 요청 모달**

- 모달 타이틀: 예약 취소 요청.
- 예약 정보 요약 + 취소 사유 선택 + 확인 시 발송·취소 대기 전환 안내.

**FR-9-3. 요청 처리·진행 배너**

- 상단 액션 영역과 본문 사이에 요청 처리·진행 배너 자리를 둔다. 처리 대기 중인 요청이 없으면 렌더되지 않는다.
- 4가지 요청 유형(유저 변경 / 관리자 변경 / 파트너 변경 / 파트너 취소)을 동일한 시각적 컴포넌트로 노출하되 칩·헤드라인·상세 라벨·액션이 달라진다 (유저 플로우 '요청 처리·진행 배너' 참조).
- 유저 변경 요청은 승인/거절/무시 액션과 각 도움말을, 파트너 변경 요청은 유저 응답 시 승인/거절을, 파트너 취소·관리자 변경·미응답 파트너 변경은 대기 상태를 노출한다.
- 요청 종결 시 배너는 사라지고 변경/취소 요청 버튼이 다시 활성된다.

**FR-9-4. 방문일 직접 변경**

- 주요 정보 블록에서 방문일 변경 버튼으로 방문일·시간을 직접 변경할 수 있고, 변경 시 예약자 안내 문구를 노출한다.
- 등급이 TRAVEL_PARTNER_SUPERIOR인 경우에만 노출한다.

**FR-9-5. 상세 본문 운영 블록**

- 예약상품 세부 정보(상품·수량·인원별 요구정보), 예약자 세부 정보(국적·SNS·이메일 발송 포함), 결제 정보(할인·정산·멤버십 할인 툴팁), 바우처 관리(발급·생성), 기타사항(특이사항 편집 + 최근/전체 수정내역) 블록을 노출한다.

**FR-10. 모바일 환경 대응**

- 리스트는 카드 리스트로 전환한다 (상태 배지·요청 칩·스팟·상품·옵션·예약자·인원·방문일시·예약 코드·승인 버튼).
- 필터는 모바일 레이아웃으로 재배치하고 데스크톱 대비 축소된 세트를 노출한다. 주문상태·변경요청은 드롭다운으로 제공하고, 스팟 selector는 별도 줄 풀폭 드롭다운으로 둔다. 특이사항 필터·빠른 기간 프리셋·필터 초기화 버튼·필터 칩은 모바일 리스트 화면에서 생략한다.
- 상세는 풀스크린 시트로 열리고(오버레이 모달 아님), 헤더(뒤로 + 예약 코드 + 상태 배지) + 카드형 블록 스택 본문 + 하단 고정 액션 바(승인/사용 완료 처리 풀폭 + 취소 요청·변경 요청 2분할)로 구성한다.
- 예약 변경 요청·예약 취소 요청 모달은 풀스크린 바텀시트(헤더 + 본문 + 하단 고정 취소/확인)로 제공한다.
- 데이터·동작·요청 처리 로직·버튼 활성/비활성 규칙은 데스크톱과 동일하며 표현(레이아웃)만 모바일에 맞춘다.

### 백엔드 요구사항

**BR-1. 예약 리스트 조회 API 필터·정렬 파라미터 정비**

- 헤더 클릭 정렬을 지원하기 위해 정렬 키 + 정렬 방향 파라미터를 정비한다.
  - 지원 정렬 키: 방문 일시 / 상태. 입력값이 없으면 기본 정렬(방문 일시 오름차순) 적용.
- 필터 파라미터를 정비한다: 키워드, 예약 언어, 기간 기준(예약 일자/생성일)+기간, 주문상태, 특이사항 유무, 변경요청 유형. 변경요청 유형별 카운트도 함께 반환한다.
- 기존 필터 항목(스팟 등)은 변경 없이 유지한다.

**BR-2. 일괄 승인 API**

- 예약 코드 다건 입력 → 각 건에 대해 승인 처리 → 건별 성공·실패·사유를 포함한 결과 응답.
- 승인 대기가 아닌 상태의 건은 실패 처리되고 사유 코드와 메시지가 함께 반환된다.
- 트랜잭션은 건별로 독립 처리되어, 일부 실패가 전체 실패로 이어지지 않는다.
- 인가 검증: 요청 파트너가 보유하지 않은 예약은 처리 대상에서 제외된다.

**BR-3. 예약 상세 조회 응답 정비**

- 상세 상단 액션 영역과 요청 처리·진행 배너에서 사용하는 다음 정보가 한 번의 호출로 응답에 포함되도록 정비한다.
  - 현재 상태와 함께, 가능한 액션 목록 (승인/사용 완료 처리 가능 여부·취소 요청 가능 여부·변경 요청 가능 여부 등 상태 머신 기반 플래그).
  - 각 액션이 비활성일 경우의 사유 코드 및 안내 메시지.
  - 현재 처리 대기 중인 요청 유형(없음 / 유저 변경 / 관리자 변경 / 파트너 변경 / 파트너 취소)과 표시·처리에 필요한 데이터(요청일·유저 응답일·취소 사유 등).
- 클라이언트에서 추가 호출 없이 액션 영역의 활성/비활성과 배너 표시·처리 분기를 결정할 수 있어야 한다.

**BR-4. 예약 변경 요청 모달 — 템플릿 조회 및 디폴트 결정**

- 카테고리 '파트너용'에서 사용하는 메일 템플릿 목록은 [COM-2503](https://creatrip.atlassian.net/browse/COM-2503)에서 정의된 마스터 단위 응답을 사용한다. 응답에는 마스터 식별자·한국어 제목·예약자 언어 번역(제목·본문)이 포함된다.
- 디폴트 템플릿 선택 규칙: 한국어 제목이 예약 마감으로 인한 날짜/시간 변경 안내 인 마스터를 기본 선택한다. 해당 마스터가 없으면 응답 목록의 첫 번째 마스터를 기본 선택한다.
- 언어 디폴트는 예약자의 예약 언어로 설정한다. 해당 언어 변형이 응답에 없으면 응답에 포함된 첫 번째 언어로 기본 선택한다.
- 카테고리 '직접 입력'인 경우 템플릿 디폴트 결정 규칙은 적용되지 않으며, 파트너가 입력한 제목·본문을 그대로 전달한다.
- 변경 요청 메일 발송은 기존 어드민 발송 흐름을 그대로 사용한다. 새 발송 API를 추가하지 않는다.

**BR-5. 요청 처리·방문일 변경·운영 블록 데이터**

- 요청 처리·진행 배너의 처리 액션(유저 변경 승인/거절/무시, 파트너 변경에 대한 유저 응답 승인/거절 등)은 기존 요청 처리 흐름을 그대로 활용한다.
- 방문일 직접 변경, 특이사항 편집, 수정내역 조회, 바우처 발급·생성, 이메일 발송 등 상세 본문 블록이 사용하는 데이터·동작은 기존 흐름을 활용하며, 본 티켓에서 새 인터페이스를 추가하지 않는다. 신규 인터페이스가 필요한 항목이 발견되면 별도로 정리한다.
