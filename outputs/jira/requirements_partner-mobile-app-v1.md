# 파트너 예약 관리 모바일 앱 v1 — 요구사항 정리

> 프레임워크 선정(Capacitor vs RN) 판단을 위한 자료. 양식 문서가 아닌 v1 스코프 + 디테일 정리.

## 목표

- v1의 본질: 현재 카카오 **알림톡(공식 채널)을 모바일 앱 푸시로 전환**.
- 스코프: 예약 관리 + 푸시 알림. v2의 다이렉트 메시징은 별도.
- 안정성 요건: 파트너 매장 운영에 직접 영향 → 출시 전 충분한 테스트 + 기능 오류 최소화.

---

## 요구사항

### 1. 파트너 로그인

- 어드민 자격증명과 **동일** (어드민 로그인 가능한 모든 파트너 계정이 그대로 사용 가능).
- 파트너 등급 `TRAVEL_PARTNER` / `TRAVEL_PARTNER_SUPERIOR` 모두 동일 기능 사용.
- **로그인 후 재로그인 불필요** — 사실상 무기한 장기 토큰.
- 토큰은 OS 보안 저장소에 보관 (iOS Keychain / Android Keystore).
- 관리자 측에서 권한 회수 등으로 토큰 강제 무효화 가능한 구조.
- 공유 디바이스(매장 공용 단말) 시나리오는 v1 미지원.

### 2. 예약 리스트 — 푸시 트리거 기반

- **푸시 수신이 갱신 트리거**. 알림톡의 "지금 들어왔다" 즉시성을 그대로 대체.
- 앱 진입 시점에 최신 리스트 1회 동기화.
- 다중 스팟 보유 파트너: 모든 보유 스팟의 예약 **통합 노출**. 푸시 본문에 스팟명을 포함해 식별.
- 스팟별 필터는 v1 비범위.
- **포그라운드에서 푸시 수신 시**: 시스템 배너 노출 + 리스트 자동 갱신 (둘 다 수행).

### 3. 예약 처리 액션

- `[승인]` / `[변경 요청]` / `[취소 처리]` 3종 액션.
- **변경 요청 흐름**: 어드민의 로그인 상태 변경요청 폼에서 추출 예정인 공용 폼 컴포넌트(`DateChangeRequestMailTemplate`)를 그대로 호출.
- **모든 처리 액션은 운영팀 어드민 알림 시스템에 정상 도달해야 함** (별도 기획 진행 중인 어드민 알림 — `requirements_admin-partner-action-notification.md`).
- 처리 완료 시 **인앱 토스트**로 결과 피드백 (어드민의 "저장되었습니다" 패턴과 동일 톤):
  - 파트너가 유저의 예약을 **승인** 완료한 시점
  - 파트너가 **변경 요청 발송**을 완료한 시점
  - 파트너가 **취소 처리**를 완료한 시점

### 4. 푸시 알림 — 5종 이벤트

다음 시점에 푸시 발송:

1. 예약 접수 (유저가 신규 예약 생성)
2. 유저의 예약 변경 요청
3. 유저의 예약 취소 요청
4. 예약 변경 처리 완료
5. 예약 취소 처리 완료

- 본문에 스팟명, 예약자명 등 식별 정보 포함.
- 푸시 탭 시 해당 **예약 상세로 딥링크**.
- 콜드 스타트 + 토큰 만료 케이스: 로그인 화면 → 로그인 성공 후 **원래 의도된 예약 상세로 자동 복귀** (intent preservation).

### 5. 푸시 수신 설정

- 위 **5종 이벤트 타입별로 ON/OFF 토글**.
- 앱 내에서 파트너가 직접 변경.
- OS 푸시 권한 레이어와는 별개의 서버 측 발송 제어.

### 6. OS 푸시 권한 거절 케이스

- 앱 진입 시 인앱 상단 안내 배너: "푸시가 꺼져 있어요. 알림을 받으시려면 설정에서 켜주세요."
- 배너 CTA → **OS 설정 화면으로 딥링크**.
- 알림톡 채널은 일절 건드리지 않음 (별개 채널).

### 7. 알림 인박스 (푸시 조회 및 보관)

- 수신한 푸시 이력을 **30일 보관**, 시간순 노출.
- 각 항목: 이벤트 타입, 스팟명, 예약자명, 발생 시각, 읽음/안읽음 (배경색 구분).
- 항목 클릭 시: 읽음 상태 전이 + 해당 **예약 상세로 이동**.
- **단건 삭제** 가능.
- 어드민 알림에서 사용되는 처리 필요/처리됨/자동확정 상태 라벨은 본 인박스에는 적용하지 않음 (단순화).

### 8. 알림톡과의 관계

- **앱과 알림톡은 별개 채널**. 앱은 알림톡 관련 UI/조작을 일절 노출하지 않음.
- 알림톡 수신 설정은 **관리자 운영 영역** — 어드민에 기존 토글 기능 존재, 그대로 활용.
- 전환 운영 흐름:
  1. 관리자가 파트너에게 앱 사용 권유
  2-1. 사용함 → 관리자가 어드민에서 해당 파트너의 알림톡 설정 제거
  2-2. 미사용 → 알림톡 설정 유지

### 9. 강제 업데이트 인프라

- 앱 진입 시 minimum supported version 체크 엔드포인트 호출.
- 응답에 따라 **강제 업데이트 화면을 노출할 수 있는 인프라**를 v1 출시 시점에 박아둠.
- 실제 강제 발동 정책은 운영 중에 정의.

## 프레임워크 평가 시 고려할 요소

### 필요한 네이티브 통합

- **FCM / APNS 푸시** — 포그라운드/백그라운드 양쪽에서 안정적으로 수신, 배너 노출, 페이로드 핸들링.
- **푸시 페이로드 기반 딥링크** — 예약 상세 화면으로 라우팅. 콜드 스타트 시에도 intent preservation.
- **OS 설정 화면 딥링크** — 푸시 권한 거절 안내 배너의 CTA.
- **보안 토큰 저장** — Keychain / Keystore.
- **앱 진입 시 minimum version gate** — 강제 업데이트 화면 진입 차단.

### 기존 자산 재사용 가능성

본 v1의 기능 대부분이 어드민에 이미 존재하거나 진행 중이라, 재사용 폭이 프레임워크 결정에 큰 변수가 됩니다.

- 어드민 React + Apollo + GraphQL 코드, 컴포넌트, 쿼리·뮤테이션
- 추출 예정 공용 변경 요청 폼 (`DateChangeRequestMailTemplate`)
- 예약 처리 mutation (`confirmReservation` 등) — 어드민과 동일 호출

### 기능 성격

- 리스트 표시 + 단건 액션 버튼 중심. 네이티브 제스처·복잡한 애니메이션 비중 낮음.
- 오프라인 우선 동기화 미요건 (v1 비범위).
- 카메라/AR/위치 등 네이티브 센서 의존 없음.
- v2(다이렉트 메시징)도 리스트 + 텍스트 입력 + 자동 번역 호출 중심 → 동일 프레임워크 연속성 평가 필요.

### 안정성 관점

- 파트너 매장 운영에 직접 영향 → 출시 전 충분한 테스트.
- **푸시 신뢰성**(전송 누락, 백그라운드 처리)이 알림톡 대체의 핵심 품질 지표.
- 기능 오류 최소화 — 어드민에서 이미 검증된 코드 경로를 재사용할수록 안정성 기여.

### 의존 기획서 (선행/병행)

- `requirements_partner-alimtalk-reservation-change-request.md` — 변경 요청 공용 폼 추출. 본 v1 변경 요청 흐름이 의존.
- `requirements_admin-partner-action-notification.md` — 파트너 액션이 어드민 알림에 도달하는지 검증 대상.
- `requirements_partner-permission-open-to-all.md` — 파트너 등급 간 기능 동일성 근거.

### 함께 검토 부탁드리는 항목

- iOS App Store 심사 통과 — 단순 WebView 래퍼에 대한 reject 리스크 vs 푸시·인박스 같은 네이티브 통합으로 정당화 가능 여부 (Capacitor 측 평가 핵심).
- Capacitor 시: 어드민 웹 번들에서 파트너 라우트만 잘라낸 별도 빌드 타겟 구성 가능성 (번들 사이즈/의존성 추출).
- RN 시: 어드민의 React 컴포넌트·쿼리를 어느 정도까지 직접 재사용 가능한지, 어디부터 분기 구현이 필요한지.
- v2 다이렉트 메시징 + 자동 번역 확장 시 두 옵션의 친화도.
- 두 옵션의 빌드/배포 파이프라인 및 장기 유지보수 비용.
