# 세부 기획안 요구사항 문서 양식

> 파트너용 예약 관리 앱 정식 요구사항. 기존 `requirements_partner-mobile-app-v1.md`는 초안으로 두고, 본 문서를 개발 논의 기준 문서로 사용한다.
> 범위: Phase 1(예약 관리 + 푸시 전환), Phase 2(파트너↔고객 DM). DM 스펙은 추가될 수 있다.

## 배경

### 문제 정의

현재 파트너는 예약 접수·변경·취소를 카카오 알림톡(공식 채널)으로 전달받는다. 알림톡은 즉시성은 확보되지만 다음 한계가 있다.

- 채널 운영 비용이 지속 발생한다.
- 파트너가 받은 알림과 실제 처리(승인·변경·취소) 동선이 분리되어 있어, 알림을 보고 별도로 어드민에 들어가 처리해야 한다.
- 파트너와 고객이 예약 관련 내용을 **직접 주고받을 수단이 없다.** 예약 변경 같은 소통이 CS나 알림톡을 우회한다.
- 파트너(주로 한국)와 고객(주로 외국)의 **언어 장벽**으로 직접 소통 자체가 어렵다.

본 앱은 두 단계로 이 문제를 해결한다.

- **Phase 1**: 알림톡을 앱 푸시로 전환하고, 예약 처리 액션을 앱 안에서 바로 수행한다.
- **Phase 2**: 예약 단위로 파트너와 고객이 직접 소통하는 DM을 제공하고, 자동 번역으로 언어 장벽을 없앤다.

### 가설적 임팩트

- 알림톡 발송 비용 절감(앱 사용 전환 파트너 비중에 비례). 정량값 {TBD}
- 푸시로 전환해도 알림톡 수준의 즉시성을 유지하여 예약 처리 지연을 늘리지 않는다.
- 예약 변경 커뮤니케이션을 DM으로 흡수하여 관련 CS 인입을 감소시킨다. 정량값 {TBD}
- 웹은 읽기만 가능하게 하여 고객의 **앱 설치 동기**를 만든다.

## 구현

### 유저 플로우

#### Phase 1 — 예약 관리 + 푸시

- 파트너는 앱에 **어드민과 동일한 계정**으로 로그인한다. 한 번 로그인하면 재로그인 없이 계속 사용한다.
- 신규 예약, 고객의 예약 변경 요청, 고객의 예약 취소 요청이 발생하면 파트너는 **푸시 알림**을 받는다.
- 파트너는 푸시를 탭하여 해당 예약 상세로 바로 진입한다.
- 파트너는 예약 상세에서 **[승인] / [변경 요청] / [취소 처리]** 중 하나를 수행한다.
- 처리를 마치면 파트너는 결과 안내(인앱 토스트)를 보고, 처리 내용은 운영팀 어드민 알림에도 도달한다.
- 파트너는 받은 푸시 이력을 앱 내 알림 인박스에서 다시 확인한다.

#### Phase 2 — 파트너↔고객 DM

- 예약이 **'승인대기'부터 '확정'까지의 상태**인 동안, 파트너와 고객은 해당 예약에 연결된 DM으로 서로 메시지를 주고받는다. (주 사용 맥락: 예약 변경 관련 소통)
- **앱을 쓰는 파트너 ↔ 앱을 쓰는 고객**: 읽기·쓰기 모두 가능하다.
- **웹의 파트너 ↔ 웹의 고객**: 읽기만 가능하다. 메시지 작성은 앱에서만 가능하며, 이는 고객에게 앱 사용 동기를 제공하기 위함이다.
- 메시지는 상대의 언어로 **자동 번역**되어 노출된다.
- 예약이 **'사용 완료' 상태가 되면 DM 입력이 막힌다.** 과거 대화 내역은 계속 열람할 수 있다.
- 파트너와 고객은 과거 DM 내역을 열람하고, 개별 메시지를 삭제할 수 있다.
- 관리자는 어드민에서 파트너와 고객이 나눈 DM을 모니터링한다.

### 프론트엔드 요구사항

#### Phase 1 — 앱

- **로그인**: 어드민 자격증명으로 로그인. 토큰은 OS 보안 저장소에 보관하고, 사실상 무기한 유지한다. 관리자 측 권한 회수 시 강제 무효화될 수 있다. (공유 단말 시나리오는 비범위)
- **예약 리스트**: 푸시 수신을 갱신 트리거로 삼고, 앱 진입 시 1회 동기화한다. 다중 스팟 보유 파트너는 모든 스팟의 예약을 통합 노출하며, 항목에 스팟명을 함께 보여 식별한다. 포그라운드에서 푸시를 받으면 시스템 배너 노출과 리스트 자동 갱신을 함께 수행한다.
- **예약 상세 + 처리 액션**: **[승인] / [변경 요청] / [취소 처리]** 3종. 변경 요청은 어드민의 변경요청 폼과 동일한 공용 폼을 호출한다. 처리 완료 시 인앱 토스트로 결과를 안내한다.
- **푸시 알림**: 예약 접수 / 변경 요청 / 취소 요청 / 변경 처리 완료 / 취소 처리 완료 5종 이벤트. 본문에 스팟명·예약자명 등 식별 정보를 포함하고, 탭 시 예약 상세로 딥링크한다. 콜드 스타트·토큰 만료 시 로그인 후 의도한 예약 상세로 자동 복귀한다.
- **푸시 수신 설정**: 위 5종 이벤트 타입별 ON/OFF 토글을 앱 안에서 직접 변경한다.
- **OS 푸시 거절 케이스**: 앱 진입 시 상단 안내 배너 노출 — **"푸시가 꺼져 있어요. 알림을 받으시려면 설정에서 켜주세요."** 배너 CTA는 OS 설정 화면으로 딥링크한다.
- **알림 인박스**: 수신한 푸시 이력을 30일 보관하고 시간순으로 노출한다. 각 항목은 이벤트 타입·스팟명·예약자명·발생 시각·읽음/안읽음을 보이고, 클릭 시 읽음 처리 후 예약 상세로 이동한다. 단건 삭제가 가능하다.
- **강제 업데이트**: 앱 진입 시 최소 지원 버전을 확인하고, 필요 시 강제 업데이트 화면을 노출할 수 있는 구조를 둔다. (실제 발동 정책은 운영 중 정의)

#### Phase 2 — 앱 (DM 작성·열람)

- 파트너와 고객은 **예약 상세에서 DM으로 진입**한다.
- DM 화면은 메시지 목록을 시간순으로 보이고, 새 메시지를 실시간으로 갱신한다.
- 사용자는 텍스트를 입력해 전송한다. 보낸 메시지와 받은 메시지는 **상대 언어로 자동 번역**되어 표시된다. (원문/번역문 노출 방식 {TBD})
- 사용자는 메시지의 읽음 상태를 확인하고, 과거 내역을 열람하며, 개별 메시지를 삭제할 수 있다.
- 예약이 **'사용 완료' 상태이면 입력창을 비활성화**하고 안내를 노출한다 — **"이용이 완료된 예약이라 메시지를 보낼 수 없어요."** (문구안). 기존 내역은 계속 열람 가능하다.

#### Phase 2 — 웹 (파트너 어드민 / 고객 웹, 읽기 전용)

- 파트너 어드민과 고객 웹은 해당 예약의 DM 내역을 **읽기 전용**으로 노출한다.
- 메시지 입력·전송 진입점은 노출하지 않거나 비활성화하고 안내를 보인다 — **"메시지 보내기는 앱에서 할 수 있어요."** (문구안)

#### Phase 2 — 관리자 어드민 (모니터링)

- 관리자는 파트너와 고객이 나눈 DM을 조회·열람한다. (예약 / 파트너 / 고객 기준 조회, 대화 내역 열람)
- 노출 범위·검색·신고 처리 등 세부 운영 기능 {TBD}

### 백엔드 요구사항

#### Phase 1

- **파트너 인증**: 어드민과 동일 계정 체계. 장기 토큰 발급과 관리자 측 강제 무효화 지원.
- **예약 조회·처리**: 어드민의 예약 처리 로직(승인·변경요청·취소)을 재사용한다. 모든 처리는 운영팀 어드민 알림 시스템에 정상 도달해야 한다.
- **푸시 발송**: 5종 이벤트 시점에 푸시를 발송한다. (현재 푸시 인프라는 OneSignal) 본문 식별 정보·딥링크 페이로드를 포함한다.
- **푸시 수신 설정 저장**: 이벤트 타입별 ON/OFF를 서버에서 관리한다. OS 권한과는 별개의 발송 제어다.
- **알림 인박스 저장**: 발송 이력을 30일 보관·조회한다.
- **버전 게이트**: 최소 지원 버전 확인 엔드포인트를 제공한다.

#### Phase 2

- **DM 도메인**: 예약 단위로 메시지를 저장·조회·삭제한다. 메시지 주체(파트너/고객)·발신 시각·읽음 상태를 관리한다.
- **상태 기반 가드**: 예약 상태가 **'승인대기'~'확정'일 때만 작성 가능**하고, **'사용 완료'면 작성 불가**로 처리한다. 상태 전이 시 작성 가능 여부가 즉시 반영되어야 한다.
- **채널별 권한 분기**: 앱은 읽기·쓰기, 웹은 읽기만 허용한다.
- **자동 번역**: 메시지를 상대 언어로 번역해 전달한다. (현재 번역 인프라 활용) 원문 보존 여부·재번역 정책 {TBD}
- **실시간 전달**: 새 메시지를 상대에게 실시간 전달하고, DM 수신 시 푸시를 발송한다. (실시간 전송 방식 — 구독/푸시 기반 — {TBD})
- **관리자 모니터링 조회**: 파트너-고객 DM을 관리자 어드민에서 조회하는 API를 제공한다.

## 참고: RN vs Native 간략 의견 (개발 논의용)

> 프레임워크는 개발자분들과 논의해 확정한다. 아래는 v2(DM)까지 포함했을 때의 잠정 의견이며, Capacitor는 후보에서 제외했다.

- **잠정 의견: v2 DM을 포함하면 RN이 유리.** 초안(v1 단독)에서 네이티브로 기운 근거는 "출시 후 거의 안 고침 + 푸시 디버깅 레이어 단순화"였는데, DM은 양 플랫폼에서 **계속 진화하는 UI surface**라 네이티브의 2-코드베이스(Swift+Kotlin) 반복 비용이 누적된다.
- **자산 재사용**: 채팅 UI는 React 선언형 모델의 강점 영역이고, 어드민의 React·Apollo·GraphQL 자산을 RN이 그대로 공유한다. 네이티브는 데이터 레이어만 재사용(Apollo iOS/Kotlin codegen)하고 UI는 두 번 작성한다.
- **푸시 신뢰성은 프레임워크 요인이 약함**: 현재 푸시는 OneSignal 기반이고 RN·네이티브 모두 OneSignal SDK가 성숙하다. "기존 앱 푸시 불안정"은 프레임워크보다 **통합·설정 품질** 문제일 가능성이 높다.
- **단서**: 킬/백그라운드 data-only 푸시 처리 같은 임계 구간만 네이티브 모듈로 보완하는 하이브리드를 권한다. 피해야 할 시나리오는 **v1을 네이티브로 만든 뒤 v2에서 재작성**하는 것 — v1+v2를 한 지평으로 보면 RN 연속성이 합리적이다.
